# plugin-record-list Specification

## Purpose

검증된 플러그인 기본 컬럼 정의와 공통 조회 API를 사용해 여러 데이터 종류를 재사용 가능한 React 목록으로 표시하고, 번호형 페이지 탐색과 조회 모드별 상태를 일관되게 제공한다.

목록의 페이지·응답 계약은 [조회 API](../record-query-api/spec.md)를 따른다. 저장형 목록에는 아래의 내부 UUID·수집 상태·저장 시각·수동 동기화 요구사항이 적용된다. 라이브 목록에는 [라이브 조회 계약](../live-db-plugin-source/spec.md)과 조회 API의 라이브 요구사항이 적용되며, 외부 키로 상세를 조회하고 저장·수집 시각을 생성하지 않는다. 공통 컬럼 표시와 번호형 탐색은 두 모드에서 재사용한다. 검색·필터는 [검색 명세](../record-search-filters/spec.md), 정렬은 [정렬 명세](../record-sorting/spec.md)를 따른다.

## Requirements

### Requirement: 목록 레코드에서 공통 상세로 이동한다
기본 목록은 별도 `상세` 액션 열과 `보기` 링크 없이 각 데이터 행 전체를 상세 이동 대상으로 제공해야 한다(SHALL). 각 저장 레코드의 플랫폼 내부 UUID를 같은 메뉴의 상세 경로에만 SHALL 사용해야 하며, 외부 원천의 `externalKey`를 route 식별자로 사용하지 않아야 한다(MUST NOT). 목록을 조회하는 보안팀과 개발팀 사용자에게 동일한 탐색 동작을 제공하며 기존 조회 범위를 변경하지 않아야 한다(MUST). 각 행은 Tab으로 접근할 수 있는 상세 링크와 Enter 활성화를 제공하고, 보조 기술에 링크 의미와 해당 레코드의 상세 이동 대상을 전달해야 한다(SHALL). 마우스 hover와 키보드 focus 상태는 행 전체에서 시각적으로 구별되어야 한다(MUST).

#### Scenario: 목록 행 상세 이동
- **WHEN** 사용자가 데이터 행의 어느 셀이나 그 여백을 클릭한다
- **THEN** 현재 메뉴 경로와 해당 레코드 내부 UUID로 생성한 상세 URL로 이동한다
- **AND** 목록에는 별도 `상세` 액션 열과 `보기` 링크가 표시되지 않는다

#### Scenario: 키보드와 보조 기술 접근
- **WHEN** 사용자가 Tab으로 데이터 행의 상세 링크에 접근한다
- **THEN** 행마다 하나의 Tab 정지점에서 행 전체의 focus 상태가 보인다
- **AND** 보조 기술은 링크와 레코드를 식별하는 상세 이동 대상 이름을 전달한다
- **AND** Enter를 누르면 클릭과 동일한 상세 URL로 이동한다

#### Scenario: 행 hover 표시
- **WHEN** 포인터가 데이터 행의 어느 셀 위에 놓인다
- **THEN** 행 전체의 hover 상태와 클릭 가능함을 나타내는 포인터를 표시한다

#### Scenario: 표시 값이 없거나 중복된 레코드
- **WHEN** 레코드의 표시 값이 누락되거나 다른 레코드와 같다
- **THEN** 링크의 접근 가능한 이름은 내부 UUID를 포함해 대상을 구별하고 URL도 해당 내부 UUID를 사용한다
- **AND** 선언하지 않은 원천 필드는 이름에 추가하지 않는다

#### Scenario: 데이터 없는 상태
- **WHEN** 최초 로딩, 빈 결과 또는 조회 실패로 표시할 저장 레코드가 없다
- **THEN** 가상의 상세 이동 행이나 링크를 생성하지 않고 기존 상태 안내를 유지한다

#### Scenario: 상세에서 목록 복귀
- **WHEN** 사용자가 목록 복귀 동작을 선택한다
- **THEN** 같은 플러그인의 등록 메뉴 경로로 이동한다

### Requirement: 선언형 기본 컬럼으로 저장 레코드를 표시한다
클라이언트는 route context의 pluginId, sourceId, dataType으로 플랫폼 저장 레코드 목록을 조회하고 플러그인의 검증된 기본 columns 순서와 표시명으로 공통 목록을 렌더링해야 한다(SHALL). 각 행은 `sourceValues`에서 선언된 column key만 읽어야 하며 선언되지 않은 필드, `omittedFields`, 큰 본문, 원천 설정과 Connection 정보를 표시하거나 별도로 요청하지 않아야 한다(MUST).

#### Scenario: 플러그인 기본 목록 표시
- **WHEN** 저장 조회 API가 레코드를 반환하고 메뉴의 columns가 여러 scalar 필드를 선언한다
- **THEN** 화면은 선언 순서와 표시명을 표 머리글에 사용하고 각 행에서 해당 key의 값만 표시한다

#### Scenario: 다른 플러그인 정의 재사용
- **WHEN** 이름, 경로, 조회 범위와 컬럼이 다른 검증된 플러그인 메뉴로 이동한다
- **THEN** 클라이언트 본체에 플러그인별 목록 코드를 추가하지 않아도 해당 정의로 목록을 조회하고 표시한다

#### Scenario: 비공개 필드 제외
- **WHEN** 목록 응답의 `sourceValues`에 columns에 선언되지 않은 필드가 포함된다
- **THEN** 화면은 그 필드의 이름과 값을 렌더링하지 않는다

### Requirement: 기본 scalar 값을 일관되게 표현한다
클라이언트는 선언 타입에 따라 string은 문자열 그대로, number는 한국어 locale 숫자, boolean은 `예` 또는 `아니요`, datetime은 한국어 locale 날짜·시간으로 표시해야 한다(SHALL). null, 누락 또는 선언 타입과 맞지 않는 값은 `—`로 표시해야 한다(MUST).

#### Scenario: 기본 타입 표시
- **WHEN** 한 행에 유효한 string, number, boolean, datetime 값이 있다
- **THEN** 각 값은 선언 타입에 맞는 기본 표현으로 표시된다

#### Scenario: 빈 값 표시
- **WHEN** 선언된 필드가 null이거나 `sourceValues`에 없다
- **THEN** 해당 셀은 빈 셀 대신 `—`를 표시한다

#### Scenario: 타입 불일치 표시
- **WHEN** 저장 값이 선언된 scalar 타입과 맞지 않거나 datetime 문자열이 유효하지 않다
- **THEN** 화면은 값을 추정하거나 객체를 문자열화하지 않고 `—`를 표시한다

### Requirement: 수집 및 조회 상태를 구분한다
클라이언트는 목록 로딩, 미수집, 정상 빈 결과, 수집 중, 마지막 실행 실패, 부분 완료와 조회 실패를 사용자가 구분할 수 있게 표시해야 한다(SHALL). 실행 중·실패·부분 완료에도 저장 items가 있으면 기존 목록을 함께 유지해야 한다(MUST).

#### Scenario: 최초 로딩
- **WHEN** 현재 조회 범위의 첫 요청이 완료되지 않았다
- **THEN** 화면은 목록 로딩 상태를 표시하고 이전 범위의 행을 표시하지 않는다

#### Scenario: 미수집 상태
- **WHEN** collection status가 `never_collected`이고 items가 비어 있다
- **THEN** 화면은 아직 수집된 데이터가 없음을 안내한다

#### Scenario: 정상 빈 결과
- **WHEN** collection status가 `success`이고 items가 비어 있다
- **THEN** 화면은 수집은 완료됐지만 표시할 결과가 없음을 안내한다

#### Scenario: 수집 중 기존 결과
- **WHEN** collection status가 `running`이다
- **THEN** 화면은 수집 중임을 알리고 반환된 저장 items가 있으면 목록도 함께 표시한다

#### Scenario: 실패 또는 부분 완료 결과
- **WHEN** collection status가 `failed` 또는 `partial`이다
- **THEN** 화면은 마지막 실행 상태를 각각 구분해 경고하고 반환된 저장 items가 있으면 목록도 함께 표시한다

#### Scenario: 조회 실패
- **WHEN** 저장 조회 클라이언트가 취소 이외의 실패 결과를 반환한다
- **THEN** 화면은 안전한 조회 실패 메시지와 다시 시도 동작을 표시하며 실패 응답 원문을 노출하지 않는다

### Requirement: 페이징 컨트롤의 상태와 접근성을 일관되게 제공한다
기본 목록은 현재 페이지·전체 건수와 20·50·100·200건 페이지 크기를 표시하고 처음·이전 화살표 아이콘, 최대 10개 페이지 번호, 다음·마지막 화살표 아이콘 동작을 SHALL 제공해야 한다. 현재 페이지는 aria-current=page로 표시하고 버튼은 의미 있는 접근성 이름과 키보드 조작을 제공해야 한다. 번호 구간은 1~10, 11~20처럼 현재 페이지가 포함된 10개 단위여야 한다.

#### Scenario: 표 상단 조회 정보와 크기 선택
- **WHEN** 기본 목록을 표시한다
- **THEN** 표 좌측 상단에는 `전체 N건`, 우측 상단에는 `20개씩 보기`, `50개씩 보기`, `100개씩 보기`, `200개씩 보기` 선택을 표시한다
- **AND** 표 하단에는 페이지 탐색 버튼을 표시하며 별도의 `현재 / 전체 페이지` 문구와 현재 항목 수 문구는 표시하지 않는다

#### Scenario: 첫 묶음 탐색 상태
- **WHEN** 첫 페이지가 표시되고 다음 페이지가 있다
- **THEN** 처음·이전을 비활성화하고 다음·마지막을 활성화하며 현재 페이지를 1로 표시한다

#### Scenario: 마지막 묶음 탐색 상태
- **WHEN** 마지막 페이지가 표시된다
- **THEN** 다음·마지막을 비활성화하고 현재 페이지와 이전 이동 가능 여부를 유지한다

#### Scenario: 보조 기술을 이용한 조작
- **WHEN** 사용자가 키보드 또는 스크린 리더로 11페이지 이상인 목록을 탐색한다
- **THEN** 현재 페이지를 포함한 최대 10개 번호와 이동 버튼의 이름·상태를 식별하고 유효한 대상을 선택할 수 있다

#### Scenario: 로딩과 빈 결과 및 조회 실패 상태
- **WHEN** 조회가 진행 중이거나 실패했다
- **THEN** 마지막 성공 페이지와 항목을 유지하고 로딩·오류·재시도를 구분하며 불가능한 이동을 비활성화한다. 빈 결과는 전체 0건과 모든 이동 비활성 상태로 표시한다

### Requirement: 조회 조건 변경과 요청 생명주기를 안전하게 처리한다
클라이언트는 route context 또는 묶음 크기가 바뀌면 현재 페이지를 초기화하고 새 조건의 1페이지를 조회해야 한다(SHALL). 진행 중인 이전 요청은 AbortSignal로 취소하고 그 결과가 새 화면 상태를 덮지 못하게 해야 한다(MUST). 묶음 이동 조회가 실패하면 마지막으로 성공한 목록과 탐색 위치를 유지해야 한다(MUST).

#### Scenario: 묶음 크기 변경
- **WHEN** 사용자가 20·50·100·200 중 다른 묶음 크기를 선택한다
- **THEN** 클라이언트는 현재 페이지를 초기화하고 현재 조회 범위의 page=1을 새 limit으로 요청한다

#### Scenario: route context 변경
- **WHEN** 사용자가 다른 플러그인 메뉴로 이동한다
- **THEN** 클라이언트는 이전 위치와 행을 폐기하고 새 pluginId, sourceId, dataType으로 1페이지를 요청한다

#### Scenario: 이전 요청의 늦은 완료
- **WHEN** 조건 변경 또는 새 이동 전에 시작된 요청이 취소 후 늦게 완료되거나 실패한다
- **THEN** 그 결과는 현재 조건의 목록·위치·오류를 변경하지 않는다

#### Scenario: 묶음 이동 조회 실패
- **WHEN** 페이지 이동 조회가 실패한다
- **THEN** 화면은 안전한 오류와 재시도 동작을 표시하면서 마지막으로 성공한 목록, 현재 페이지를 유지한다

#### Scenario: 검색·필터·정렬 조건 변경
- **WHEN** 적용된 검색·필터·정렬 조건이 변경된다
- **THEN** 같은 초기화 경계를 적용하여 1페이지부터 요청하고 이전 조건의 응답을 무시한다

### Requirement: 기본 목록은 번호로 페이지를 직접 조회한다
기본 목록은 cursor 이력 대신 page=1부터 시작하여 선택한 페이지를 동일 범위와 limit으로 직접 SHALL 조회해야 한다. 응답 items는 누적하지 않고 교체하며 서버가 보정한 page를 현재 위치로 사용해야 한다.

#### Scenario: Jump to arbitrary or last page
- **WHEN** 사용자가 페이지 번호 또는 마지막 이동을 선택한다
- **THEN** 선택한 번호 또는 totalPages로 직접 조회하고 성공한 응답의 page 및 items를 표시한다

#### Scenario: Range shrinks
- **WHEN** 마지막 페이지의 항목이 삭제되어 요청한 페이지가 범위를 벗어난다
- **THEN** 서버가 반환한 마지막 유효 페이지로 화면 위치를 보정한다

### Requirement: 플러그인 전체 동기화 범위와 실행 가능성을 표시한다
목록 화면은 `지금 동기화` 동작 주변에 현재 목록의 데이터 종류나 페이지가 아니라 해당 플러그인의 활성 수집 대상 전체가 full 범위로 실행됨을 SHALL 안내해야 한다. 플러그인을 사용할 수 없거나 활성 수집 대상이 없거나 실행 권한이 없으면 동작을 비활성화하거나 숨기고 사용자가 알 수 있는 범위에서 이유를 표시해야 한다(SHALL).

#### Scenario: 실행 가능한 플러그인
- **WHEN** 사용자가 실행 권한이 있고 플러그인에 활성 수집 대상이 있다
- **THEN** 화면은 `지금 동기화` 버튼과 플러그인의 활성 수집 대상 전체가 실행된다는 안내를 표시한다

#### Scenario: 활성 대상 없음
- **WHEN** 플러그인에 실행 가능한 활성 수집 대상이 없다
- **THEN** 화면은 동기화 동작을 실행할 수 없게 하고 활성 대상이 없다는 이유를 표시한다

#### Scenario: 실행 권한 없음
- **WHEN** 현재 사용자가 수동 동기화 실행 권한이 없다
- **THEN** 화면은 실행할 수 있는 동작을 제공하지 않고 허용된 범위의 권한 안내만 표시한다

### Requirement: 실행 중 중복 조작을 막고 완료 결과를 표시한다
목록 화면은 동기화 요청을 보내는 동안과 접수된 실행이 terminal 상태가 되기 전까지 추가 동기화 조작을 MUST 허용하지 않아야 한다. 화면은 동기화 중, 성공, 부분 성공, 실패와 마지막 성공 시각을 구분해 표시하고, 실패 상세에는 서버가 허용한 안전한 안내만 사용해야 한다(SHALL).

#### Scenario: 접수 요청 중 중복 클릭
- **WHEN** 수동 동기화 접수 요청이 완료되지 않은 상태에서 사용자가 버튼을 다시 조작한다
- **THEN** 화면은 두 번째 요청을 보내지 않고 요청 중 상태를 표시한다

#### Scenario: 실행 중 상태
- **WHEN** 수동 동기화가 accepted 또는 running 상태다
- **THEN** 버튼은 비활성화되고 화면은 동기화 중 상태를 표시한다

#### Scenario: 부분 성공 또는 실패
- **WHEN** 상태 조회가 partial 또는 failed를 반환한다
- **THEN** 화면은 결과를 구분하고 서버가 제공한 안전한 후속 조치와 기존 저장 목록을 함께 표시한다

#### Scenario: 마지막 성공 시각
- **WHEN** 플러그인 대상 중 성공 이력이 있다
- **THEN** 화면은 locale에 맞춘 마지막 성공 시각을 표시한다

### Requirement: 완료 후 목록을 첫 페이지부터 갱신한다
접수한 동기화가 success, partial 또는 failed로 종료되면 목록 화면은 진행 상태 조회를 중단하고 현재 플러그인·데이터 종류·묶음 크기의 cursor 없는 첫 페이지를 SHALL 다시 조회해야 한다. 이전 페이지의 늦은 응답이나 polling 응답은 갱신된 목록과 상태를 덮어써서는 안 된다(MUST NOT).

#### Scenario: 성공 후 목록 갱신
- **WHEN** 접수한 동기화가 success로 종료된다
- **THEN** 화면은 방문한 cursor 이력과 현재 페이지 위치를 초기화하고 첫 페이지의 최신 저장 데이터를 조회한다

#### Scenario: 부분 성공 후 목록 갱신
- **WHEN** 접수한 동기화가 partial로 종료된다
- **THEN** 화면은 결과 경고를 유지하면서 첫 페이지를 다시 조회해 성공적으로 저장된 데이터를 표시한다

#### Scenario: 실패 후 기존 데이터 유지
- **WHEN** 접수한 동기화가 새 데이터를 확정하지 못하고 failed로 종료된다
- **THEN** 화면은 첫 페이지를 다시 조회하고 기존 저장 데이터와 실패 안내를 함께 표시한다

#### Scenario: route 변경 중 완료
- **WHEN** 사용자가 다른 플러그인 route로 이동한 뒤 이전 route의 실행 또는 polling 요청이 완료된다
- **THEN** 이전 결과는 현재 route의 목록·실행 상태를 변경하지 않는다
