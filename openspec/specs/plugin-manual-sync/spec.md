# plugin-manual-sync Specification

## Purpose

보안 운영자가 플러그인 데이터 목록에서 해당 플러그인의 활성 수집 대상 전체를 비동기로 실행하고, 권한·중복 실행·결과 보존 경계 안에서 진행 상태와 결과를 확인할 수 있게 한다.

## Requirements

### Requirement: 플러그인별 수동 동기화를 비동기로 접수한다
플랫폼은 유효하고 활성 수집 대상이 있는 plugin ID에 대해 그 플러그인의 활성 대상 전체를 full 범위로 실행하는 수동 동기화 요청을 SHALL 제공해야 한다. 요청이 접수되면 수집 완료를 기다리지 않고 `202 Accepted`와 불투명한 요청 식별자를 반환해야 하며(MUST), 다른 플러그인의 대상을 포함해서는 안 된다(MUST NOT).

#### Scenario: 수동 동기화 접수
- **WHEN** 실행 권한이 있는 사용자가 활성 수집 대상이 있는 플러그인의 동기화를 요청한다
- **THEN** API는 `202 Accepted`와 요청 식별자를 반환하고 해당 플러그인의 활성 대상 전체에 full 수집을 비동기로 요청한다

#### Scenario: 장시간 수집
- **WHEN** 원천 수집 완료에 HTTP 요청 제한보다 긴 시간이 필요하다
- **THEN** 접수 응답은 완료를 기다리지 않고 반환되며 실행 결과는 상태 조회로 확인할 수 있다

#### Scenario: 다른 플러그인 격리
- **WHEN** 한 플러그인의 수동 동기화가 접수된다
- **THEN** 다른 plugin ID에 속한 수집 대상은 실행 범위에 포함되지 않는다

### Requirement: 실행 가능성과 중복 상태를 안정적으로 반환한다
플랫폼은 plugin ID가 현재 registry에 없거나 활성 수집 대상이 없으면 원천 수집을 시작하지 않고 안정된 공개 오류 코드와 실행 불가 이유를 SHALL 반환해야 한다. 같은 대상·full 범위의 실행이 이미 진행 중이면 중복 수집을 시작해서는 안 되며(MUST NOT), `409 Conflict`와 현재 실행을 식별할 수 있는 비밀정보 없는 참조를 반환해야 한다(MUST).

#### Scenario: 사용할 수 없는 플러그인
- **WHEN** 현재 registry에 없는 비활성 또는 제거된 plugin ID로 동기화를 요청한다
- **THEN** API는 실행을 시작하지 않고 플러그인을 사용할 수 없다는 안정된 오류를 반환한다

#### Scenario: 활성 대상 없음
- **WHEN** 플러그인은 식별되지만 실행 가능한 활성 수집 대상이 없다
- **THEN** API는 실행을 시작하지 않고 활성 대상이 없다는 이유를 반환한다

#### Scenario: 중복 실행 요청
- **WHEN** 기동·CLI·API 요청으로 같은 대상과 full 범위의 실행이 이미 진행 중이다
- **THEN** API는 두 번째 원천 수집을 시작하지 않고 `409 Conflict`와 현재 실행 참조를 반환한다

### Requirement: 실행 권한 경계를 적용한다
수동 동기화 API는 실행 서비스에 도달하기 전에 `collection:execute` 권한 판단을 SHALL 수행해야 한다. 계정관리가 비활성화된 배포 모드에서는 모든 접속 요청을 허용하는 정책을 적용할 수 있으나, 권한 판단을 생략해서는 안 되며(MUST NOT), 권한이 없는 요청은 대상 존재 여부나 실행 상태를 추가로 노출하지 않고 거부해야 한다(MUST).

#### Scenario: 계정관리 비활성 모드
- **WHEN** 계정관리가 비활성화된 배포에서 수동 동기화를 요청한다
- **THEN** 비활성 모드 권한 정책이 요청을 허용하고 정상적인 대상 검증을 계속한다

#### Scenario: 권한 없는 요청
- **WHEN** 활성화된 권한 정책이 요청 주체에게 `collection:execute`를 허용하지 않는다
- **THEN** API는 수집을 등록하지 않고 대상 존재 여부나 현재 실행 정보 없이 `403 Forbidden`을 반환한다

### Requirement: 요청과 플러그인 실행 결과를 조회한다
플랫폼은 접수된 요청 식별자에 대해 `accepted | running | success | partial | failed` 상태와 시작·종료 시각, 대상 집계, 비밀정보 없는 오류 요약을 SHALL 반환해야 한다. 플러그인 상태에는 마지막 성공 시각을 포함해야 하며(SHALL), 존재하지 않거나 호출자에게 허용되지 않은 요청 식별자는 서로 구분 가능한 내부 정보를 노출하지 않아야 한다(MUST NOT).

#### Scenario: 실행 중 상태 조회
- **WHEN** 접수된 수동 동기화의 하나 이상의 대상이 진행 중이다
- **THEN** 상태 조회는 요청 식별자, running 상태와 알려진 시작 시각을 반환한다

#### Scenario: 부분 성공 집계
- **WHEN** 플러그인의 활성 대상 중 일부만 성공한다
- **THEN** 상태 조회는 partial과 대상별 공개 상태, 종료 시각 및 마지막으로 성공한 실행 시각을 반환한다

#### Scenario: 실패 정보 보호
- **WHEN** Connection 인증, 원천 응답 또는 저장 오류로 실행이 실패한다
- **THEN** 응답에는 안정된 오류 코드와 후속 조치용 안전한 요약만 포함되고 자격증명·원천 응답·내부 stack은 포함되지 않는다

#### Scenario: 알 수 없는 요청 식별자
- **WHEN** 존재하지 않거나 호출자에게 허용되지 않은 요청 식별자를 조회한다
- **THEN** API는 두 경우를 구분하지 않는 not-found 응답을 반환한다

### Requirement: 실패해도 저장 데이터와 플랫폼 관리 정보를 보존한다
수동 동기화는 기존 공통 수집·가공·검증·저장 계약을 SHALL 사용해야 한다. 실패 또는 부분 실패한 대상은 마지막으로 확정된 checkpoint와 기존 저장 레코드 및 플랫폼이 관리하는 담당자·업무 필드를 보존해야 하며(MUST), 성공한 묶음만 기존 원자 저장 계약에 따라 반영해야 한다(MUST).

#### Scenario: 원천 수집 실패
- **WHEN** 새 묶음을 확정하기 전에 원천 수집이 실패한다
- **THEN** 기존 저장 데이터, checkpoint와 플랫폼 관리 필드는 변경되지 않고 실행은 failed로 기록된다

#### Scenario: 일부 레코드 격리
- **WHEN** 한 실행에서 유효한 레코드와 격리되는 잘못된 레코드가 함께 처리된다
- **THEN** 유효한 묶음은 공통 저장 계약으로 반영되고 기존 플랫폼 관리 필드는 보존되며 실행은 partial로 기록된다
