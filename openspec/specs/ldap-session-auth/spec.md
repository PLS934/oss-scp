# ldap-session-auth Specification

## Purpose

선택적으로 활성화한 단일 LDAP/Active Directory 인증과 서버 세션으로 플랫폼 접근자를 확인하고, 기본 비활성화 설치의 기존 익명 사용 호환성을 유지한다.

## Requirements

### Requirement: 선택적 계정관리 모드
플랫폼은 `AUTH_ENABLED` 설정으로 계정관리 모드를 선택하도록 SHALL 지원하고 기본값을 비활성화로 두어야 한다. 비활성화 상태에서는 LDAP 및 세션 설정을 요구하지 않고 기존 웹 화면과 API를 인증 없이 제공해야 한다.

#### Scenario: 기본 비활성화 실행
- **WHEN** 운영자가 `AUTH_ENABLED`를 지정하지 않고 플랫폼을 실행한다
- **THEN** LDAP 연결 없이 기존 웹 화면과 API를 사용할 수 있다

#### Scenario: 활성화 설정 누락
- **WHEN** 운영자가 인증을 활성화했지만 필요한 LDAP 또는 세션 설정을 제공하지 않는다
- **THEN** 서버는 안전하지 않은 부분 설정으로 실행되지 않고 설정 오류를 비밀값 없이 보고한다

### Requirement: TLS로 보호된 단일 LDAP 인증
플랫폼은 단일 LDAP/AD 디렉터리에서 서비스 계정으로 사용자를 검색한 뒤 검색된 사용자 DN과 사용자가 입력한 비밀번호로 Bind하여 신원을 확인해야 한다(SHALL). `ldaps://` 직접 TLS와 `ldap://` 연결 후 필수 StartTLS를 지원하고 두 방식 모두 서버 인증서를 검증해야 하며, 평문 Bind 또는 인증서 검증 비활성화 설정을 제공해서는 안 된다(MUST NOT).

#### Scenario: LDAPS 로그인 성공
- **WHEN** 사용자가 LDAPS로 연결된 디렉터리의 올바른 로그인 ID와 비밀번호를 제출한다
- **THEN** 플랫폼은 서비스 계정 검색과 사용자 Bind를 완료하고 인증된 사용자 신원을 얻는다

#### Scenario: StartTLS 로그인 성공
- **WHEN** LDAP URL이 `ldap://`이고 StartTLS를 성공한 뒤 사용자가 올바른 자격증명을 제출한다
- **THEN** 플랫폼은 TLS가 설정된 연결에서만 서비스 계정 검색과 사용자 Bind를 수행한다

#### Scenario: StartTLS 협상 실패
- **WHEN** `ldap://` 연결에서 StartTLS 협상 또는 서버 인증서 검증이 실패한다
- **THEN** 플랫폼은 어떤 자격증명도 평문으로 전송하지 않고 인증 서비스를 사용할 수 없다는 안전한 오류를 반환한다

#### Scenario: 사내 CA 사용
- **WHEN** 운영자가 유효한 사내 CA 인증서를 설정하고 해당 CA로 서명된 LDAP 서버에 연결한다
- **THEN** 플랫폼은 주입된 CA를 신뢰 기준에 포함해 서버 신원을 검증한다

### Requirement: 안전한 LDAP 사용자 검색
플랫폼은 로그인 ID를 LDAP 검색 필터에 넣기 전에 RFC 4515 방식으로 escaping하고 설정된 검색 범위에서 결과가 정확히 한 개인 경우에만 사용자 Bind를 시도해야 한다(SHALL). 안정적인 사용자 식별자는 설정된 LDAP 속성에서 읽어야 한다.

#### Scenario: 검색 필터 특수문자
- **WHEN** 로그인 ID에 LDAP 필터 문법으로 해석될 수 있는 문자가 포함된다
- **THEN** 해당 문자는 데이터로 escaping되어 검색 조건을 변경하지 못한다

#### Scenario: 검색 결과 없음 또는 복수
- **WHEN** 사용자 검색 결과가 없거나 둘 이상이다
- **THEN** 플랫폼은 사용자 Bind를 시도하지 않고 두 경우를 동일한 잘못된 자격증명 결과로 처리한다

#### Scenario: 안정적 사용자 식별자 누락
- **WHEN** 검색된 엔트리에 설정한 사용자 식별자 속성이 없거나 정규화할 수 없다
- **THEN** 플랫폼은 세션을 만들지 않고 외부에는 사용자 존재 여부나 LDAP 응답 내용을 노출하지 않는다

### Requirement: 영속 서버 세션
플랫폼은 인증 성공 시 예측할 수 없는 세션 ID를 발급하고 PostgreSQL 또는 MySQL에 세션 ID의 keyed hash, 사용자 식별자, 로그인 ID, 생성 시각과 절대 만료 시각만 저장해야 한다(SHALL). 원본 세션 ID와 LDAP 비밀번호는 DB 또는 로그에 저장해서는 안 된다(MUST NOT).

#### Scenario: 로그인 후 세션 발급
- **WHEN** LDAP 인증이 성공한다
- **THEN** 브라우저는 원본 세션 ID가 담긴 쿠키를 받고 DB에는 원본을 복원할 수 없는 keyed hash와 최소 세션 정보만 저장된다

#### Scenario: API 서버 재시작
- **WHEN** 유효한 세션이 DB에 있는 동안 API 서버가 재시작된다
- **THEN** 동일한 쿠키를 가진 사용자는 다시 로그인하지 않고 인증 상태를 복구한다

#### Scenario: 세션 만료
- **WHEN** 저장된 절대 만료 시각이 지난 세션으로 요청한다
- **THEN** 플랫폼은 세션을 거부하고 만료된 DB 행을 삭제 대상으로 처리한다

#### Scenario: PostgreSQL과 MySQL 동등성
- **WHEN** 같은 세션 동작을 지원 대상 PostgreSQL 또는 MySQL 설치에서 수행한다
- **THEN** 생성, 조회, 만료와 삭제의 관찰 가능한 결과가 동일하다

### Requirement: 안전한 세션 쿠키와 로그아웃
세션 쿠키는 HttpOnly, SameSite=Lax, Path=/ 속성을 가져야 하고 운영 환경에서는 Secure 속성을 가져야 한다(SHALL). 로그아웃은 대응하는 서버 세션을 폐기하고 쿠키를 만료시키며 유효한 세션이 없어도 반복 호출 가능한 동일한 성공 응답을 반환해야 한다.

#### Scenario: 운영 로그인 쿠키
- **WHEN** 운영 환경에서 로그인이 성공한다
- **THEN** 응답 쿠키에는 HttpOnly, SameSite=Lax, Secure와 Path=/ 속성이 적용된다

#### Scenario: 로그아웃 후 재사용
- **WHEN** 사용자가 로그아웃한 뒤 기존 쿠키로 보호된 API를 호출한다
- **THEN** 서버는 기존 세션을 찾지 못하고 인증 필요 응답을 반환한다

#### Scenario: 로그아웃 반복
- **WHEN** 세션 쿠키가 없거나 이미 폐기된 상태에서 로그아웃을 호출한다
- **THEN** 서버는 사용자 또는 세션 존재 여부를 노출하지 않고 같은 성공 응답과 만료 쿠키를 반환한다

### Requirement: API 인증 경계
인증 활성화 상태에서 플랫폼은 health, ready와 인증 API를 제외한 모든 기존 업무 API에 유효한 서버 세션을 요구해야 한다(SHALL). health와 ready는 컨테이너 상태 확인을 위해 계속 익명 호출할 수 있어야 한다.

#### Scenario: 익명 상태 확인
- **WHEN** 인증을 활성화한 서버의 health 또는 ready API를 자격증명 없이 호출한다
- **THEN** 각 API는 기존 상태 확인 계약에 따라 응답한다

#### Scenario: 익명 업무 API 호출
- **WHEN** 인증을 활성화한 서버의 기존 업무 API를 세션 없이 호출한다
- **THEN** 서버는 업무 데이터를 반환하지 않고 `401 AUTH_REQUIRED`를 반환한다

#### Scenario: 인증된 업무 API 호출
- **WHEN** 유효한 세션을 가진 사용자가 기존 업무 API를 호출한다
- **THEN** 서버는 기존 API 계약에 따라 요청을 처리한다

#### Scenario: 다른 출처의 상태 변경 요청
- **WHEN** 인증 쿠키가 포함된 상태 변경 요청의 Origin이 요청 Host와 일치하지 않는다
- **THEN** 서버는 요청을 거부하고 상태를 변경하지 않는다

### Requirement: 세션 상태와 로그인 웹 흐름
웹 클라이언트는 업무 데이터보다 먼저 인증 상태를 확인하고, 인증 활성화 상태에서 세션이 없으면 로그인 화면만 표시해야 한다(SHALL). 유효한 세션이면 기존 앱과 현재 로그인 ID 및 로그아웃 동작을 제공해야 한다.

#### Scenario: 인증 활성화 첫 방문
- **WHEN** 세션이 없는 사용자가 인증 활성화된 웹 화면을 연다
- **THEN** 업무 메뉴나 데이터를 요청하지 않고 로그인 화면을 표시한다

#### Scenario: 새로고침 후 복구
- **WHEN** 유효한 HttpOnly 세션 쿠키를 가진 사용자가 페이지를 새로고침한다
- **THEN** 웹은 세션 상태를 복구하고 기존 앱을 표시한다

#### Scenario: 보호 요청 중 세션 상실
- **WHEN** 앱 사용 중 보호 API가 인증 필요 응답을 반환한다
- **THEN** 웹은 인증 상태를 다시 확인하고 유효한 세션이 없으면 로그인 화면으로 전환한다

#### Scenario: 비활성화 웹 호환성
- **WHEN** 인증이 비활성화된 설치에서 사용자가 웹 화면을 연다
- **THEN** 별도의 로그인 없이 기존 앱을 사용한다

### Requirement: 인증 실패 보호와 rate limit
플랫폼은 존재하지 않는 사용자, 복수 검색 결과와 잘못된 비밀번호에 동일한 `401 INVALID_CREDENTIALS` 응답을 반환해야 한다(SHALL). LDAP 연결·TLS·서비스 Bind·검색 장애는 세부정보 없는 `503 AUTH_SERVICE_UNAVAILABLE`로 처리하고, IP와 로그인 ID별 로그인 시도 제한을 적용해야 한다.

#### Scenario: 자격증명 실패 일반화
- **WHEN** 로그인 ID가 없거나 검색 결과가 복수이거나 비밀번호가 틀리다
- **THEN** 상태, 응답 본문과 공개 메시지는 사용자 존재 여부를 구분하지 않는다

#### Scenario: LDAP 장애
- **WHEN** 디렉터리 연결 또는 검색을 수행할 수 없다
- **THEN** 서버는 내부적으로 자격증명 실패와 구분하되 외부에는 LDAP 상세나 비밀정보 없는 서비스 장애 응답을 반환한다

#### Scenario: 로그인 시도 초과
- **WHEN** 한 IP 또는 한 로그인 ID가 설정된 시간창의 시도 수를 초과한다
- **THEN** 서버는 LDAP 인증을 수행하지 않고 `429 TOO_MANY_ATTEMPTS`와 재시도 가능 시간을 반환한다

#### Scenario: 비밀정보 비노출
- **WHEN** 설정, LDAP, DB 또는 인증 요청 처리에서 오류가 발생한다
- **THEN** 로그와 공개 응답에 사용자 비밀번호, Bind 비밀번호, 원본 세션 ID, 세션 hash 또는 LDAP 드라이버 상세가 포함되지 않는다
