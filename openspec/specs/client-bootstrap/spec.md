# client-bootstrap Specification

## Purpose

개발자가 로컬에서 클라이언트를 실행하고 수정 결과를 즉시 확인하며, 일반 사용자가 외부 계정이나 개발 도구 없이 Docker로 시작 화면과 서버 연결 상태를 확인할 수 있는 재현 가능한 실행 기반을 제공한다.

## Requirements

### Requirement: 로컬 클라이언트 실행과 변경 반영
프로젝트는 문서화된 런타임과 패키지 관리자만으로 클라이언트를 설치·개발 실행할 수 있도록 SHALL 지원한다. DB·외부 자격증명·Docker를 요구하지 않고, 정상적인 화면 소스 변경은 개발 서버 수동 재시작이나 브라우저 수동 새로고침 없이 반영되어야 한다.

#### Scenario: 새 체크아웃에서 실행
- **WHEN** 개발자가 문서의 설치 및 클라이언트 개발 명령을 실행한다
- **THEN** 브라우저에서 앱을 식별할 수 있는 시작 화면이 표시된다

#### Scenario: 화면 변경 반영
- **WHEN** 실행 중인 개발 화면의 텍스트를 소스에서 수정하고 저장한다
- **THEN** 서버 재시작이나 수동 새로고침 없이 열린 브라우저에 수정 내용이 표시된다

### Requirement: 서버 연결 상태 표시
클라이언트는 인증 없이 시작 화면을 제공하고 `GET /api/v1/health`를 호출해 대기·성공·실패를 텍스트로 구분해야 한다(SHALL). 성공은 HTTP 200, JSON 콘텐츠 유형, 파싱 가능한 JSON 객체의 `status`가 `ok`일 때만 표시한다. 표시는 서버 HTTP 연결 상태만 의미하며 데이터 최신성이나 외부 수집처 상태를 의미하지 않아야 한다. 요청은 5초 제한 시간 이후 실패 처리해야 한다.

#### Scenario: 요청 대기
- **WHEN** 시작 화면을 열고 상태 확인 요청의 응답을 기다린다
- **THEN** 화면을 사용할 수 있으며 연결 확인 중이라는 안내가 표시된다

#### Scenario: 정상 연결
- **WHEN** 서버가 정의된 상태 확인 응답을 반환한다
- **THEN** 서버 연결 성공이 표시된다

#### Scenario: 연결 또는 응답 실패
- **WHEN** 서버가 없거나 네트워크 오류, 5초 제한 시간 초과, 비정상 HTTP 상태, 잘못된 콘텐츠 유형·JSON·status가 발생한다
- **THEN** 시작 화면은 유지되고 연결 실패가 표시되며 성공으로 처리하지 않는다

#### Scenario: 복구 후 다시 확인
- **WHEN** 서버 연결이 복구된 뒤 사용자가 페이지를 새로고침한다
- **THEN** 새 상태 확인 요청을 수행하고 정상 응답이면 성공을 표시한다

### Requirement: 동일 출처 API 연결
개발 및 Docker 실행 경로는 브라우저가 웹 화면과 동일한 출처의 API 경로로 요청하도록 SHALL 지원한다. API 경로와 응답 상태를 보존하며 환경별 서버 주소를 브라우저 번들에 고정하지 않아야 한다.

#### Scenario: 개발 프록시
- **WHEN** 개발자가 로컬 API 서버와 클라이언트를 실행하고 화면에 접속한다
- **THEN** 브라우저의 `/api/v1/health` 요청이 API 서버로 전달되어 연결 성공을 표시한다

#### Scenario: 존재하지 않는 API
- **WHEN** 웹 서버를 통해 존재하지 않는 `/api/` 경로를 호출한다
- **THEN** API의 404 응답이 유지되고 시작 화면 HTML이나 성공 응답으로 대체되지 않는다

### Requirement: Docker 정적 화면과 통합 실행
프로젝트는 Docker와 Compose만 설치한 환경에서 클라이언트·서버 이미지를 빌드하고 함께 실행할 수 있도록 SHALL 지원한다. 배포용 클라이언트 이미지는 호스트 소스 마운트와 개발 watcher 없이 정적 화면을 제공하며 서버 장애와 무관하게 화면을 제공해야 한다.

#### Scenario: Compose 통합 실행
- **WHEN** 사용자가 새 체크아웃에서 문서의 Compose 빌드·기동 명령을 실행한다
- **THEN** 공개된 웹 포트에서 시작 화면을 제공하고 프록시를 통한 서버 연결 성공을 브라우저에 표시한다

#### Scenario: API 없는 클라이언트 실행
- **WHEN** 클라이언트 이미지를 단독 실행하거나 실행 중 API 서비스를 중단한다
- **THEN** 정적 시작 화면은 제공되고 연결 실패를 안내한다

#### Scenario: 재빌드 없는 접속 설정 변경
- **WHEN** 같은 클라이언트 이미지에 문서화된 다른 API upstream 실행 설정을 지정한다
- **THEN** 이미지 재빌드 없이 지정 서버로 프록시하고 브라우저 번들에 비밀정보를 넣지 않는다

### Requirement: 재현 가능한 검사와 안내
프로젝트는 잠금 파일 기반 설치, 클라이언트 타입 검사·린트·자동화 테스트·배포 빌드와 브라우저·Docker 통합 검증을 CI에서 실행하도록 SHALL 구성한다. 문서에는 환경변수 예시, 실행·종료·정리 명령, 검증한 OS·CPU 및 미검증 범위를 명시해야 한다.

#### Scenario: 검사 실패
- **WHEN** 클라이언트 검사나 통합 검증이 실패한다
- **THEN** CI는 해당 검사를 실패로 표시하며 기존 서버 검사도 계속 실행 대상에 포함한다

#### Scenario: 문서만으로 실행
- **WHEN** 사용자가 새 환경에서 문서의 로컬 또는 Docker 경로를 따른다
- **THEN** 외부 계정 없이 시작 화면과 서버 상태를 확인하고 실행을 종료·정리할 수 있다

### Requirement: Docker 개발 중 코드 변경 반영
프로젝트는 호스트 Node.js·pnpm 설치 없이 Docker 개발 명령으로 클라이언트와 서버를 함께 실행하고 호스트의 정상 소스 변경을 이미지 재빌드 없이 반영하도록 SHALL 지원한다. 클라이언트 변경은 HMR로, 서버 변경은 자동 재시작으로 반영하며 기존 배포 이미지 실행도 유지해야 한다.

#### Scenario: Docker 개발 시작
- **WHEN** 새 체크아웃에서 문서의 Docker 개발 기동 명령을 실행한다
- **THEN** 브라우저에서 시작 화면과 실제 서버 연결 성공을 확인할 수 있다

#### Scenario: 컨테이너 실행 중 화면 변경
- **WHEN** 호스트에서 화면 텍스트를 수정한다
- **THEN** 이미지 재빌드·컨테이너 재생성·브라우저 수동 새로고침 없이 열린 화면에 수정이 반영된다

#### Scenario: 컨테이너 실행 중 서버 변경
- **WHEN** 호스트에서 정상적인 서버 응답 코드를 수정한다
- **THEN** 이미지 재빌드나 수동 재시작 없이 서버가 자동 재시작하고 다음 API 요청에 변경된 응답을 반환한다

#### Scenario: 의존성 변경 후 재설치
- **WHEN** 패키지 선언과 잠금 파일 변경 후 문서의 의존성 갱신 명령을 실행한다
- **THEN** 컨테이너 의존성이 갱신되고 호스트 의존성을 덮어쓰지 않으며 앱을 다시 실행할 수 있다

### Requirement: 다른 컴퓨터에서 웹 접속
배포 실행은 네트워크 경로와 방화벽이 허용된 다른 컴퓨터에서 실행 호스트의 IP와 웹 포트로 시작 화면에 접속할 수 있도록 SHALL 지원한다. 해당 브라우저의 API 요청은 접속한 웹 출처를 통해 서버로 전달되어야 한다.

#### Scenario: 다른 컴퓨터에서 화면과 API 확인
- **WHEN** 다른 컴퓨터의 브라우저에서 문서화된 실행 호스트 IP와 웹 포트로 접속한다
- **THEN** 시작 화면과 실제 서버 연결 성공을 확인하고 방문자 컴퓨터의 localhost로 API를 요청하지 않는다

#### Scenario: 개발 화면의 접속 제한
- **WHEN** 로컬 개발 또는 Docker 개발 설정으로 실행한다
- **THEN** 웹 화면은 실행한 컴퓨터의 localhost에서 접속할 수 있고 다른 컴퓨터에는 개발 웹 포트를 공개하지 않는다

#### Scenario: 네트워크 접근 조건 안내
- **WHEN** 사용자가 다른 컴퓨터 접속 안내를 읽는다
- **THEN** 실행 호스트 IP·웹 포트·네트워크 연결·방화벽 허용 조건과 localhost의 의미를 확인할 수 있고 자동으로 인터넷에 공개되는 것으로 안내하지 않는다

### Requirement: Docker workspace 의존성 격리 검증

프로젝트는 workspace 설치를 수행하는 모든 개발 서비스에서 루트 및 전체 workspace 패키지의 node_modules와 pnpm store를 서비스별 전용 named volume에 격리하도록 SHALL 검증한다. 새 패키지의 볼륨 누락·공유는 컨테이너 기동 전에 검사 실패로 보고해야 한다.

#### Scenario: 새 workspace의 볼륨 누락
- **WHEN** pnpm이 인식하는 새 패키지를 추가하고 개발 서비스의 의존성 볼륨을 추가하지 않는다
- **THEN** 검사 명령은 0이 아닌 종료 코드와 누락된 서비스·경로를 보고한다

#### Scenario: 개발 실행과 정리
- **WHEN** 깨끗한 임시 소스에서 개발 서비스를 실행하고 HMR·watch·의존성 재설치 검사를 마친다
- **THEN** 실제 의존성 마운트와 store는 전용 볼륨을 사용하고 호스트의 의존성 경로에는 파일이 남지 않는다
- **AND** 테스트 종료 후 해당 Compose 프로젝트의 컨테이너·볼륨과 임시 소스가 정리되며 실패는 숨기지 않는다

#### Scenario: Linux 회귀 검증
- **WHEN** Ubuntu CI에서 workspace 회귀 검사와 웹·서버·mock Docker 검사를 실행한다
- **THEN** 볼륨 누락·공유·호스트 의존성 파일 생성을 탐지하고 실제 설치·변경 반영·정리 결과를 검증한다
