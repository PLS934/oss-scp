# record-search-filters Specification

## Purpose

보안팀과 개발팀이 플러그인별 표에서 지정된 필드를 검색하고 여러 필터를 조합하여 전체 저장 데이터 중 필요한 결과를 찾도록 한다. 원천 조회 없이 두 플랫폼 DB에서 동일한 조건과 묶음 이동 규칙을 제공한다.

이 문서의 플랫폼 DB·cursor·수집 상태 요구사항은 저장형 조회에 적용한다. 라이브 조회가 재사용하는 입력 검증과 원천에서의 조건 적용·페이지 분할은 [라이브 조회 명세](../live-db-plugin-source/spec.md)를 따른다. 번호형 페이지의 응답은 [조회 API](../record-query-api/spec.md), 화면의 요청 생명주기는 [공통 목록](../plugin-record-list/spec.md)을 참조한다.

## Requirements

### Requirement: 플러그인이 검색과 필터를 명시한다
플랫폼은 최상위 string 필드의 선택적 `searchable: true`와 scalar 필드의 선택적 `filter`를 SHALL 검증해야 한다. `filter.kind`는 string/number/boolean의 `select` 또는 `multiSelect`, number의 `numberRange`, datetime의 `dateRange`를 허용한다. 선택형은 필드 타입과 일치하는 고유한 `value` 및 비어 있지 않은 `label`의 정적 `options`를 1~100개 선언해야 한다. 검색·필터 대상은 해당 데이터 종류의 기본 목록 columns에 포함되어야 한다. 미선언 필드를 타입만으로 검색·필터 대상으로 삼아서는 안 된다(MUST NOT).

#### Scenario: 유효한 선언과 기존 플러그인
- **WHEN** 플러그인이 호환되는 검색·필터를 선언하거나 새 속성을 생략한다
- **THEN** 선언은 승인되고 생략된 플러그인은 기존 목록 동작을 유지한다

#### Scenario: 잘못된 선언
- **WHEN** 중첩 필드, 목록에 없는 필드, 타입 불일치, 중복 옵션 또는 알 수 없는 필터 종류를 선언한다
- **THEN** 플랫폼은 필드 위치를 식별하는 설정 오류로 거부한다

### Requirement: 검색 필드를 OR 조건으로 조회한다
플랫폼은 검색어 앞뒤 공백을 제거하고 빈 검색어는 조건 없음으로 SHALL 처리해야 한다. 비어 있지 않은 검색어는 검색 가능한 string 필드 중 하나에 연속 부분 문자열로 포함되면 일치한다. ASCII A~Z 대소문자는 구분하지 않고 나머지 문자는 정확히 비교하며 내부 공백은 보존한다. `%`, `_`, 역슬래시는 문자 자체로 취급하고 정규식·와일드카드·단어 분할을 적용하지 않는다. null·누락·타입 불일치 값은 일치하지 않는다.

#### Scenario: 여러 필드 검색과 리터럴 문자
- **WHEN** 검색어가 지정된 필드 하나에만 포함되거나 `%`를 검색한다
- **THEN** 해당 필드가 일치하면 반환하고 `%`는 실제 해당 문자가 있는 값에만 일치한다

### Requirement: 타입별 필터를 결합한다
플랫폼은 선택형 값을 타입을 보존해 정확히 비교하고 multiSelect 내부 값은 OR, 서로 다른 필터 및 검색과는 AND로 SHALL 결합해야 한다. 문자열 선택값은 대소문자와 공백을 구분한다. numberRange는 유한한 min/max를 포함 경계로, dateRange는 유효한 `YYYY-MM-DD` from/to를 UTC 시작일 00:00 포함·종료일 다음 날 00:00 미포함으로 적용한다. 범위 한쪽 생략은 허용한다. 미선택·빈 배열·양쪽 없는 범위는 조건 없음이며 null·누락·잘못된 저장 타입은 활성 필터에 일치하지 않는다.

#### Scenario: 검색과 복수 필터
- **WHEN** 이름 검색, 영향 여부 선택, 점수 범위를 함께 적용한다
- **THEN** 검색과 두 필터를 모두 만족한 레코드만 반환한다

#### Scenario: 날짜 경계
- **WHEN** 날짜 종료일을 지정한다
- **THEN** 종료일 UTC의 모든 시각은 포함하고 다음 날 UTC 00:00은 제외한다

### Requirement: API가 선언에 맞는 조건만 받는다
GET `/api/v1/records`는 선택적인 `q` 문자열과 JSON 배열을 URL 인코딩한 `filters`를 SHALL 지원해야 한다. 항목은 `{field, kind, value}`(select), `{field, kind, values}`(multiSelect), `{field, kind, min?, max?}` 또는 `{field, kind, from?, to?}` 형태여야 한다. 서버는 등록된 범위의 선언으로 검증하고 클라이언트가 지정한 검색 필드나 임의 연산자를 신뢰해서는 안 된다(MUST NOT). q는 정규화 전후 최대 200 Unicode 코드 포인트, filters는 디코딩된 UTF-8 4096바이트 및 20항목, multiSelect는 100값으로 제한한다. 중복 필드·추가 키·반복 q/filters 인자·잘못된 JSON·미허용 값·뒤집힌 범위·잘못된 날짜·검색 미지원 범위의 비어 있지 않은 q는 DB 조회 전에 HTTP 400 `INVALID_QUERY`로 거부한다.

#### Scenario: 직접 API 우회 요청
- **WHEN** 조회자가 필터 미허용 필드나 선언되지 않은 선택값을 직접 전달한다
- **THEN** 서버는 조건을 무시하지 않고 400을 반환한다

#### Scenario: 조건 없는 기존 호출
- **WHEN** q와 filters를 생략한다
- **THEN** 기존 목록 응답과 오류 계약을 유지한다

### Requirement: 조건을 전체 데이터와 cursor에 적용한다
플랫폼은 범위 내 전체 저장 데이터에서 조건을 적용한 뒤 기존 고정 정렬과 keyset 묶음 분할을 SHALL 수행해야 한다. 조건의 정규화 결과와 검색·필터 선언을 cursor에 귀속하고 다른 조건이나 변경된 선언의 cursor는 `INVALID_CURSOR`로 거부한다. 필터 순서와 multiSelect 값 순서·중복만 다른 요청은 동일 조건이다. 기존 v1 cursor는 조건 없는 요청에만 허용한다. 수집 상태와 lastStoredAt은 기존 범위 기준을 유지하고 요약 크기 제한도 유지한다.

#### Scenario: 다음 묶음에 있는 일치 결과
- **WHEN** 조건 없는 첫 묶음에는 일치 결과가 없고 그 뒤에 일치 레코드가 있다
- **THEN** 조건부 첫 조회에서 해당 레코드를 반환한다

#### Scenario: 조건 변경과 cursor 재사용
- **WHEN** 검색어나 필터를 바꾸고 기존 cursor를 전달한다
- **THEN** 서버는 400 INVALID_CURSOR를 반환한다

#### Scenario: 양쪽 DB 동일 결과
- **WHEN** 같은 데이터와 검색·필터·cursor 요청을 PostgreSQL과 MySQL에 실행한다
- **THEN** 동일한 일치 결과·정렬·경계·hasNextPage를 제공한다

### Requirement: 공통 표에서 조건을 적용하고 초기화한다
플랫폼은 메뉴의 `list.query`에 검색 가능 여부와 선언 순서의 필터 key/label/type/kind/options만 SHALL 제공해야 한다. 기존 columns 항목 형식은 유지한다. 화면은 검색 가능한 경우 목록 위에 검색창을 표시해야 한다. 필터가 선언된 컬럼명은 해당 필터 팝오버를 여는 버튼이어야 하며 선언이 없는 컬럼명은 일반 텍스트로 유지한다. 현재 필터 조건은 검색창 아래에 `필드명: 값`과 개별 삭제 수단을 포함한 배지로 표시한다. 유효한 컬럼 필터 변경과 조건 배지 삭제는 즉시 첫 페이지 조회에 반영한다. 숫자·날짜 범위가 뒤집히는 등 입력이 유효하지 않으면 요청하지 않고 오류를 표시하며 마지막으로 성공한 결과를 유지한다. 검색어는 무테 원형 화살표 버튼 또는 Enter로 확정하고, 검색창 지우기는 입력값과 적용된 검색어를 즉시 해제한다. 공통 적용·초기화 버튼과 미적용 안내는 표시하지 않는다. 날짜는 UTC 기준임을 표시한다. 조건 변경 시 cursor 이력을 폐기하고 첫 묶음으로 조회하며 메뉴 변경 시 조건을 초기화한다. 새 조건 요청 중에는 이전 조건 결과를 표시하지 않고 늦게 도착한 이전 응답은 무시한다.

#### Scenario: 필터 즉시 적용
- **WHEN** 사용자가 두 번째 묶음에서 유효한 컬럼 필터를 변경하거나 조건 배지를 삭제한다
- **THEN** 변경 조건으로 첫 묶음을 즉시 조회하고 다른 조건은 유지한다

#### Scenario: 검색 명시적 실행
- **WHEN** 사용자가 검색어를 편집한 뒤 화살표 버튼을 누르거나 Enter를 입력한다
- **THEN** 현재 필터와 검색어를 결합해 첫 묶음을 조회하며 검색 지우기는 적용된 검색어도 즉시 해제한다

#### Scenario: 잘못된 범위 유지
- **WHEN** 숫자 또는 날짜 범위 입력이 유효하지 않다
- **THEN** 새 요청 없이 오류를 표시하고 마지막으로 성공한 결과를 유지한다

#### Scenario: 컬럼 필터 추가 및 제거
- **WHEN** 사용자가 필터가 선언된 컬럼명을 눌러 팝오버에서 조건을 입력한다
- **THEN** 검색창 아래에 해당 조건 배지를 표시하고 배지의 삭제 수단은 다른 draft 조건을 유지한 채 그 조건만 제거한다

#### Scenario: 결과 없음과 실패
- **WHEN** 활성 조건의 조회가 빈 결과로 성공하거나 서버 조회가 실패한다
- **THEN** 성공은 별도 초기화 버튼 없이 검색·필터 결과 없음 안내를, 실패는 오류 및 같은 조건 재시도를 제공하고 수집 상태 안내를 유지한다

### Requirement: 저장 조회의 접근 범위와 읽기 전용 경계를 유지한다
검색·필터는 기존 목록과 같은 접근 범위를 SHALL 사용해야 한다. 현재 계정관리 비활성화 상태에서는 기존 익명 조회를 유지하며 새 역할별 권한을 구현한 것으로 간주하지 않는다. 검색·필터 선언은 접근 권한을 부여하지 않는다. 외부 수집처 호출이나 레코드·플랫폼 담당자 정보 변경은 발생해서는 안 된다(MUST NOT).

#### Scenario: 원천 장애 중 검색
- **WHEN** 외부 원천이 중단된 상태에서 저장 데이터 검색·필터를 요청한다
- **THEN** 플랫폼 DB만 읽어 결과를 반환하고 수집 실행 및 담당자 정보를 변경하지 않는다

### Requirement: 기존 번호형 페이지네이션에도 같은 조건을 적용한다
플랫폼은 main의 번호형 목록 화면을 유지하며 count와 목록 조회에 같은 검색·필터를 SHALL 적용해야 한다. 전체 건수와 페이지 수는 일치 결과 기준이며 기존 읽기 전용 snapshot 계약을 유지한다. 조건 적용·초기화는 1페이지로 이동한다. cursor API는 계속 지원한다.

#### Scenario: 조건부 번호형 마지막 페이지
- **WHEN** 필터 결과가 여러 페이지이며 마지막 페이지를 요청한다
- **THEN** 필터 결과 기준 전체 건수·페이지 수와 마지막 결과를 반환한다
