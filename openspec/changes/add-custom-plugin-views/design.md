## Context

현재 `App`은 서버에서 받은 각 `MenuItem`에 대해 `RecordList`와 `RecordDetail` route를 직접 생성한다. 외부 플러그인 설정에는 실행 가능한 프론트엔드 코드가 포함되지 않으며, 배포 웹은 Vite로 미리 빌드한 정적 자산이다. 자세한 변경 목적은 `proposal.md`를 따른다.

이번 변경은 route 선택, 사용자 정의 화면의 공개 입력 타입, 정적 등록부와 React 오류 경계를 함께 도입한다. 서버·플러그인 설정 계약을 바꾸지 않으면서 향후 #94의 독립 UI 번들 계약이 교체할 수 있는 작은 선택 경계를 만드는 것이 필요하다.

## Goals / Non-Goals

**Goals:**

- 목록과 상세를 서로 독립적으로 교체하는 정적 타입 계약을 제공한다.
- 기존 메뉴 context, URL과 애플리케이션 shell을 그대로 사용한다.
- 등록이 없거나 사용자 정의 화면이 실패해도 다른 플러그인 사용을 유지한다.
- 현재 공통 목록·상세와 서버 조회 경계를 회귀 없이 보존한다.

**Non-Goals:**

- 외부 플러그인 JSON에 UI 경로나 번들 정보를 추가하지 않는다.
- 런타임 모듈 로딩, 별도 UI 패키지, 플러그인별 의존성과 SDK 버전 협상을 도입하지 않는다.
- 공통 목록의 검색·필터 기능을 사용자 정의 화면에 자동 합성하지 않는다. 사용자 정의 화면은 제공되는 공개 조회 클라이언트를 필요에 따라 사용한다.

## Decisions

### 플러그인 ID를 키로 하는 웹 소스 registry

`apps/web`에 `CustomPluginViews` 타입과 정적 registry 모듈을 둔다. 각 항목은 선택적인 `List`와 `Detail` React 컴포넌트를 가진다. 현재 플러그인 계약은 플러그인당 메뉴가 최대 하나이므로 `pluginId`가 충분한 키이며, source나 경로 문자열을 중복 선언하지 않는다.

registry는 서버 메뉴 응답이나 외부 설정에서 만들어지지 않고 웹 빌드가 import한다. 따라서 운영자가 검토한 코드만 현재 플랫폼 React 버전과 함께 컴파일된다. 외부 번들 manifest를 같은 registry 뒤에 연결하는 작업은 #94에서 별도로 설계한다.

대안으로 `App` 내부 조건문을 고려했지만 플러그인이 늘 때 route 코드가 플러그인 구현을 직접 알아야 하므로 제외한다. 경로 기반 registry도 고려했지만 운영자 설정으로 바뀌는 경로에 웹 빌드가 결합되므로 제외한다.

### 화면 종류별 최소 props 계약

목록 컴포넌트에는 `menu`, 상세 컴포넌트에는 `menu`와 `recordId`를 전달한다. `MenuItem`은 서버가 공개한 표시 정의와 조회 context를 이미 함께 가지므로 별도 props를 중복 정의하지 않는다. 상세 route의 URL 해석은 플랫폼이 담당해 사용자 정의 컴포넌트가 라우터 hook에 의존하지 않게 한다.

사용자 정의 화면은 기존 `records` 모듈 등 공개 웹 조회 클라이언트를 사용한다. 클라이언트 props는 권한 증명이 아니며, 서버가 요청마다 조회 범위와 향후 권한을 계속 검사한다.

대안으로 조회 결과와 로딩 상태까지 플랫폼이 props로 공급하는 방식을 고려했지만 사용자 정의 화면의 조회 방식까지 공통 화면에 결합하고 검색·집계 같은 후속 요구를 제한하므로 제외한다.

### route 선택을 작은 resolver로 분리

route를 만들 때 `pluginId`로 registry 항목을 찾고 목록·상세 컴포넌트를 각각 선택한다. 항목이나 해당 화면 종류가 없으면 기존 `RecordList` 또는 `RecordDetail`을 사용한다. resolver와 props 타입을 별도 모듈에 두어 `App`은 선택 결과만 렌더링하고, 테스트에서 임시 registry를 주입할 수 있게 한다.

### route 단위 오류 경계

선택된 사용자 정의 컴포넌트만 오류 경계로 감싼다. 렌더링 예외가 발생하면 route 본문에 일반화된 오류 안내를 표시하고, shell과 메뉴는 유지한다. route 위치 또는 선택된 플러그인·화면 종류가 바뀌면 오류 경계를 새 key로 다시 생성해 다른 화면까지 실패 상태가 이어지지 않게 한다.

오류 발생 시 공통 화면으로 자동 전환하는 방식은 선택하지 않는다. 사용자 정의 화면의 의미를 공통 화면이 온전히 대체한다는 보장이 없고, 반복 렌더링이나 사용자의 혼동을 만들 수 있기 때문이다.

### 샘플은 한 화면 종류의 교체와 반대쪽 fallback을 함께 증명

저장소의 샘플 플러그인 하나에 사용자 정의 목록 화면을 등록하고 상세 화면은 등록하지 않는다. 샘플 목록은 전달받은 공개 context를 표시하고 기존 공개 조회 클라이언트로 데이터를 읽어 전용 표현을 제공한다. 이를 통해 실제 registry 연결, 사용자 정의 목록, 공통 상세 fallback과 상세 직접 접근을 한 흐름에서 검증한다.

## Risks / Trade-offs

- [정적 registry의 플러그인 ID 오타는 빌드 시 실제 외부 registry와 대조할 수 없음] → 해당 항목은 활성 메뉴와 일치할 때만 사용되며, 샘플·통합 테스트와 문서에서 ID 일치를 검증한다.
- [사용자 정의 화면이 공통 접근성·상태 표현을 자동 상속하지 않음] → 공개 입력과 API 경계만 최소 계약으로 두고 샘플 및 문서에 로딩·오류·빈 상태와 접근성 요구를 명시한다.
- [React 오류 경계가 이벤트 handler나 비동기 오류를 포착하지 못함] → 렌더링 생명주기 오류 격리로 범위를 명시하고, 비동기 요청 오류는 각 화면이 정상 상태로 처리하게 한다.
- [플랫폼과 함께 빌드하므로 플러그인 UI 변경 때 웹 이미지를 다시 빌드해야 함] → 현재 단계의 의도된 제약이며 #94에서 독립 빌드·배포 계약으로 확장한다.

## Migration Plan

기존 registry의 초기값은 샘플로 명시한 플러그인 외에는 비어 있으며, 미등록 플러그인은 현재 공통 화면을 그대로 사용한다. 배포는 일반 웹 이미지 업데이트로 적용한다. 문제가 있으면 사용자 정의 registry 항목을 제거한 이전 웹 빌드로 롤백하며 서버나 저장 데이터 migration은 필요하지 않다.
