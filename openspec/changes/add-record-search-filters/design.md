## Context

동기는 proposal.md를 따른다. 현재 `record-list.tsx`는 범위·limit을 sessionKey로 사용하며 AbortController와 요청 번호로 늦은 응답을 배제한다. API 서비스는 범위·limit·cursor만 DB에 전달한다. `platform-db/src/query.ts`의 v1 cursor는 범위·limit·고정 정렬에 귀속되고 두 DB 어댑터는 JSON 원천 값을 저장한 platform_records를 읽는다. 플러그인 설정은 `plugin-config`가 검증하며 런타임 registry에 definitions와 menus가 있다. 기존 목록 명세는 columns 원소를 key/label/type으로 제한하므로 검색 메타데이터는 별도 list.query에 추가한다.

## Goals / Non-Goals

**Goals:** 선언 검증 → API 조건 검증 → DB 조건 적용 → 표 상호작용의 경계를 분리하고 두 DB에서 같은 결과를 제공한다.

**Non-Goals:** 새로운 수집처·변환 로직·저장 식별자·중복 및 갱신 정책은 도입하지 않는다. 담당자 데이터는 읽기 요청으로 변경하지 않는다. 정렬·개인 설정·동적 옵션·중첩 검색은 proposal.md의 제외 범위를 따른다.

## Decisions

1. **선언과 메타데이터.** 기존 FieldDefinition scalar 분기에 searchable/filter 선택 속성을 추가하고 목록 포함 여부까지 검증한다. 목록 밖 필드 검색은 기존 메타데이터 노출 제한과 충돌하므로 이번 범위에서 제외한다. list.query는 `{searchEnabled, filters: [{key,label,type,kind,options?}]}`로 제공한다. 원천 Connection이나 전체 필드 정의는 반환하지 않는다. 문자열/숫자/boolean 선택형과 numberRange/dateRange를 지원한다. 자동 타입 추론 대신 명시적 종류를 사용한다.
2. **요청 및 검증 경계.** GET의 q와 URL 인코딩된 filters JSON으로 기존 호출을 확장한다. RecordQueryService가 registry에서 해당 범위의 허용 선언을 해석한다. HTTP 문자열 파싱 이후 공통 조건 정규화로 필드·연산자·옵션·타입·한도를 확인한다. DB에는 검증된 제한적 조건 모델만 전달한다. 조건 없는 호출은 기존 범위 동작을 보존하고 활성 조건에 필요한 등록 정의가 없으면 INVALID_QUERY로 처리한다. 범용 query DSL과 POST 검색 endpoint는 현재 필요보다 넓다.
3. **검색 비교.** ASCII 대소문자를 접고 나머지는 정확히 비교하는 리터럴 부분 문자열 검색을 제안 기본값으로 정한다. 언어별 case folding·악센트 처리 및 전문 검색은 도입하지 않는다. 이는 DB 기본 collation이 만드는 결과 차이를 줄인다. PostgreSQL translate 및 MySQL 중첩 REPLACE 등으로 ASCII만 접고 명시적 이진/결정적 비교로 구현한다. LIKE 사용 시 패턴과 escape를 명시하거나 리터럴 부분 문자열 함수를 쓴다. 필드 JSON 접근도 바인딩 또는 검증된 경로 인코딩을 사용하며 사용자 텍스트를 SQL 조각으로 붙이지 않는다.
4. **타입 비교와 시간.** 선택형은 JSON 타입 확인 후 정확히 비교하고 숫자 범위는 안전한 타입 확인 이후 수치 비교한다. datetime은 저장값의 유효성을 확인하고 UTC 시각으로 비교한다. 잘못된 저장값의 변환이 전체 쿼리를 실패시키지 않도록 guarded conversion을 사용한다. 날짜 입력은 UTC 달력일로 정의하여 브라우저 시간대의 암묵적 차이를 피한다. 시작/종료 단독 입력과 종료일 다음 날 경계 계산도 검증한다.
5. **SQL 및 cursor.** 기존 범위 WHERE에 조건을 추가하고 이후 keyset 경계·ORDER BY·limit+1을 적용한다. JS에서 전체 레코드를 읽어 필터링하는 방식은 사용하지 않는다. v2 cursor에는 정규화된 조건 및 관련 선언의 SHA-256 지문을 포함한다. 정규화는 빈 조건 제거, 필드 순 정렬, 선택값 중복 제거·타입별 결정적 정렬, q ASCII 접기를 포함한다. 지문은 권한 증명이 아니며 매 요청마다 허용 선언을 검증한다. 조건 없는 기존 v1 cursor는 허용하되 활성 조건과 결합하면 거부한다. 새 cursor 크기는 기존 제한 내에 둔다. 수집 상태·마지막 저장 시각은 필터와 무관한 기존 범위 기준을 유지한다.
6. **화면 상태와 컬럼 필터.** 검색어와 필터 draft 상태를 목록 세션으로 올려 검색 영역과 표 헤더가 함께 사용한다. 검색 영역은 검색창, 현재 draft 조건 배지, 적용·초기화를 렌더링한다. 표 헤더는 `list.query.filters`에서 같은 key의 선언이 있을 때만 클릭 가능한 필터 버튼을 표시하며 선택형·다중 선택·숫자 범위·날짜 범위 팝오버를 연다. 팝오버는 `document.body`에 렌더링하고 헤더의 화면 좌표와 viewport 경계를 기준으로 배치하여 표의 가로 스크롤 영역에 잘리지 않게 한다. 바깥 클릭과 Escape로 닫고 배지 삭제는 해당 draft만 제거한다. 입력 draft와 적용된 조건은 계속 분리하고 적용/Enter로 확정한다. 적용된 조건을 sessionKey에 포함하고 기존 취소·요청 번호 패턴을 재사용한다. 초기화와 메뉴 변경은 입력·적용 조건·cursor를 함께 초기화한다. 재시도는 적용 조건을 유지한다. label, 키보드 조작, 숫자/날짜 입력 검증, 미적용 안내, 조회 실패·결과 없음 상태를 제공한다.

## Risks / Trade-offs

- JSON 부분 문자열 검색의 전체 스캔 비용 → 범위 제한 및 기존 응답 한도를 유지하고 양쪽 DB의 대표 데이터 EXPLAIN·소요 시간을 기록한다. 인덱스는 실측 근거가 있을 때만 별도 migration으로 추가한다.
- DB collation·숫자·datetime 변환 차이 → 같은 fixture로 한국어, ASCII 대소문자, 악센트, 공백, 특수문자, null, 잘못된 타입, 시간대·날짜 경계를 교차 검증한다.
- 정적 옵션이 새 원천 값과 어긋남 → 미허용 옵션 요청은 명시적으로 거부하며 새 원천 값은 필터 없는 목록에서는 그대로 조회한다. 운영자가 플러그인 옵션을 갱신한다.
- 수집 중 페이지 간 데이터 변화 → 기존 keyset 일관성 수준을 유지하며 전체 스냅샷을 보장하지 않는다.

## Migration Plan

저장 스키마 변경 없이 서버·클라이언트를 함께 배포한다. 새 속성 생략은 기존 플러그인 호환 경로다. 샘플의 실제 cve/name, score, affected, observedAt에 검색·숫자 범위·boolean 선택·날짜 범위를 선언하여 예시를 제공한다. 기존 서버는 새 플러그인 속성을 거부할 수 있으므로 롤백 시 플러그인 선언도 이전 버전으로 복원한다. v2 cursor를 이해하지 못하는 이전 버전에서는 첫 묶음부터 다시 조회한다. 개발 계획의 기존 편집과 다른 change를 덮어쓰지 않으며 0.1.0 지원 범위 변경은 이 작업에서 하지 않는다.

## 구현 시 현재 main 반영

#102가 main에 병합되어 기본 화면은 번호형 페이지네이션을 사용한다. 번호형 화면을 유지하고 동일한 검색·필터를 count와 목록 SQL 모두에 적용한다. 전체 건수와 페이지 수는 조건부 결과 기준이며 적용·초기화는 1페이지로 돌아간다. 기존 cursor API의 v2 조건 귀속과 v1 호환성도 유지한다. 번호형 count와 목록은 기존 REPEATABLE READ 읽기 전용 트랜잭션으로 일관성을 유지한다. 메뉴 전환 시 입력·적용 조건을 초기화하고 조건 변경 시 sessionKey로 이전 응답과 결과를 배제한다.
