## Purpose

개발자가 로컬에서 서버를 실행하고 수정 결과를 확인할 수 있는 기본 개발 경로와, 개발 도구를 설치하지 않은 사용자가 Docker로 동일한 서버를 실행하고 상태 확인 API로 기동 여부를 검증할 수 있는 계약을 제공한다.

## ADDED Requirements

### Requirement: 로컬 개발 실행과 변경 반영
프로젝트는 문서화된 런타임과 패키지 관리자를 설치한 개발자가 Docker 없이 의존성을 설치하고 서버를 실행할 수 있도록 SHALL 지원한다. 개발 실행은 정상적인 소스 변경을 감지해 서버를 자동 재시작해야 한다.

#### Scenario: 깨끗한 로컬 환경에서 실행
- **WHEN** 개발자가 새 체크아웃에서 문서의 의존성 설치 및 개발 실행 명령을 수행한다
- **THEN** DB·외부 계정·Docker 없이 서버가 실행되고 상태 확인 API에 접근할 수 있다

#### Scenario: 개발 소스 변경
- **WHEN** 개발 모드로 서버를 실행한 상태에서 API 응답 코드를 수정하고 저장한다
- **THEN** 서버를 직접 재실행하지 않아도 변경된 응답을 확인할 수 있다

### Requirement: 상태 확인 API 계약
서버는 인증 없이 `GET /api/v1/health` 요청에 HTTP 200, JSON 본문 `{"status":"ok"}`, JSON 콘텐츠 유형을 반환해야 한다(SHALL). 이 상태는 서버 HTTP 처리 가능 여부만 의미하며 DB·원천 수집처의 상태나 데이터 최신성을 의미하지 않는다. 내부 설정·비밀정보는 노출하지 않아야 한다.

#### Scenario: 익명 호출
- **WHEN** 로그인이나 자격증명 없이 실행 중인 서버의 상태 확인 API를 호출한다
- **THEN** HTTP 200과 정의된 JSON 응답을 받는다

#### Scenario: 존재하지 않는 경로
- **WHEN** 정의되지 않은 API 경로를 호출한다
- **THEN** 서버는 HTTP 404를 반환하며 정상 상태 확인 응답으로 대체하지 않는다

### Requirement: 실행 설정과 시작 실패
서버는 실행 시 포트를 설정할 수 있도록 SHALL 지원하고, 미설정 시 3000을 사용해야 한다. 포트가 정수 1–65535가 아니거나 이미 사용 중이면 실패 원인을 로그로 알리고 비정상 종료해야 한다.

#### Scenario: 사용자 지정 포트
- **WHEN** 사용 가능한 유효한 포트로 서버를 실행한다
- **THEN** 해당 포트에서 상태 확인 응답을 받는다

#### Scenario: 잘못된 설정 또는 포트 충돌
- **WHEN** 잘못된 포트 값을 지정하거나 이미 사용 중인 포트에서 서버를 시작한다
- **THEN** 프로세스가 0이 아닌 종료 코드와 실패 로그를 남기고 실행 성공으로 보고하지 않는다

### Requirement: 개발 도구 없는 Docker 실행
프로젝트는 Docker와 Compose를 사용할 수 있는 호스트에서 Node.js·pnpm 설치 없이 서버 이미지를 빌드하고 실행할 수 있도록 SHALL 지원한다. 이미지는 빌드된 실행 파일과 운영 의존성을 포함하고 호스트 소스 마운트·개발 watcher·DB·외부 자격증명 없이 동작해야 한다.

#### Scenario: Compose로 빌드와 실행
- **WHEN** 새 체크아웃에서 문서화된 Compose 빌드·기동 명령을 실행한다
- **THEN** 호스트에서 상태 확인 API를 호출할 수 있고 컨테이너 상태 검사가 정상으로 전환된다

#### Scenario: 이미지 단독 실행
- **WHEN** 빌드한 이미지를 소스 볼륨 없이 실행하고 포트를 공개한다
- **THEN** 호스트에 개발 도구가 없어도 상태 확인 API를 호출할 수 있다

#### Scenario: 서버가 응답하지 않는 상태
- **WHEN** 컨테이너 내부 상태 확인 요청이 설정된 제한 시간 내 성공하지 않는 상태가 반복된다
- **THEN** 상태 검사는 실패하고 설정된 재시도 기준에 따라 컨테이너를 unhealthy로 표시한다

### Requirement: 재현 가능한 검증과 안내
프로젝트는 잠금 파일을 사용하는 설치, 타입 검사, 린트, 자동화 테스트, 배포 빌드 명령과 Docker 검증을 문서화하고 CI에서 실행하도록 SHALL 구성한다. 문서는 로컬 개발과 Docker 설치·실행을 구분하며 환경변수 예시, 종료·정리 명령, 검증한 OS·CPU 범위와 미검증 범위를 알려야 한다.

#### Scenario: CI 검증 실패
- **WHEN** 타입 검사·린트·테스트·빌드·Docker 기동 및 API 검증 중 하나가 실패한다
- **THEN** CI는 해당 검증을 실패로 표시하고 성공으로 처리하지 않는다

#### Scenario: 문서로 재현
- **WHEN** 기여자가 문서의 선행 조건과 명령만 사용해 새 환경에서 검증한다
- **THEN** 로컬 개발 또는 Docker 실행 경로를 선택해 API 응답까지 확인하고 해당 실행을 종료·정리할 수 있다
