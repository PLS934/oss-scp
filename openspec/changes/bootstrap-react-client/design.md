## Context

동기는 [proposal.md](proposal.md)를 따른다. 현재 `apps/api`는 `/api/v1/health`를 제공하며 workspace는 이미 `apps/*`를 포함한다. 루트 `dev`·`start`·검사 명령은 API를 대상으로 하고 CI는 서버 로컬 검사와 Docker 검사로 구성된다. `.dockerignore`는 기본 전체 제외 후 API 빌드 입력만 허용하므로 웹 빌드 입력을 명시적으로 추가해야 한다.

개발 플랜과 이번 설계는 Docker에서도 소스 수정 자동 반영을 지원한다. 로컬 개발과 기존 배포 이미지 실행도 유지한다. 현재 미커밋 README·개발 전략·OpenSpec 설정과 개발 플랜은 사용자 작업으로 보존한다.

## Goals / Non-Goals

**Goals:** 기존 서버 계약과 실행 명령을 보존하면서 클라이언트 개발·배포·오류 경로를 검증 가능하게 연결한다.

**Non-Goals:** 범위는 proposal을 따른다. 상태 확인에 DB·connector·저장 모델·checkpoint를 도입하지 않는다. 이번 시작 화면을 업무용 JSON renderer로 일반화하지 않는다.

## Decisions

1. **독립 workspace 앱**: `apps/web`, 패키지명 `@oss-scp/web`을 사용한다. 기존 `pnpm dev`는 API watch를 유지하고 `pnpm dev:web`을 추가해 두 터미널로 실행한다. 루트 build·typecheck·test는 두 앱을 포함하도록 확장한다. 통합 개발 프로세스 관리 도구 추가보다 기존 사용법 유지와 의존성 절감을 택한다. Node.js 24.19.0·pnpm 10.34.5를 공유한다. 공식 자료와 패키지 호환성을 확인해 React 19.2.8·Vite 8.2.2·React 플러그인 6.1.1·Playwright 1.63.0을 고정했다. TypeScript 5.9.3 및 Vitest 4.1.11은 기존 버전을 재사용한다.

2. **작은 상태 화면**: 앱 제목, 서버 연결 상태, 상태의 의미와 실패 시 서버 실행 확인·새로고침 안내를 제공한다. 초기 mount에서 상대 경로로 fetch하고 5초 AbortController 제한 시간을 둔다. HTTP 200·JSON 콘텐츠 유형·객체의 `status === 'ok'`를 검사한다. 네트워크·파싱·계약 오류를 실패로 통일한다. effect 정리에서 요청·타이머를 취소하고 오래된 응답의 상태 덮어쓰기를 방지한다. 자동 폴링이나 재시도 버튼은 도입하지 않고 새로고침으로 재확인한다. 상태는 색상뿐 아니라 텍스트와 접근 가능한 알림 영역으로 표현한다.

3. **동일 출처 프록시**: 브라우저는 항상 `/api/v1/health`를 호출한다. Vite는 `/api`를 기본 `http://127.0.0.1:3000`으로 전달하고 서버 측 개발 설정 `API_PROXY_TARGET`으로 재지정한다. 로컬 Vite는 기본 `127.0.0.1:5173`에서 연결을 받으며 포트 충돌 시 실패시킨다. 절대 API 주소를 번들에 넣거나 CORS 설정을 추가하는 대안보다 환경별 재빌드와 서버 변경을 줄인다. `/api` 경로를 rewrite하지 않는다.

4. **배포 Nginx와 API 독립성**: 멀티 스테이지 Dockerfile에서 frozen lockfile로 설치·빌드하고 최종 이미지에는 정적 산출물과 Nginx 실행 설정만 포함한다. `API_UPSTREAM`은 실행 시 지정하는 host:port 값이며 Compose에서는 `api:3000`을 기본으로 한다. Nginx 템플릿 치환은 해당 설정만 대상으로 해 Nginx 자체 변수를 보존한다. Docker DNS를 사용하는 런타임 upstream 해석을 구성하여 API 이름이 기동 시 없거나 컨테이너 IP가 바뀌어도 정적 서버가 기동하고 후속 요청에서 재해석하도록 한다. 고정 upstream의 기동 시 DNS 의존과 healthy 조건의 강제 시작 의존은 피한다. API 장애는 API 요청에만 실패를 반환한다. `/api/`는 정적 fallback으로 처리하지 않는다. 이미지 healthcheck는 정적 화면 제공 여부를 검사한다. Compose 웹 포트는 `0.0.0.0:${WEB_PORT:-8080}`에 바인딩하고 기존 API 공개 포트와 계약은 유지한다.

5. **검증 구성**: 워크플로 파일은 `.github/workflows/integration-ci.yaml`, 표시 이름은 `서버·클라이언트 통합 검증`으로 한다. 기존 검사 명령과 job 구성은 유지하며 문서 참조를 새 경로로 맞춘다. Vitest로 응답 판정·제한 시간·주요 실패 조건을, Playwright로 실제 화면 상태·Vite 프록시·HMR 및 Compose 화면을 검증한다. HMR 검사는 임시 복사본을 수정해 사용자 소스를 보존하고 브라우저 document가 교체되지 않는 것도 확인한다. 기존 서버 CI 검사를 유지하면서 클라이언트 검사와 브라우저 준비 단계를 추가한다. Docker-only 설치 경로 자체는 호스트 Node.js 없이 빌드·기동 가능해야 하며 CI 브라우저 검증 도구 설치는 별개다.

6. **Docker에서도 수정 자동 반영**: 클라이언트는 컨테이너 안에서 Vite를, 서버는 NestJS watch를 실행하고 호스트 소스를 연결한다. 브라우저에서 접근할 수 있도록 개발 서버는 컨테이너 내부에서 `0.0.0.0`에 바인딩하며 웹 프록시는 `http://api:3000`을 사용한다. 호스트 node_modules를 컨테이너에 공유하지 않고 컨테이너 의존성 볼륨을 분리한다. 시작·재시작 시 frozen-lockfile 설치로 의존성 볼륨을 갱신한다. 개발 이미지에는 Nest CLI의 프로세스 트리 종료에 필요한 procps를 포함하고, 서버 개발 출력은 tsconfig.dev.json으로 의존성 볼륨 하위에 저장한다. 일반 소스 수정은 이미지 재빌드 없이 반영한다. 배포 Dockerfile의 최종 실행 단계는 기존대로 빌드 산출물만 사용한다. 기본 `compose.yaml`은 배포용이며 `compose.dev.yaml`은 여기에 개발 설정을 덧붙이는 파일로 구성한다. 배포 실행은 `docker compose up --build`, 개발 실행은 `docker compose -f compose.yaml -f compose.dev.yaml up --build`로 안내한다. 개발 파일은 단독 사용하지 않는다. 개발 웹 컨테이너는 내부 포트 8080을 사용하되 호스트 포트는 `127.0.0.1:${WEB_PORT:-8080}:8080`으로 제한한다. 개발 override에서는 ports 목록을 교체하여 기본 파일의 외부 공개 매핑이 남지 않도록 하고 필요한 Compose 버전과 병합 결과를 검증한다. 컨테이너 내부의 `0.0.0.0` 바인딩과 호스트 외부 공개는 구분한다. HMR은 실행 컴퓨터에서 사용한다. 이미지·실행 명령·환경변수·healthcheck를 개발 단계에 맞게 덮어쓰고 합성 결과에 배포 전용 설정이 남지 않는지 검증한다. 종료는 동일한 파일 조합으로 `down`을 사용한다.

7. **다른 컴퓨터에서 웹 접속**: 다른 컴퓨터 접속은 배포 실행에만 제공하며 `http://<실행 호스트 IP>:8080`으로 안내한다. 로컬 개발은 `http://localhost:5173`, Docker 개발은 `http://localhost:8080`으로 실행한 컴퓨터에서만 접속한다. `0.0.0.0`은 바인딩 주소이며 브라우저 접속 주소가 아니다. 브라우저 API 요청은 접속한 웹 주소의 상대 경로를 사용하므로 방문자 컴퓨터의 localhost를 호출하지 않는다. API 자체의 호스트 공개 범위를 추가로 넓힐 필요는 없다. 네트워크 경로와 방화벽 포트 허용을 선행 조건으로 문서화하며 방화벽·공유기·인터넷 공개 설정을 자동 변경하지 않는다.

## Risks / Trade-offs

- [API 부재 시 Nginx 시작 실패 또는 재생성 후 오래된 IP 사용] → API 없이 웹 단독 실행, API 중단·재생성 후 페이지 재확인을 실제 Docker로 검증한다.
- [루트 검사 확장과 Docker 허용 목록 변경이 서버 빌드에 영향] → 서버 기존 테스트·프로세스 검사·단독 이미지 검사를 유지한다. 환경파일·비밀정보는 빌드 입력으로 허용하지 않는다.
- [모의 응답 검사만으로 프록시 성공을 오인] → 실제 API 프로세스와 Compose 경로에서도 브라우저 연결 성공을 검증한다.
- [새 의존성·이미지 버전의 호환성] → 구현 시 선택 근거와 정확한 고정 버전을 기록하고 frozen install·빌드로 확인한다. 현재 제안은 해당 버전 검증을 완료했다는 의미가 아니다.
- [컨테이너에서 소스 변경 감지 누락·의존성 덮어쓰기] → 분리된 의존성 볼륨과 임시 복사본의 실제 변경 검사를 사용하고, 필요한 환경에서는 명시적인 polling 설정을 제공한다. 개발 종료 시 볼륨 정리와 재설치 방법도 검증한다.
- [지원 환경을 과장] → CI Ubuntu 24.04 linux/amd64를 기본 검증 대상으로 유지한다. 로컬 macOS·다른 아키텍처는 실제 실행 결과만 문서에 기록한다.

## Migration Plan

최신 main에서 저장소 전략에 맞는 작업 브랜치를 만들고 앱·공유 설정·CI·문서를 하나의 이슈 범위로 반영한다. 기존 미커밋 문서는 보존하고 필요한 변경만 통합한다. 데이터 migration은 없다. 검증 실패 시 웹 서비스와 관련 설정 변경을 되돌려 기존 API 단독 실행 경로로 복귀할 수 있다. 이미지 게시·태그·릴리스는 이번 변경에서 수행하지 않는다.

## Open Questions

추가 OS·CPU 지원과 공개 이미지 레지스트리·릴리스 트리거는 후속 범위다. 구현을 막는 기능 결정은 없다.
