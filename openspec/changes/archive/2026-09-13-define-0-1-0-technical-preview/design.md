## Context

`docs/development-workflow.md`는 0.x를 정식 출시 전 개발 릴리스로 정의하지만 구체적인 첫 개발 릴리스 범위와 게이트는 정의하지 않는다. `docs/plans/development-plan.md`는 Phase 0과 설치 가능한 Phase 1 MVP를 설명하고 첫 정식 릴리스를 1.0.0으로 둔다. 현재 `main`은 PostgreSQL·MySQL, Docker와 브라우저를 포함한 CI를 통과하지만 공개 릴리스 산출물과 폐쇄망 설치·업데이트·복구는 #71과 #88에 남아 있다.

이 변경은 구현된 기능을 늘리지 않고, 현재 기능과 후속 릴리스 작업 사이에 검증 가능한 0.1.0 경계를 만든다. 구체적인 요구사항은 `specs/technical-preview-release/spec.md`를 따른다.

## Goals / Non-Goals

**Goals:**

- 문서와 이슈에서 동일하게 사용할 0.1.0 대상·포함 범위·제외 범위를 정한다.
- #70, #71, #88, #89와 CI·산출물 검증을 명시적 출시 차단 게이트로 만든다.
- 0.1.0 개발 릴리스와 향후 1.0.0 정식 릴리스의 기대 수준을 분리한다.
- 후속 릴리스 구현 이슈가 독립 PR로 완료될 수 있도록 책임 경계를 유지한다.

**Non-Goals:**

- #70, #71, #88, #89의 기능이나 문서를 대신 구현하지 않는다.
- 버전 태그, GitHub Release 또는 Docker 산출물을 생성하지 않는다.
- 1.0.0 Phase 1 범위를 축소하거나 우선순위를 확정하지 않는다.
- 검증하지 않은 플랫폼이나 DB 조합을 지원 범위에 추가하지 않는다.

## Decisions

### 0.1.0은 폐쇄망 단일 서버 기술 프리뷰다

0.1.0을 소스 스냅샷만 제공하는 개발 빌드가 아니라, 폐쇄망 단일 서버에서 핵심 여정을 실제 평가할 수 있는 기술 프리뷰로 정의한다. 이 기준은 현재 프로젝트가 목표로 하는 설치 방식과 #88을 릴리스 전에 검증하려는 결정에 맞는다.

대안으로 개별 이미지 archive만 제공하는 가벼운 프리뷰를 고려했지만, 설치·업데이트·복구 가능성을 다음 버전으로 미루면 첫 공개 사용자가 프로젝트의 핵심 배포 가정을 검증할 수 없으므로 선택하지 않는다.

### 기능 목록보다 사용자 여정으로 포함 범위를 정한다

포함 범위는 오프라인 설치에서 수집·저장·조회와 업데이트·복구까지 이어지는 사용자 여정으로 작성한다. 개별 패키지나 내부 구현 목록은 빠르게 낡고, 부분 구현만으로 출시 게이트를 통과했다고 오해하기 쉽기 때문이다.

### 지원과 검증을 같은 의미로 사용한다

0.1.0의 지원 환경은 현재 CI가 실제 사용하는 Ubuntu 24.04 linux/amd64, PostgreSQL 17.6, MySQL 8.4.6과 Docker Compose로 제한한다. macOS 로컬 개발 등 동작 가능한 다른 조합은 검증 대상 지원 환경으로 표기하지 않는다.

대안으로 버전 범위를 넓게 선언할 수 있지만, 첫 기술 프리뷰에서는 검증 증거 없는 호환성 약속보다 정확한 기준 조합이 안전하다. 범위 확대는 별도 검증과 함께 후속 릴리스에서 수행한다.

### 릴리스 게이트는 이슈 상태와 산출물 증거를 모두 요구한다

#70, #71, #88, #89가 닫힌 것만으로 완료를 판단하지 않는다. 최종 태그 후보의 전체 CI와 공개할 바로 그 번들의 설치·업데이트·복구 결과, 릴리스 노트의 버전·digest·체크섬·제한 사항을 함께 확인한다. 이슈가 닫혔지만 최종 조합이 달라진 경우 발생하는 검증 공백을 막기 위한 결정이다.

### 문서의 책임을 분리한다

- `docs/development-workflow.md`: 0.1.0 출시 절차와 차단 게이트
- `docs/plans/development-plan.md`: 0.1.0과 Phase 0·Phase 1·1.0.0의 관계
- `README.md`: 현재 프로젝트 상태와 지원 범위로 가는 짧은 진입점
- GitHub issue #90: 결정 요약, 관련 작업과 검증 상태 추적

세부 설치 명령과 번들 구조는 #71·#88 문서가 소유한다. 같은 내용을 여러 문서에 복제하지 않고 링크로 연결한다.

## Risks / Trade-offs

- [0.1.0이라는 번호를 안정판으로 오해할 수 있음] → 모든 사용자 진입점과 릴리스 노트에 기술 프리뷰와 미지원 범위를 표시한다.
- [정확한 DB patch 버전 제한이 지나치게 좁을 수 있음] → 0.1.0은 검증한 버전만 약속하고 호환 범위 확대를 후속 검증으로 관리한다.
- [이슈를 닫은 뒤 최종 산출물이 달라질 수 있음] → 태그 후보 commit과 산출물 digest를 기준으로 마지막 end-to-end 검증을 다시 수행한다.
- [개발 플랜의 미래 기능을 현재 지원 기능으로 오해할 수 있음] → Phase 계획과 릴리스 지원 표를 분리하고 알려진 제한 사항을 릴리스 노트에 반복 확인한다.

## Migration Plan

1. 범위 문서를 main에 병합하고 #90에 결정 결과를 반영해 닫는다.
2. #70, #71, #88, #89를 독립 변경으로 순서대로 완료한다.
3. 릴리스 후보 commit에서 전체 CI와 최종 번들의 폐쇄망 설치·업데이트·복구를 검증한다.
4. 실패하면 태그를 만들지 않고 수정 commit에서 전체 게이트를 다시 수행한다.
5. 성공한 commit에 v0.1.0 태그를 한 번만 생성하고 기술 프리뷰 릴리스를 공개한다.
