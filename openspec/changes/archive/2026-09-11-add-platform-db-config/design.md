## Context

이번 작업은 **운영자가 입력한 DB 접속 정보를 읽고, 올바른 설정인지 검사하는 공통 기능**을 만드는 것이다. 정상 입력은 프로그램이 사용할 설정으로 반환하고, 잘못된 입력은 고쳐야 할 항목을 알려준다.

현재 서버에는 HTTP 주소·포트 설정과 서버 상태 확인 API만 있다. 이번에는 설정 검사 기능을 별도로 만들며, 서버가 이 기능을 호출해 실제 DB에 접속하는 작업은 PostgreSQL #27, MySQL #28에서 진행한다.

### 운영자가 입력할 설정 예시

아래는 로컬 PostgreSQL용 입력 형식을 설명하는 예시다. 비밀번호는 설명용 값이며, 현재 서버에서 이 설정을 적용해 연결할 수 있다는 의미는 아니다.

```dotenv
PLATFORM_DB_TYPE=postgres
PLATFORM_DB_HOST=localhost
PLATFORM_DB_PORT=5432
PLATFORM_DB_NAME=oss_scp
PLATFORM_DB_USER=oss_scp_app
PLATFORM_DB_PASSWORD=example-only-password
PLATFORM_DB_TLS_MODE=disable
```

주소·포트는 DB 위치, DB 이름은 사용할 데이터베이스, 계정·비밀번호는 접속 자격증명이다. `TLS_MODE=disable`은 이 로컬 예시에서 암호화를 사용하지 않는다는 뜻이다. 기본값 `verify-full`은 암호화와 서버 인증서 검증을 요구한다.

비밀번호 파일을 사용하려면 `PLATFORM_DB_PASSWORD` 항목을 제거하고 다음을 지정한다. 프로그램은 해당 경로의 파일 내용을 비밀번호로 읽는다.

```dotenv
PLATFORM_DB_PASSWORD_FILE=/run/secrets/platform_db_password
```

### 입력에 따른 결과

아래는 등록된 테스트용 DB 연결 코드를 전달해 설정 검사 함수를 호출했을 때의 동작이다. 이번에는 실제 PostgreSQL·MySQL 연결 코드를 포함하지 않는다.

| 입력 상황 | 설정 검사 결과 |
|---|---|
| 필수값과 형식이 올바름 | 다음 연결 단계에서 사용할 설정을 반환 |
| 포트를 생략함 | 등록된 DB의 기본 포트 적용 |
| `PLATFORM_DB_PORT=abc` | 포트에 정수가 필요하다는 설정 오류 반환 |
| DB 계정 누락 | `PLATFORM_DB_USER`가 필요하다는 설정 오류 반환 |
| 비밀번호 값과 파일을 모두 지정 | 두 방식 중 하나만 지정해야 한다는 오류 반환 |
| 비밀번호 파일을 읽을 수 없음 | 파일 설정 오류 반환, 비밀번호·파일 경로는 오류에 노출하지 않음 |
| 등록되지 않은 DB 종류 선택 | 해당 종류를 사용할 수 없다는 오류 반환 |

**설정 검사 통과는 DB 연결 성공을 뜻하지 않는다.** 예를 들어 비밀번호 문자열의 형식이 올바른지는 이번에 확인하지만, 실제 DB의 비밀번호와 일치하는지는 #27·#28에서 접속할 때 확인한다. 포트가 숫자 범위를 만족하는지와 그 포트에 DB가 실행 중인지는 별개다.

## Goals / Non-Goals

**Goals:** 접속 설정 읽기·필수값과 형식 검사·비밀번호 파일 읽기·오류 반환을 구현한다. 서버와 수집 CLI가 같은 결과를 사용하도록 공통 코드로 제공하고, 후속 DB별 연결 코드가 따라야 할 인터페이스를 정의한다.

**Non-Goals:** 실제 DB 접속, DB 설치, 테이블 생성·변경(migration), 데이터 저장·조회, 웹 설정 입력 화면. 이번에는 현재 서버 시작 과정에 설정 검사 호출을 추가하지 않는다.

완료 여부는 실제 DB 없이 테스트용 입력·임시 비밀번호 파일로 확인한다. 정상 입력의 반환값과 잘못된 입력의 오류가 명세대로 동작하면 설정 검사 기능의 검증이 된다. 기존 서버 상태 확인 테스트도 유지한다.

## Decisions

이하에서는 위 동작을 어떤 코드에 배치할지 설명한다. **파서**는 설정을 읽고 해석하는 함수, **어댑터**는 PostgreSQL·MySQL 각각의 연결 코드, **계약**은 그 코드들이 따라야 할 입력·출력 규칙을 뜻한다. **readiness**는 DB를 사용할 준비가 되었는지, **liveness**는 서버가 살아 있는지를 의미한다.

기존 `packages/plugin-config`의 CommonJS·TypeScript 선언 파일·Vitest 구성을 참고하고, workspace 전체를 검사하는 기존 CI 흐름을 사용한다.

1. `packages/platform-db`에 프레임워크 독립적인 설정 파서와 타입·등록 검증을 둔다. API config 내부 구현은 CLI 재사용을 어렵게 하고, 범용 플러그인 설정 패키지에 넣으면 원천 연결과 운영 DB가 섞이므로 별도 패키지를 선택한다. 기존 TypeScript/CommonJS와 Vitest 버전을 재사용하며 DB 드라이버를 추가하지 않는다.
2. 호출자가 환경변수와 어댑터 목록을 전달한다. 패키지가 `.env`를 암묵적으로 로드하지 않는다. 현재 API bootstrap은 그대로 두고 후속 #27에서 파서를 호출한다. 파서는 항상 완전한 설정을 요구하며 무설정 성공/가짜 DB 모드를 만들지 않는다. #26의 설정 예시는 주석으로 제공하고 아직 API에서 적용하지 않는다는 설명을 붙인다.
3. `readPlatformDbConfig(env, adapters)`는 검증된 타입을 반환한다. `PlatformDbAdapterFactory`는 id, contractVersion: 1, defaultPort와 `connect(config)`를 제공하고 반환 연결은 `checkReady(): Promise<boolean>`, `close(): Promise<void>`를 제공한다. 등록 유효성은 파일 읽기 전에 검증한다. DB별 기본 포트는 factory 등록 값이며 postgres 5432/mysql 3306은 후속 구현 및 테스트 fixture 값이다. 실제 연결 타임아웃·풀 정리·안전한 연결 오류 변환은 #27·#28 책임이다. 수명주기 계약은 readiness가 제한 시간 내 반환되고 close가 반복 호출 가능함을 문서화한다.
4. 비밀번호 파일의 마지막 개행 한 개만 제거한다. `trim()`은 실제 비밀번호를 바꿀 수 있어 사용하지 않는다. 직접 값과 파일 두 방식이 겹치면 우선순위를 두지 않고 거부한다. 파일 읽기는 제한 바이트까지만 수행하며 일반 파일 여부를 확인한다. secret 마운트 호환성을 위해 파일 심볼릭 링크를 허용한다. 비밀번호를 반환한 설정 객체 전체를 로그에 출력하지 않으며 사용자 오류에는 원본 cause를 첨부하지 않는다.
5. TLS 기본값은 verify-full이다. 로컬 DB에서는 disable을 명시한다. 암호화만 하고 인증서는 무시하는 모드는 두지 않는다. CA 파일의 PEM 형식은 Node 기본 암호화 기능으로 검사하고 실제 체인/호스트 검증은 드라이버가 맡는다. 비밀번호와 CA 경로는 절대 경로로 통일해 CLI 작업 디렉터리 차이를 제거한다. 환경별 경로는 사용자가 주입한다.
6. 테스트는 가짜 어댑터와 임시 파일로 기본값·오류·비밀정보 미노출·등록 계약을 검증한다. 실제 DB 연결 테스트는 후속 이슈로 남긴다. 기존 CI의 재귀 테스트에 포함하고 기존 health 회귀 테스트를 유지한다.

## Risks / Trade-offs

- TLS 기본값 때문에 로컬 평문 DB에는 추가 설정 필요 → 로컬 예제에 disable 명시, 운영 예제는 verify-full.
- 계약만 추가되어 실제 접속으로 오인할 가능성 → 문서에 #27·#28 선행 필요와 설정 검증/연결 성공 구분 명시.
- 환경변수 오타와 잘못된 값 → 알려진 설정 이름과 고정 오류를 제공하고 경계값 테스트. 추가 확장 변수는 향후 계약에서 정의한다.
- 현재 다른 작업 브랜치와 미커밋 문서 존재 → 구현 시 최신 main의 별도 worktree로 이 change만 옮기고 참조용 로컬 플랜을 보존한다.

## Migration Plan

스키마 migration이나 데이터 이관은 없다. 구현은 새 패키지·잠금 파일·주석 예시·문서만 추가하며 현재 서버의 배포 환경을 바꾸지 않는다. 기본 Node.js 24 LTS 및 pnpm 버전은 저장소 설정을 따른다. 검증은 기존 Actions Ubuntu 24.04/linux-amd64와 실제 로컬 실행 환경을 구분해 보고하고 미실행 환경의 호환성을 주장하지 않는다.

구현 후 `pnpm install --frozen-lockfile`, 패키지 테스트, `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build` 및 OpenSpec strict 검증을 실행한다. 변경 제거로 코드 롤백이 가능하며 DB 복구 작업은 없다.
