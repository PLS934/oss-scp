## Context

`packages/http-collector/test/single-memory-worker.mjs`는 collector와 loopback HTTP 서버를 한 프로세스에서 실행한다. 서버는 2,000개의 4 KiB 문자열 객체와 약 8 MiB JSON 문자열을 생성하고, 요청 직후 한 번의 강제 GC 전후 전체 프로세스 heap 차이를 제품 보관량으로 간주한다. Node.js 24.19.0에서 관찰된 약 8.34 MiB는 생성한 원시 payload 약 7.81 MiB와 가깝고, 이 측정에는 서버 객체, HTTP 연결·응답 버퍼 및 V8의 비동기 회수 시점이 섞여 있다.

현재 `collectHttpSingle`은 응답을 읽고 JSON을 해석한 뒤 callback에 `items`와 허용된 metadata만 전달하고 `{ requests, records }`를 반환한다. 구현에서 장기 보관 컬렉션은 관찰되지 않지만, 구현 단계에서 참조 회수 경계를 확인해 제품 누수 여부를 최종 판정한다.

## Goals / Non-Goals

**Goals:**

- server fixture의 응답 생성 heap과 collector 프로세스 heap을 분리한다.
- transient HTTP/V8 할당이 정리될 기회를 준 뒤 작은 응답과 큰 응답의 완료 후 보관량을 독립 실행으로 비교한다.
- 반환 summary와 완료 후 보관량이 원천 응답 크기에 비례하지 않는다는 계약을 회귀 검사한다.
- Node.js 24.19.0에서 반복 가능한 진단값을 출력해 실패 원인을 확인할 수 있게 한다.

**Non-Goals:**

- peak memory나 응답 파싱 중의 일시적 메모리 사용량을 제한하지 않는다.
- streaming JSON parser를 도입하거나 HTTP 수집 API를 변경하지 않는다.
- 고정 상한을 관찰값에 맞춰 올리거나 메모리 검사를 제거하지 않는다.

## Decisions

### 응답 생성 서버를 별도 프로세스로 격리한다

메모리를 측정하는 collector worker와 loopback fixture server를 서로 다른 프로세스로 실행한다. collector 측정값에는 서버가 생성한 payload 객체와 직렬화 문자열이 포함되지 않으며, fixture는 기존처럼 외부 자격증명 없이 loopback에서만 동작한다.

대안으로 같은 프로세스에서 서버 변수만 비우는 방법은 Node HTTP 내부 참조와 이벤트 루프 수명을 측정 경계에서 제거했음을 보장하지 못하므로 채택하지 않는다.

### 절대값 하나 대신 입력 크기 증가에 대한 보관량을 비교한다

작은 입력과 큰 입력을 각각 새 collector 프로세스에서 측정하고, warm-up 뒤 여러 GC 및 이벤트 루프 turn을 거쳐 안정화한 heap을 비교한다. 회귀 검사는 큰 입력의 완료 후 heap이 약 8 MiB 원천 응답 전체에 비례해 남는지를 판별하며, 측정 결과와 입력 payload 크기를 함께 출력한다.

대안인 기존 4 MiB 절대 임계값 유지 또는 8.34 MiB 이상으로 상향은 머신·런타임 노이즈에 민감하거나 실제 전체 응답 보관을 허용하므로 채택하지 않는다.

### 제품 코드 수정은 참조 보관이 입증된 경우에만 수행한다

격리된 측정에서도 큰 입력에 비례한 보관이 재현되면 heap snapshot 또는 최소 참조 실험으로 `collectHttpSingle`의 참조 경로를 확인하고 그 경로만 제거한다. 격리 후 비례 보관이 사라지면 테스트 하네스만 수정하고 제품 코드는 유지한다.

추측성 리팩터링은 회귀 원인을 흐리고 이슈 범위를 넓히므로 채택하지 않는다.

## Risks / Trade-offs

- [강제 GC 후에도 런타임 캐시와 allocator 변동이 남을 수 있음] → 독립 프로세스, warm-up, 복수 GC/event-loop turn, 입력 크기 대비 비례 비교를 함께 사용하고 반복 실행으로 안정성을 검증한다.
- [하위 프로세스 종료나 출력 오류가 메모리 실패로 오인될 수 있음] → 각 프로세스의 종료 상태와 구조화된 출력부터 검증하고 stderr를 실패 진단에 포함한다.
- [비례 기반 허용 폭이 너무 넓으면 실제 보관을 놓칠 수 있음] → 약 8 MiB 전체 응답 보관과 런타임 고정 노이즈를 명확히 구분하는 입력 크기와 허용 폭을 사용하고, 수정 전 하네스 결함이 재현됨을 먼저 기록한다.

## Migration Plan

런타임 API나 데이터 변경은 없다. 테스트와 필요 시 최소 제품 수정만 함께 배포하며, 회귀가 발생하면 해당 커밋을 되돌려 기존 동작으로 복귀할 수 있다.
