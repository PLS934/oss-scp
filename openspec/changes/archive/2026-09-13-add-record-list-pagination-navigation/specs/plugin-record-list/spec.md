## ADDED Requirements

### Requirement: 페이징 컨트롤의 상태와 접근성을 일관되게 제공한다
클라이언트는 현재 묶음 위치와 20·50·100·200건의 묶음 크기 선택을 표시하고, 이전·다음 동작을 키보드와 스크린 리더로 식별하고 실행할 수 있게 해야 한다(SHALL). 첫 묶음에서는 이전을, 마지막 묶음에서는 다음을 비활성화해야 하며(MUST), 조회 중에는 중복 이동을 허용하지 않아야 한다(MUST).

#### Scenario: 첫 묶음 탐색 상태
- **WHEN** 첫 묶음 조회가 완료되고 다음 묶음이 있다
- **THEN** 화면은 현재 위치를 첫 번째 묶음으로 표시하고 이전 동작을 비활성화하며 다음 동작을 활성화한다

#### Scenario: 마지막 묶음 탐색 상태
- **WHEN** 현재 응답의 `hasNextPage`가 false이고 `nextCursor`가 null이다
- **THEN** 화면은 다음 동작을 비활성화하고 현재 위치와 이전 이동 가능 여부를 유지한다

#### Scenario: 로딩과 빈 결과 및 조회 실패 상태
- **WHEN** 목록이 로딩 중이거나 빈 결과를 반환하거나 조회에 실패한다
- **THEN** 화면은 현재 성공한 목록 위치와 모순되지 않는 탐색 상태를 표시하고 실행할 수 없는 이동 동작을 비활성화한다

#### Scenario: 보조 기술을 이용한 조작
- **WHEN** 사용자가 키보드 또는 스크린 리더로 페이징 영역을 탐색한다
- **THEN** 이전·다음 버튼, 현재 묶음 위치, 묶음 크기 선택의 이름과 상태를 식별하고 가능한 동작을 실행할 수 있다

## MODIFIED Requirements

### Requirement: cursor로 다음 묶음을 조회한다
클라이언트는 cursor 없는 첫 묶음에서 시작하고 `hasNextPage`와 `nextCursor`가 유효할 때 방문한 cursor를 이력에 추가해 다음 묶음을 조회해야 한다(SHALL). 방문 이력의 직전 cursor를 사용해 이전 묶음으로 돌아갈 수 있어야 하며(SHALL), 이동한 묶음은 현재 items를 누적하지 않고 새 묶음으로 교체해야 한다(MUST).

#### Scenario: 다음 묶음 이동
- **WHEN** 현재 응답의 `hasNextPage`가 true이고 사용자가 다음 묶음을 선택한다
- **THEN** 클라이언트는 같은 조회 범위와 limit에 `nextCursor`를 전달하고 반환된 다음 items로 표를 교체하며 현재 위치를 한 묶음 증가시킨다

#### Scenario: 이전 묶음 이동
- **WHEN** 사용자가 다음 묶음으로 이동한 뒤 이전 묶음을 선택한다
- **THEN** 클라이언트는 방문 이력의 직전 cursor로 조회하고 중복되거나 누락된 항목 없이 직전 묶음과 위치를 표시한다

#### Scenario: 마지막 묶음
- **WHEN** 현재 응답의 `hasNextPage`가 false이고 `nextCursor`가 null이다
- **THEN** 화면은 다음 묶음 이동을 비활성화한다

#### Scenario: 다음 묶음 로딩 중 중복 방지
- **WHEN** 이전 또는 다음 묶음 요청이 진행 중이다
- **THEN** 화면은 추가 이동 요청을 허용하지 않고 진행 중인 조회 상태를 표시한다

### Requirement: 조회 조건 변경과 요청 생명주기를 안전하게 처리한다
클라이언트는 route context 또는 묶음 크기가 바뀌면 방문한 cursor 이력과 현재 위치를 폐기하고 새 조건의 첫 묶음을 조회해야 한다(SHALL). 진행 중인 이전 요청은 AbortSignal로 취소하고 그 결과가 새 화면 상태를 덮지 못하게 해야 한다(MUST). 묶음 이동 조회가 실패하면 마지막으로 성공한 목록과 탐색 위치를 유지해야 한다(MUST).

#### Scenario: 묶음 크기 변경
- **WHEN** 사용자가 20·50·100·200 중 다른 묶음 크기를 선택한다
- **THEN** 클라이언트는 cursor 이력과 현재 위치를 초기화하고 cursor 없이 현재 조회 범위의 첫 묶음을 새 limit으로 요청한다

#### Scenario: route context 변경
- **WHEN** 사용자가 다른 플러그인 메뉴로 이동한다
- **THEN** 클라이언트는 이전 cursor 이력, 위치와 행을 폐기하고 새 pluginId, sourceId, dataType으로 첫 묶음을 요청한다

#### Scenario: 이전 요청의 늦은 완료
- **WHEN** 조건 변경 또는 새 이동 전에 시작된 요청이 취소 후 늦게 완료되거나 실패한다
- **THEN** 그 결과는 현재 조건의 목록·위치·오류를 변경하지 않는다

#### Scenario: 묶음 이동 조회 실패
- **WHEN** 이전 또는 다음 묶음 조회가 실패한다
- **THEN** 화면은 안전한 오류와 재시도 동작을 표시하면서 마지막으로 성공한 목록, cursor 이력과 현재 위치를 유지한다
