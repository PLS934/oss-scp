## Context

`apps/web/src/record-list.tsx`는 현재 단일 cursor 상태로 다음 묶음만 조회하고, 요청 시작 시 결과를 비운다. 조회 API는 역방향 cursor나 전체 건수를 제공하지 않으므로 이전 이동은 클라이언트가 이미 방문한 시작 cursor를 기억해야 하며, 위치는 절대 페이지 번호가 아니라 방문 순서로 표현해야 한다. 요구 동작은 `specs/plugin-record-list/spec.md`에 정의한다.

## Goals / Non-Goals

**Goals:**

- 성공적으로 방문한 묶음의 cursor와 현재 위치를 하나의 일관된 탐색 상태로 관리한다.
- 이동 요청 실패와 요청 경합 중에도 마지막 성공 화면을 보존한다.
- 기존 API 계약과 React 목록 구조를 유지하면서 단위·브라우저 검증이 가능한 경계를 만든다.

**Non-Goals:**

- 전체 건수나 임의 페이지 번호 계산을 추가하지 않는다.
- 묶음 크기를 계정 또는 브라우저 저장소에 영속화하지 않는다.
- 서버 조회 API나 cursor 형식을 변경하지 않는다.

## Decisions

### 성공한 cursor 경로를 배열과 현재 인덱스로 관리한다

첫 묶음의 cursor를 `undefined`로 둔 경로와 0 기반 인덱스를 함께 관리한다. 다음 성공 시 응답의 `nextCursor`를 경로 뒤에 추가하고, 이전 이동은 인덱스를 하나 줄인 cursor를 사용한다. 사용자가 이미 방문한 경로 안에서 앞뒤로 이동할 수 있지만 임의 위치로 건너뛰지는 않는다.

서버에 역방향 cursor를 추가하는 대안은 API·저장 계층 변경 범위가 커지고, 현재 요구는 이미 방문한 묶음으로 돌아가는 것만 필요해 채택하지 않는다. 화면별 응답 전체를 캐시하는 대안도 데이터 갱신과 메모리 사용 의미를 추가하므로 cursor만 보관하고 매 이동마다 다시 조회한다.

### 이동 의도와 마지막 성공 상태를 분리한다

요청 대상 cursor와 위치는 이동 의도로 관리하되 결과가 성공할 때만 화면의 현재 위치와 cursor 경로를 확정한다. 이동 중에는 마지막 성공 결과를 유지하고 탐색 버튼과 묶음 크기 선택을 비활성화한다. 실패하면 의도를 폐기하고 마지막 성공 상태에서 재시도할 수 있게 한다.

요청 시작 즉시 결과와 위치를 교체하는 단순 구현은 실패 시 빈 화면 또는 실제 표시 데이터와 위치가 어긋날 수 있어 채택하지 않는다.

### route context와 묶음 크기를 탐색 세션의 경계로 사용한다

`pluginId`, `sourceId`, `dataType` 또는 묶음 크기가 바뀌면 탐색 경로와 성공 결과를 즉시 초기화하고 첫 cursor로 조회한다. 각 effect 실행은 `AbortController`와 증가하는 요청 식별자를 함께 사용해 이전 fetch를 취소하고 취소를 무시한 늦은 응답도 차단한다.

### 네이티브 폼 요소와 명시적 상태 문구를 사용한다

이전·다음은 항상 렌더링되는 `<button>`에 `disabled` 상태를 적용하고, 묶음 크기는 연결된 `<label>`과 `<select>`를 유지한다. 현재 묶음은 텍스트로 제공하고 페이징 영역에 접근 가능한 이름을 부여한다. 별도 ARIA 위젯을 만드는 대안보다 키보드·스크린 리더 기본 동작이 예측 가능하다.

### 상태 전이와 실제 사용자 흐름을 나눠 검증한다

뷰 단위 테스트는 버튼 상태, 위치 문구, 빈 결과·오류·로딩 표현을 검증한다. 컴포넌트 테스트는 cursor 경로와 성공/실패/경합 전이를 검증하고, Playwright 흐름은 다음→이전, 마지막 묶음, 크기 및 route 변경과 느린 응답 무시를 실제 요청 파라미터와 함께 확인한다.

## Risks / Trade-offs

- [이전 묶음 재조회 사이에 저장 데이터가 바뀌면 처음 보았던 행과 달라질 수 있음] → cursor 계약의 현재 의미를 유지하고 응답 캐시를 도입하지 않으며, 테스트는 고정 fixture로 중복·누락을 검증한다.
- [cursor 이력이 브라우저 히스토리나 새로고침에 보존되지 않음] → 이번 범위의 화면 세션 상태로 명시하고 route 또는 새 마운트에서는 첫 묶음부터 시작한다.
- [빠른 연속 클릭이 여러 이동 의도를 만들 수 있음] → 요청이 시작되는 즉시 모든 이동 컨트롤을 비활성화하고 요청 ID로 늦은 응답을 무시한다.

## Migration Plan

클라이언트만 점진적으로 배포하며 데이터 또는 API 마이그레이션은 없다. 문제가 발생하면 해당 UI 커밋을 되돌려 기존 순방향 cursor 동작으로 복구할 수 있다.
