## Purpose

API가 시작될 때 확정된 설정 revision의 모든 활성 수집 대상을 기존 조회를 방해하지 않고 전체 동기화하도록 하는 외부 동작을 정의한다.

## ADDED Requirements

### Requirement: 기동 시 활성 대상 전체 수집
API는 최초 실행과 모든 재시작에서 확정된 runtime registry에 등록되고 활성화된 각 수집 대상을 full 범위로 한 번씩 요청해야 한다(SHALL). 누락된 과거 일정을 보충하는 조건으로 기동 실행을 제한해서는 안 된다(MUST NOT).

#### Scenario: 최초 실행
- **WHEN** 플랫폼 DB에는 해당 대상의 수집 이력이 없고 API가 유효한 registry로 시작한다
- **THEN** 각 등록·활성 대상의 full 범위 수집이 한 번 요청된다

#### Scenario: 수집 이력이 있는 재시작
- **WHEN** 이전 수집 성공 또는 실패 이력이 있는 API 인스턴스가 재시작한다
- **THEN** 마지막 실행 시각이나 일정 누락 여부와 무관하게 각 등록·활성 대상의 full 범위 수집이 요청된다

#### Scenario: 빈 registry
- **WHEN** API가 등록·활성 수집 대상이 없는 유효한 registry로 시작한다
- **THEN** API는 정상적으로 요청을 처리하고 새로운 수집 실행이나 대상 작업을 만들지 않는다

### Requirement: 비차단 요청 처리와 상태 가시성
API는 registry 검증과 기동 수집 요청 등록에 필요한 유한한 초기화만 완료한 뒤 HTTP 요청을 받아야 하며, 장시간 수집 완료를 기다려서는 안 된다(MUST NOT). 최초 수집 전, 실행 중 및 종료 상태를 플랫폼 DB에서 조회할 수 있어야 한다(SHALL).

#### Scenario: 기동 수집 진행 중 기존 데이터 조회
- **WHEN** 하나 이상의 기동 full 수집이 진행 중이고 플랫폼 DB에 이전 저장 데이터가 있다
- **THEN** 목록·상세 조회는 원천을 호출하거나 수집 완료를 기다리지 않고 이전 저장 데이터를 반환한다

#### Scenario: 최초 수집 전과 진행 중 상태
- **WHEN** 대상이 아직 성공한 적이 없거나 첫 기동 수집이 진행 중이다
- **THEN** 상태 조회는 각각 미수집 또는 수집 중 상태와 알려진 실행 식별자·시작 시각을 반환한다

#### Scenario: 백그라운드 수집 실패
- **WHEN** HTTP 수신 시작 뒤 기동 수집 대상 하나가 실패한다
- **THEN** API는 계속 기존 저장 데이터와 다른 HTTP 요청을 제공하고 해당 대상의 실패 상태를 기록한다

### Requirement: 대상별 실패 격리와 공통 수집 계약
기동 수집은 수동 CLI와 동일한 수집·가공·검증·묶음 저장·checkpoint 코어를 사용해야 한다(SHALL). 한 대상의 실패는 다른 등록 대상의 시작 또는 완료를 막아서는 안 되며(MUST NOT), 대상별 결과를 합산한 기동 실행은 모두 성공이면 success, 성공과 실패 또는 격리 오류가 섞이면 partial, 성공한 대상이 없으면 failed로 종료해야 한다(SHALL).

#### Scenario: 일부 대상 실패
- **WHEN** 두 활성 대상 중 하나의 원천 요청 또는 가공이 실패하고 다른 하나는 정상 완료한다
- **THEN** 정상 대상은 저장과 checkpoint를 완료하고 실패 대상은 기존 데이터·checkpoint를 보존하며 상위 실행은 partial로 기록된다

#### Scenario: 모든 대상 성공
- **WHEN** 모든 활성 대상의 full 범위 수집과 저장이 정상 완료된다
- **THEN** 각 대상과 상위 기동 실행은 success로 기록되고 전체 범위 완료 여부가 참으로 기록된다

#### Scenario: 호출자 종료
- **WHEN** API가 종료 신호를 받는 동안 기동 수집이 진행 중이다
- **THEN** 공통 수집 코어에 취소 신호를 전달하고 완료되지 않은 대상은 성공으로 기록하지 않는다
