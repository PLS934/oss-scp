# oss-scp 통합 개발 플랜

oss-scp는 외부 자산·취약점 데이터를 수집·가공해 플랫폼 DB에 저장하고 통합 조회·관리하는 오픈소스 플랫폼이다. 플러그인으로 데이터 수집·가공·데이터 정의와 메뉴·목록·상세를 확장한다. JSON 정의와 Connector SDK를 플러그인의 구성 요소로 사용한다. 이 플랜은 서비스 운영 DB와 수집 대상인 원본 DB를 서로 다른 역할로 명확히 분리한다. 자산 정의와 원본 Connection의 비밀 제외 설정은 서비스 운영자가 Git에서 관리하는 파일을 원본으로 삼는다.

## 문서 범위

현재 합의한 제품 요구사항과 구현 순서를 관리한다. 파일명·JSON·SDK는 명세 작성용 초안이며 구현 완료를 뜻하지 않는다. 세부 계약은 단계별 OpenSpec change에서 확정한다.

현재 구현된 범위는 React·NestJS와 로컬·Docker 실행 환경, HTTP JSON offset·single 및 로컬·HTTP CSV 수집, 공통 가공·저장·수동 수집 CLI, PostgreSQL·MySQL 연결과 저장·조회, 외부 플러그인 설정 검증, registry 기반 메뉴·기본 목록·상세와 cursor 기반 첫·이전·다음 묶음 이동이다. 기동·재시작 시 전체 수집, 배포 설정 기반 IANA 시간대 일일 전체 수집, 대상별 실행 조정·상태 조회 API, HTTP CSV의 공통 CLI 연결과 GitHub Release 번들 자산 자동화도 구현되어 있다. 인증·권한, 담당자 관리, 검색·필터·정렬·개인별 목록 설정과 운영 상태 화면 등은 남아 있다. 구현된 계약은 [OpenSpec 본 명세](../../openspec/specs/)를 기준으로 하고, 아래 단계별 계획과 구분한다. 실행 방법은 [클라이언트 가이드](../client-development.md), [서버 가이드](../server-development.md), 브랜치·배포 절차는 [개발 워크플로](../development-workflow.md)를 따른다.

### 계정관리 옵션

계정관리 활성화·비활성화 옵션을 제공하며 설치 시 기본값은 비활성화다. 운영자가 배포 설정에서 활성화하고 LDAP·AD 연결 정보를 제공하면 로그인과 역할별 권한 검사를 적용한다.

| 설정 | 동작 |
|---|---|
| 계정관리 활성화 | 사용자 인증, Employee·Security·Audit·Admin 역할과 담당 자산 범위를 적용한다. MVP의 인증 연동 수단으로 LDAP·Active Directory를 지원한다. |
| 계정관리 비활성화 | 로그인 없이 모든 데이터와 플랫폼 기능에 접근한다. 사용자별 역할·담당 자산 제한을 적용하지 않으며 LDAP 서버·계정·설정 없이 실행한다. |

운영자가 배포 설정으로 명시적으로 선택하며 소스 삭제나 별도 포크가 필요하지 않다. Git 기반 플러그인·구조 변경 절차는 두 설정에서 동일하다. 인증 장애가 발생해도 계정관리를 자동 비활성화하지 않는다.

계정관리 옵션과 인증 연동 수단은 구분한다. 현재 계정관리 활성화 시 로그인은 LDAP·AD 연동만 지원한다. 플랫폼 자체 계정 생성·비밀번호 로그인은 현재 범위에서 제외하되, 추후 추가할 수 있도록 인증 제공자 인터페이스를 분리한다. 인증 제공자는 사용자 신원을 확인하고, 플랫폼은 공통 사용자 식별·세션·역할·담당 자산 권한을 처리한다. LDAP 고유 속성이나 비밀번호 검증을 업무 코드에 결합하지 않는다. 옵션 이름, 로그인·세션·역할 매핑, 설정 전환 시 세션 처리와 비활성화 상태의 담당자 표현·감사 주체는 상세 설계에서 정한다.

## 1. 목표

서비스 운영자가 플랫폼 본체를 수정하거나 공식 플랫폼 이미지를 다시 빌드하지 않고 외부 운영자 디렉터리의 플러그인 파일과 등록 목록을 검증·교체한 뒤 서버를 재기동하는 것을 기본 운영 경험으로 삼는다. 플러그인은 데이터 수집·가공·데이터 정의와 선언형 메뉴·목록·상세 구성을 제공한다. 일반 사용자는 배포된 화면에서 개인별 표시 필드·순서·너비를 선택하고 저장할 수 있지만, 웹 UI에서 데이터 구조나 Connection을 수정하지 않는다.
서비스 운영 DB는 공통 저장소 계약과 DB별 어댑터로 확장할 수 있도록 설계한다. 초기 지원 대상은 PostgreSQL·MySQL이며, 배포 시 등록된 어댑터 중 하나를 선택한다. 새로운 DB는 본체의 업무 코드 수정 없이 어댑터·migration·등록 설정을 추가하고 빌드·배포해 연결한다.

```text
운영자가 플러그인 파일 추가·수정 및 등록 목록 갱신
→ PR과 CI가 Schema·Connection 계약 검증
→ 검토·승인 후 플랫폼 이미지와 플러그인 revision 호환성 검증
→ 외부 설정 디렉터리를 읽기 전용으로 주입하고 서버 재기동
→ 서버가 기동 전에 registry와 사전 빌드 JavaScript 모듈 검증·로드
→ 수집 실행: 원천 읽기 → 플러그인별 가공 → 플랫폼 공통 검증 → 플랫폼 DB 저장
→ 조회 API가 플랫폼 DB에서 목록·상세·집계 제공
→ JSON 기반 메뉴와 화면에서 결과 확인
```

플랫폼의 핵심 가치는 다음과 같다.

- 서로 다른 자산 데이터 원본을 동일한 방식으로 연결한다.
- 자산 종류별 메뉴와 화면을 코드 수정 없이 생성한다.
- 표의 컬럼, 표시명, 타입, 정렬, 필터를 JSON으로 설정한다.
- 수집·가공은 공개 SDK 계약으로 확장하고, 기본 목록·상세는 선언으로 생성하며 복잡한 화면은 플러그인 내부 React 코드로 교체할 수 있게 한다.
- 코어를 작게 유지해 오픈소스 기여 진입장벽을 낮춘다.

## 2. 핵심 설계 원칙

### 플러그인과 플랫폼의 역할

- `plugin.json`: 저장할 데이터 필드와 메뉴·목록·상세 화면을 설정한다.
- `source.json`: 호출할 API와 요청 파라미터·반복 호출 방식을 설정한다. 환경별 접속 주소와 인증 정보 참조는 Connection에서 관리한다.
- 가공 코드: 가져온 데이터를 저장할 필드·레코드·관계에 맞게 변환한다.
- 선택적 수집·화면 코드: 기본 설정으로 처리하기 어려운 API 호출이나 전용 화면을 구현한다.
- 플랫폼: 설정에 따라 데이터를 가져오고 가공 코드를 실행한 뒤, 결과를 검증해 DB에 저장한다. 저장된 데이터의 조회·권한 검사와 기본 메뉴·목록·상세 화면을 공통으로 제공한다.

### 운영자와 조회자의 경계를 고정한다

- 외부 `plugins/`, 등록 목록, `connections/`, LDAP 그룹-역할 매핑 파일은 운영자가 별도로 관리하는 Git revision이 유일한 원본이다. 플랫폼 이미지 버전과 이 revision을 독립적으로 고정한다.
- 운영자는 PR, CI 검증, 배포를 통해서만 자산 구조와 원본 접근 정책을 바꾼다. 운영 서버에 파일을 수동으로 넣거나 웹 관리 화면에서 설정을 쓰지 않는다.
- 일반 사용자는 이미 배포된 메뉴와 데이터를 조회·검색·필터링하며 플러그인 설정과 Connection을 생성·수정하지 않는다. 계정관리 활성화 시 설정된 역할별 접근 범위를 적용한다.
- 개발 환경에서만 file watcher로 빠르게 확인한다. 운영 환경의 설정 변경은 검증된 외부 revision 교체와 서버 재기동으로 처리하며 실행 중 동적 반영하지 않는다.

조회자가 선택한 표시 필드·순서·너비 및 검색·필터·정렬은 개인 설정이며 플러그인의 기본 정의나 다른 사용자의 화면을 변경하지 않는다. 계정관리 활성화 시 목록 설정을 플랫폼 DB에 계정별로 저장해 다른 브라우저에서도 같은 계정으로 복원한다. 비활성화 시 현재 브라우저의 localStorage에 저장해 같은 브라우저에서 복원한다. 저장 대상은 표시 필드·순서·너비와 검색·필터·정렬·페이지 크기이며 플러그인·목록별로 구분한다. 설정이 없으면 플러그인 기본값을 사용하고 기본값으로 초기화할 수 있게 한다. 계정 전환 시 다른 계정의 설정을 적용하지 않는다. 필드 삭제·타입 변경 시 유효하지 않은 개인 설정을 처리하는 세부 규칙은 상세 설계에서 정한다. 검색·필터·정렬은 조회 API로 전달해 플랫폼 DB에서 적용한다. 컬럼 숨김은 권한 제어가 아니며 조회 권한이 없는 필드는 응답 자체에서 제외한다.

### 플러그인 확장 계약

- 사용자 변경 범위는 플러그인 폴더, 등록 목록과 비밀정보를 제외한 배포 설정이다. 신규 API·데이터 종류·메뉴·목록·상세를 추가할 때 플랫폼 본체의 수집 엔진·저장소·조회 API·라우터·renderer를 수정하지 않아야 한다.
- 모듈 정보는 고유 ID·버전·메뉴·경로를, 데이터 정의는 필드·타입·표시명·고유 키·관계·검색 가능 여부를 제공한다. 외부 서버 플러그인은 기본 수집 설정, 사전 빌드된 JavaScript 가공·custom 수집 코드와 선언형 화면 정의를 패키징한다. 사용자 정의 React 화면은 플랫폼과 함께 빌드한다.
- 플러그인은 Connection과 공개 수집 SDK를 사용하며 내부 실행 정의는 플랫폼이 생성한다. 정확한 파일명·배치·등록 형식은 후속 OpenSpec에서 정한다.
- 플랫폼은 등록·호환성 검증, 수집 실행·실패 처리, 가공 결과 검증·저장·조회, 메뉴·기본 화면 생성과 권한 검사를 담당한다. 플러그인의 가공 결과는 공통 저장 경로로 전달한다.
- MVP의 기본 목록·상세는 객체·배열을 포함한 필드 정의로 생성한다. 화면 교체 경계와 공통 조회·권한 계약은 처음부터 설계하고, 복잡한 사용자 정의 화면의 등록·배포는 후속으로 구현한다.
- 플랫폼은 지정된 외부 설정 루트만 읽고 경로 이탈·누락 파일·중복 ID·경로·잘못된 참조·선언과 코드 불일치·호환되지 않는 API/schema 버전을 서버 기동 전에 거부한다. 운영 시 TypeScript transpile, 플러그인별 임의 패키지 설치, 원격 코드 다운로드와 웹 UI 동적 설치·수정은 지원하지 않는다.

### 플러그인 파일 구성과 등록 초안

폴더 하나를 플러그인 하나로 관리한다. 일반적인 연동은 설정 파일 두 개와 가공 코드 한 개로 구성하고, 특수한 수집이나 화면이 필요할 때만 파일을 추가한다. 아래 파일명·JSON 키·경로는 설계 초안이며 실제 지원 형식과 SDK 계약은 후속 OpenSpec에서 확정한다. 가공·custom 수집 코드는 JavaScript 또는 TypeScript로 작성하며 기본 예제는 TypeScript로 제공한다.

```text
plugins/
└── vulnerability-feed/
    ├── plugin.json       # 모듈·데이터·유일키·담당자·메뉴·기본 화면
    ├── source.json       # API 요청과 반복 호출 설정
    ├── transform.js      # 사전 빌드: 원천 데이터를 저장 계약에 맞게 가공
    └── fetch.js          # 선택·사전 빌드: custom 수집
```

`plugin.json` 예시:

```json
{
  "apiVersion": "oss-scp/plugin-v1",
  "id": "vulnerability-feed",
  "name": "취약점 연동",
  "version": "1.0.0",
  "source": "./source.json",
  "transform": "./transform.js",
  "data": {
    "uniqueKey": "id",
    "defaultAssigneeField": "ownerId",
    "fields": {
      "id": { "type": "string", "label": "ID" },
      "title": { "type": "string", "label": "취약점명" },
      "severity": { "type": "string", "label": "위험도" },
      "ownerId": { "type": "string", "label": "담당자" }
    }
  },
  "menu": {
    "title": "취약점",
    "icon": "shield",
    "group": "보안 관리",
    "order": 10,
    "path": "/vulnerabilities"
  },
  "views": {
    "list": { "columns": ["title", "severity", "ownerId"] },
    "detail": {
      "sections": [
        { "title": "기본 정보", "fields": ["id", "title", "severity"] },
        { "title": "담당자 정보", "fields": ["ownerId"] }
      ]
    }
  }
}
```

유일키·기본 담당자·화면 필드는 모두 가공 결과를 참조한다. 기본 담당자 필드는 원천의 사람 값을 가공한 결과이며 별도 매핑 설정으로 계정 속성과 연결한다. 수동 지정 우선 규칙을 따른다. 목록 columns는 개인 컬럼 선택 전 기본값이다. 위 예시는 한 데이터 종류의 최소 설명이며 자산 관계, 세부 권한과 사용자 정의 화면 참조 규약은 별도 명세로 정의한다. `plugin.json`이 데이터·화면 정의의 원본이며 내부 Definition은 플랫폼이 생성한다. `source.json`은 요청·수집 동작을, Connection은 환경별 base URL·접속·비밀 참조를 맡는다. 정확한 키와 스키마는 후속 OpenSpec에서 확정한다.

`source.json`의 offset 방식 예시:

```json
{
  "connectionRef": "vulnerability-api",
  "path": "/vulnerabilities",
  "method": "GET",
  "itemsPath": "data.items",
  "pagination": {
    "type": "offset",
    "offsetParam": "offset",
    "limitParam": "limit",
    "start": 0,
    "limit": 1000,
    "totalPath": "data.total"
  }
}
```

이 예시의 `vulnerability-api` Connection은 환경별 base URL을 제공한다. 원천이 `data.total`을 반환하는 경우이며 다른 원천에도 같은 종료 규칙을 강제하지 않는다. 인증 값은 코드·설정에 직접 넣지 않고 Connection/secretRef로 연결한다. 가공 코드는 추출된 데이터를 받아 필드 변환·레코드 분리를 수행하고 공통 검증·저장 경로에 결과를 반환한다.

등록 목록 예시:

```json
{
  "plugins": ["./plugins/vulnerability-feed"]
}
```

사용자는 예제 폴더 복사 → 설정·가공 코드 작성과 JavaScript 사전 빌드 → 등록 목록 추가 → 대상 플랫폼 이미지로 계약 검증 → 외부 플러그인 revision 고정·읽기 전용 주입 → 서버 재기동 순서로 사용한다. 수집 대상과 메뉴·기본 목록·상세가 함께 등록되어야 한다. 사용자 정의 React 화면은 별도 프론트엔드 번들 계약 전까지 플랫폼 빌드에 포함한다.

### 데이터 획득과 형식 처리

수집은 데이터를 가져오는 방법과 그 내용을 읽는 방법을 분리한다. JSON API, 로컬 CSV 파일, API로 다운로드하는 CSV를 지원 대상으로 둔다. 로컬 파일과 HTTP 다운로드는 서로 다른 획득 경로지만 같은 CSV 파서를 사용한다. 기본 파일 경로는 플랫폼 실행 환경에서 접근 가능한 경로이며 브라우저 업로드 기능을 의미하지 않는다.

CSV는 헤더·구분자·인코딩·따옴표·줄바꿈 규칙에 따라 행 단위로 읽고 공통 레코드 묶음으로 전달한다. 날짜·숫자·불리언 등의 업무 타입 변환은 필수 JS/TS 가공 코드가 담당한다. 파일 전체를 메모리에 모으지 않고 크기 제한·파일 변경 및 다운로드 중단 감지를 처리하며 불완전한 파일로 자산 부재를 판정하지 않는다. 설정의 정확한 형식은 샘플로 확정한다.

JSON·CSV 모두 획득 → 형식 파싱 → 필수 가공 → 검증 → DB 저장을 따른다. 각 경로는 한 번에 구현하지 않고 첫 샘플의 전체 흐름을 완성한 뒤 추가한다.

### 원천별 반복 호출 방식

자주 쓰는 호출 방식은 설정의 선택 항목으로 제공하고, 지원되지 않는 동작은 플러그인의 custom 수집 코드로 처리한다. 이 선택은 플러그인 파일의 수집 설정이며 웹에서 Connection 구조를 편집하는 기능을 의미하지 않는다.

| 방식 | 설정 또는 구현 책임 |
|---|---|
| single | 한 번 호출하고 종료 |
| offset | offset·limit 파라미터 이름, 시작 위치, 묶음 크기와 종료 조건 |
| page | page·size 파라미터 이름, 0/1 등 시작 페이지, 묶음 크기와 종료 조건 |
| cursor | 요청 토큰 이름, 응답 다음 토큰 경로와 종료 조건; 필요에 따라 후속 기본 도우미 추가 |
| custom | 별도 수집 코드가 요청·다음 위치·종료를 처리하고 공통 묶음 계약으로 반환 |

초기 기본 지원은 single·offset·page·custom이며 cursor는 실제 수집처 요구에 따라 추가한다. API 주소·메서드·파라미터·데이터 배열 경로, 원천이 제공하는 total·hasNext·다음 토큰·빈 응답 등 종료 기준을 원천별로 정의한다. 요청량보다 적게 반환하면 종료하는 규칙은 해당 API가 보장할 때만 사용한다.

offset=0/1000/2000, limit=1000처럼 반복 호출할 때도 한 묶음씩 수집 → 가공 → 검증·저장하며 전체 데이터를 메모리에 모으지 않는다. 수집용 1000건과 화면의 20·50·100·200건은 독립적이다. custom도 같은 가공·검증·권한·저장 경계를 사용한다.

저장 완료 이후 다음 offset·page·cursor 등 재개 상태를 기록한다. 종료·재개 정보의 타입과 수명은 SDK에서 정의하고 실패 후 반복된 레코드는 유일키로 갱신한다. 원천 변경으로 offset이 밀리면 유일키만으로 누락을 막을 수 없으므로 안정적 정렬·스냅샷 지원 여부와 미지원 시 제약을 수집처별로 기록한다. 토큰 미변경 등 진행 불가를 정상 종료로 오인하지 않도록 검증한다.

### 역할과 담당 자산 범위

| 역할 | 권한 |
|---|---|
| Employee | 본인 담당 자산 정보만 조회 |
| Security·Audit·Admin | 모든 데이터 접근 및 플랫폼의 모든 기능 실행; 세 역할 간 권한 차등 없음 |

역할별 작업 권한과 담당 자산 범위를 서버에서 함께 검사한다. Employee 제한은 목록·상세·검색·집계·본문·다운로드에 동일하게 적용하며 직접 URL이나 API 호출로 우회할 수 없어야 한다. 플러그인은 데이터와 자산의 연결 및 기능별 필요 권한을 선언하고 플랫폼이 공통으로 집행한다. 담당 자산 연결이 없는 데이터를 Employee에게 전체 공개하지 않는다. 복수 자산 연결의 허용 규칙은 별도 설계한다.

이 역할은 Git 파일을 배포하는 서비스 운영자의 작업 구분과 별개다. 초기에는 Security·Audit·Admin을 구분된 역할 이름으로 유지하되 모두 동일한 전체 권한을 부여한다. 담당 자산 제한 없이 조회·수정·담당자 지정·다운로드·동기화·플랫폼 관리 기능을 사용할 수 있다. Git 파일로 관리하는 구조·플러그인의 변경 절차는 그대로 유지한다. 역할·담당 자산 제한은 계정관리 활성화 시 적용하고 비활성화 시 전체 접근을 제공한다. LDAP·AD는 인증 연동 수단이며 공통 역할 검사를 LDAP 구현에 종속시키지 않는다.

### 저장 경계

공통 식별·출처·수집 시각과 모듈별 필드·관계를 구분한다. 플랫폼 DB와 원천 API·DB·파일은 별개이며 조회 API는 저장된 데이터만 읽는다. 원천은 읽기 전용으로 접근하고 수동 담당자·감사 등 플랫폼 업무 정보는 재수집으로 덮어쓰지 않는다. 정확한 물리 저장 모델은 DB 계약 설계에서 정한다.

### 실패를 격리한다

- 잘못된 JSON은 CI에서 배포 전에 차단하고, 이미 운영 중인 배포본은 계속 동작해야 한다.
- preview·개발 환경에서는 실패한 definition만 격리하고 검증 오류를 운영자에게 표시한다.
- connector 하나의 장애가 다른 자산 수집 작업에 영향을 주지 않아야 한다.
- 수집 작업은 timeout과 중복 방지를 지원한다. 요청 단위 재시도는 실행 계약에서 정하며 실패한 전체 작업의 자동 재실행을 필수로 요구하지 않는다.

수집 실패 시 마지막 저장 결과와 수집 상태·시각을 제공한다. 원천 응답 전체 복제는 필수가 아니며, 필요한 데이터만 가공·저장한다.

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| Runtime | Node.js 24 LTS | 오픈소스 사용자에게 안정적인 LTS 기준 제공 |
| Language | TypeScript | 프론트·백엔드·SDK 타입 공유 |
| Backend | NestJS | API·권한·연동의 모듈 경계와 TypeScript 기반 서버 개발 |
| Frontend | React + Vite | 범용 동적 UI 구성에 적합 |
| Table | TanStack Table | JSON 기반 동적 컬럼 구성에 적합 |
| Chart | ECharts | 다양한 선언형 차트 지원 |
| Validation | JSON Schema 2020-12 + Ajv | 공개 definition 계약 검증 |
| 서비스 운영 DB | PostgreSQL·MySQL을 MVP에서 지원 | 공통 저장소 계약 뒤에 DB별 adapter와 migration을 둠; definition·Connection 설정은 Git 파일에서 관리 |
| 서비스 DB migration | 제품별 versioned migration | 공통 schema는 유지하고 PostgreSQL·MySQL의 타입·index·upsert 차이는 adapter가 흡수 |
| 원본 DB | PostgreSQL connector를 MVP에 포함, 다른 DB driver는 이후 확장 | 표 데이터의 출처를 읽기 전용으로 연결 |
| Authentication | 계정관리를 비활성화하고 사용 가능; LDAP·Active Directory 선택 지원 | 실제 로그인·세션·역할 매핑 방식은 후속 설계; SSO는 현재 범위 제외 |
| Queue | Redis + BullMQ | 후속 자동 수집 단계의 큐·워커; 최초 수동 수집·조회에는 필수 아님 |
| Monorepo | pnpm workspace | 공식 connector와 공통 패키지 통합 관리 |
| Test | Vitest, Playwright, Testcontainers | 단위·화면·실제 DB 통합 검증 |
| Local infra | Docker Compose | 한 명령으로 개발 인프라 실행 |

NestJS는 조회·업무 API와 수집 실행 요청을 담당한다. 수집 로직은 별도 collection-engine으로 두어 초기 CLI 실행과 후속 worker가 재사용한다. Connector SDK가 HTTP 요청·응답 객체 및 NestJS DI에 직접 의존하지 않도록 프레임워크 경계를 분리한다.

### 운영 DB 확장 계약

운영 DB는 초기 PostgreSQL·MySQL 어댑터를 제공하고 등록된 어댑터에서 선택한다. 운영 DB 어댑터는 원천 데이터를 가져오는 수집 플러그인과 별개다. 수집·가공 플러그인과 업무 API는 DB 제품을 알 필요가 없어야 하며, 코어에 제품별 SQL·분기나 driver 타입을 노출하지 않는다.

신규 DB 추가 범위는 어댑터 구현·의존성, 제품별 migration, 어댑터 등록과 배포 설정, 공통 계약 테스트 및 운영 문서다. 연결·해제, 저장·갱신·유일키, 관계 조회·검색·정렬·페이징·건수, 권한 범위 조회, 저장/checkpoint 일관성과 업무 정보 보존을 같은 계약으로 검증한다. 필수 계약을 지원하지 않는 어댑터는 등록·기동 검증에서 명시적으로 거부하고 기능을 조용히 생략하지 않는다.

어댑터 등록 방식·설정 schema·계약 버전은 후속 OpenSpec에서 확정한다. DB 제품 간 기존 데이터 이전 도구는 어댑터 선택과 별도 범위이며, 어댑터 변경만으로 기존 데이터가 자동 이전된다고 가정하지 않는다.

## 4. 구현 경계

- `apps/web`, `apps/api`: 공통 화면과 조회·업무 API
- 플러그인·등록 목록: 사용자 수집 설정·가공 코드·데이터·화면 정의
- Connection: 환경별 접속·비밀정보 참조
- 공개 SDK·수집 엔진: 기본/custom 수집·묶음 처리·가공 호출·checkpoint
- 저장 adapter: 공통 저장·조회 계약 구현과 DB별 migration; 초기 PostgreSQL·MySQL 제공, 신규 DB 어댑터 등록 지원
- 공통 renderer·권한 계층: 플러그인별 메뉴·화면 생성과 접근 검사

패키지 이름과 배치는 구현 단계에서 정하고 필요한 단위부터 만든다.

## 5. 플러그인 정의와 내부 데이터 규격

사용자가 작성하는 공개 형식은 `plugin.json`·`source.json`·가공 코드다. 플랫폼은 이를 검증해 내부 실행 정의를 생성한다.

- `plugin.json`: 모듈 ID·버전, 데이터 필드·타입·표시명·유일키·기본 담당자·관계, 메뉴·목록·상세와 코드 파일 참조의 유일한 원본이다. 검색·필터·정렬 허용 여부와 표시 형식도 필드에 정의한다.
- `source.json`: Connection 참조, HTTP 메서드·경로·파라미터·응답 데이터 경로·반복 호출 방식 또는 custom 코드 참조를 정의한다.
- `connections/`: 환경별 base URL·DB 접속 대상과 secretRef·접속 정책을 정의한다. 같은 주소·인증 설정을 source와 Connection 양쪽에 중복 정의하지 않는다.
- 가공 코드: 원천 데이터를 선언한 필드·레코드·관계로 반환하는 변환의 유일한 구현이다. 별도의 JSON mapping을 중복 작성하도록 요구하지 않는다. 공통 변환 도우미는 코드에서 사용할 수 있다.
- 내부 definition registry: 위 파일을 결합·검증한 실행 모델이다. 생성 결과를 사용자가 수정하거나 별도로 버전 관리하지 않는다.

manifest에 설정 규격 버전인 `apiVersion`을 두고 모듈 릴리스 `version`과 구분한다. 정확한 버전 문자열과 JSON Schema는 후속 OpenSpec에서 확정한다. 일반 연동은 플러그인 파일 세 개와 등록 목록으로 시작하고, 환경별 연결은 기존 Connection을 참조하거나 필요할 때 추가한다.

### Connection 리소스

Connection은 `connections/`에서 Git으로 관리하는 비밀 제외 환경별 접속 설정이며 source는 connectionRef로 참조한다. 실제 인증 정보는 secretRef가 가리키는 권한 제한 secret 파일, Vault·클라우드 secret manager·Kubernetes Secret 등에 저장한다.

~~~json
{
  "id": "production-inventory-db",
  "connector": "postgres",
  "config": {
    "host": "inventory-db.internal",
    "port": 5432,
    "database": "inventory",
    "sslMode": "verify-full"
  },
  "secretRef": "vault://catalog/prod-inventory-db",
  "accessPolicy": {
    "allowedSchemas": ["inventory"],
    "allowedTables": ["servers"],
    "statementTimeoutMs": 5000
  }
}
~~~

Connection 생성·변경은 서비스 운영자가 Git PR로만 수행하고, CI와 staging에서 테스트한다. API 응답, 로그, Git의 플러그인·Connection 파일에는 password, private key, access token, 전체 connection string을 포함하지 않는다.

### 커스텀 가공 코드와 유일키 계약

새 데이터 종류를 추가하는 사용자는 플러그인에 가공 코드 파일을 제공한다. 해당 원천 데이터를 받을 때마다 플랫폼은 등록된 가공 코드를 실행하고 반환된 레코드·관계를 공통 검증한 뒤 DB에 적재한다. 중첩 배열 분리, 필드명·타입 변환, 담당자 필드 추출은 이 코드에서 처리할 수 있다. 가공 함수는 DB에 직접 쓰지 않고 결과를 반환한다.

플러그인의 가공·custom 수집 코드는 JavaScript와 TypeScript로 개발할 수 있다. TypeScript 코드는 운영 배포 전에 JavaScript로 변환하고 플랫폼은 운영 시점에 transpile하지 않는다. 기본 개발 예제는 TypeScript로 제공하며 Python 등 다른 언어 지원은 계획 범위에 포함하지 않는다. 호출 입력·출력, 오류·시간/크기 제한, 버전·의존성 계약은 공개 SDK로 정의한다.

각 데이터 종류에는 유일키 필드가 반드시 하나 존재하고, 플러그인 설정에서 어떤 필드인지 선택할 수 있어야 한다. 플랫폼은 가공 결과의 해당 필드가 존재하며 비어 있지 않고 허용 타입인지 검증한다. 같은 수집 범위의 서로 다른 레코드가 동일 키를 가지면 명시적으로 검증 실패 처리하고 임의로 덮어쓰지 않는다. 재수집에서 같은 키는 기존 레코드 갱신에 사용한다. 플러그인·데이터 종류·수집처 범위로 키를 구분해 서로 다른 출처의 같은 값이 충돌하지 않게 한다. 정확한 범위와 키 변경 시 이관 규칙은 상세 명세에서 확정한다.

### 정규화와 표 렌더링 계약

이 문서에서 mapping은 플러그인 가공 코드에 의한 변환을 뜻하며 별도 필수 JSON 파일이 아니다. 가공 결과는 선언된 레코드와 관계로 정규화한다. 유일키는 가공 결과에서 설정한 필드로 식별하며 화면은 가공 결과의 선언된 필드 경로를 참조한다. 물리 저장 구조는 DB 계약에서 정한다.

필드의 데이터 타입과 표시 형식은 분리한다. 기본 타입은 string, number, boolean, datetime, object, array를 지원한다. 객체는 내부 필드를, 배열은 요소 타입과 객체 요소의 내부 필드를 정의한다. 표시 형식에는 text, badge, link, percent, ip와 배열 요소를 표시하는 tags 등을 둔다. 이 분리로 숫자 percent의 정렬·집계와 문자열 link의 URL 검증을 각각 일관되게 처리한다.

수집 설정은 요청 방식과 건수·바이트 제한을 정의하며 화면 페이지 크기와 별개다. 구체적 처리 한도는 샘플 검증으로 정한다.

중첩 객체·배열도 필수 가공 코드를 거친 결과를 저장·표시한다. 가공 코드는 필요한 형태로 펼치거나 원래 구조를 유지해 반환할 수 있다. `plugin.json`은 반환된 데이터의 타입·내부 필드 경로·표시 방법을 정의하며 가공 코드를 대체하지 않는다. 예를 들어 `test_field2`의 객체 배열에서 `login`을 태그로 표시하고, `test_field3.test_field5`를 날짜 필드로 표시할 수 있어야 한다. 기본 목록·상세에서 이 동작을 제공하므로 별도 React 화면 코드가 필요하지 않다. 배열 검색·필터의 요소 일치 규칙, 배열 정렬 지원 범위와 중첩 깊이·요소 수·크기 제한은 명세에서 정한다.

모든 원천 데이터는 플러그인의 가공 단계와 플랫폼의 공통 검증을 반드시 통과한 뒤 업무 데이터로 저장한다. 이미 적합한 응답도 동일 경로에서 그대로 반환·검증할 수 있으며 직접 적재로 우회하지 않는다. 중첩 배열은 가공 코드에서 독립 레코드와 관계로 나눌 수 있고, 상세용 부가 정보만 제한된 JSON으로 유지할 수 있다. 원본 보관은 추적·재가공용 선택 사항이며 업무 저장을 대체하지 않는다. 목록·상세 renderer는 저장 모델의 필드만 사용하며 수집 설정이나 비밀정보를 받지 않는다. 큰 본문을 필드에 무제한 담지 않는다. 플러그인 정의 변경 시 새 수집에 적용하고, 기존 저장 데이터의 재가공·migration 필요성을 검증한다. 표시 이름 변경처럼 재가공이 불필요한 변경도 구분한다.

## 6. Connector SDK

Connector는 외부 시스템과 원본 DB에서 데이터를 가져오는 역할만 담당한다. 저장, 메뉴 생성, 화면 렌더링은 코어에서 처리한다. 서비스 운영 DB 세션이나 HTTP 요청·응답 객체 및 NestJS DI를 connector에 전달하지 않는다.

```typescript
// 공개 계약 초안. 타입과 크기 제한의 세부 사항은 샘플 검증 후 확정한다.
export interface AssetConnector<TConfig = unknown> {
  id: string;
  configSchema: JSONSchema;
  test(config: TConfig): Promise<ConnectionResult>;
  discover?(config: TConfig): Promise<DiscoveredField[]>;
  collect(context: CollectionContext<TConfig>): AsyncIterable<CollectionBatch>;
}
```

CollectionContext는 비밀정보가 해석된 설정, 실행 범위(full 또는 asset), 대상 데이터 종류·유일키와 원천 조회용 식별 정보, 재개용 checkpoint, 취소 신호와 건수·바이트 제한을 전달한다. 자산별 요청의 내부 ID는 서버가 등록된 원천 식별자로 해석하며 사용자 입력으로 Connection·조회 범위를 임의 지정하게 하지 않는다. checkpoint는 플러그인·Connection·실행 범위·설정 revision에 귀속하고 전체 실행과 자산별 실행 사이에 재사용하지 않는다. CollectionBatch는 자산·취약점 등 구분 가능한 제한된 원천 레코드 묶음과 저장 후 확정할 nextCheckpoint, 요청한 범위의 수집 완료 여부를 제공한다. asset 범위 완료를 원천 전체 수집 완료로 해석하지 않는다. 큰 본문은 제한된 스트림 또는 별도 본문 참조로 전달하는 계약을 검증한다. 단순히 AsyncIterable을 사용했다는 이유만으로 응답 전체 버퍼링이 허용되는 것은 아니다.

connector는 원천의 페이지 처리를 내부적으로 수행한다. 사용자 목록 조회 메서드는 connector에 두지 않는다. collection-engine은 mapping·검증·저장을 수행하고, 조회 API는 storage-adapter만 사용한다.

공식 connector의 초기 범위는 다음과 같다. 첫 샘플 connector부터 하나씩 구현하며 한 번에 모두 연결하지 않는다.

1. Fixture connector
2. JSON file connector
3. REST connector
4. PostgreSQL source DB connector

추후 webhook, GraphQL, S3, Prometheus, Elasticsearch connector를 확장한다.

GitHub repository와 취약점 연동은 별도 discovery 단계에서 API 응답 포맷을 확인한 뒤 범위를 확정한다. repository 식별자, 취약점의 repository 연결 방식, severity·status·package/file 정보, 담당자 또는 CODEOWNERS 포함 여부, GitHub 사용자 식별자를 확인한 뒤 관련 정의를 정한다. LDAP 사용자와의 연결은 LDAP를 선택할 때 별도 조사하며 기본 취약점 연동을 막지 않는다.

Connector가 반드시 지켜야 할 계약은 다음과 같다.

- timeout을 준수한다.
- 수집은 전체 결과를 메모리에 올리지 않고 streaming과 batch 처리로 수행한다.
- 원본 DB 수집은 OFFSET 대신 안정적인 primary key 또는 updated_at와 primary key 조합의 keyset pagination을 사용한다.
- checkpoint와 abort signal을 존중해 중단된 수집을 안전하게 재개하거나 취소할 수 있어야 한다.
- 재실행해도 동일 자산이 중복 생성되지 않는다.
- secret을 로그나 오류 응답에 출력하지 않는다.
- 레코드 오류는 격리·기록해 가능한 나머지 처리를 계속하되 부분 완료로 표시한다. 저장소 장애·설정 오류 등 실행 전체 문제는 중단한다.
- 취소 신호를 처리한다.
- 원천에서 받은 checkpoint는 해당 묶음의 데이터 저장이 완료된 뒤에만 확정한다. 재전달된 묶음도 같은 식별자로 갱신한다.
- 건수·바이트·동시성 한도를 적용하고 소비 속도가 느리면 읽기를 늦춘다. 잘못된 행·초과 레코드는 오류로 기록하고 전체 성공으로 오인하지 않는다.

## 7. 플랫폼 저장 모델과 수집·조회 흐름

### 저장소의 역할

| 저장소 | 보관 내용 | 접근 주체 |
|---|---|---|
| 원천 API·DB·파일 | 외부 시스템이 소유한 데이터 | connector의 수집 경로 |
| 플랫폼 DB | 정규화 자산·취약점, 수집 상태·checkpoint, 담당자·감사 | collection-engine, 조회·업무 API |
| 큰 본문 저장소 | 필요한 보고서·본문·첨부 | 수집 저장 경로, 상세·다운로드 API |
| Git 설정 | 플러그인 설정·Connection·계정 정책 | 검증·배포·registry loader |

플랫폼 DB는 등록된 어댑터에서 선택하며 PostgreSQL·MySQL은 초기 지원 대상이다. 제품별 migration·adapter가 SQL·JSON·index·upsert 차이를 흡수한다. 큰 본문은 별도 테이블 또는 영속 파일·객체 저장소에 보관하고 위치는 규모 조사 후 결정한다. 관리형 객체 저장소를 기본 설치의 필수 조건으로 삼지 않는다.

### 논리 모델

아래 모델은 기존 자산·취약점 도메인의 출발점이다. 새 데이터 종류를 추가할 때 본체의 테이블 정의·repository 수정이 필요하지 않도록 확장 저장 계약을 설계한다. 공통 레코드와 JSON 필드, 모듈별 스키마·migration 등 물리 저장 방식은 미정이며 검색·인덱스·관계·PostgreSQL/MySQL 호환성을 비교해 확정한다. 정확한 테이블·키는 샘플로 검증하되 아래 책임은 유지한다.

| 모델 | 주요 정보와 경계 |
|---|---|
| assets | 내부 ID, 수집처·정의·외부 ID, 이름·종류·환경, 제한된 attributes, 원천 수정 시각·수집 시각 |
| findings | 내부 ID, 연결된 asset, 수집처의 취약점 식별자, 제목·심각도·원천 상태·정규화 상태, 패키지·위치, 최초·최종 관측 시각 |
| finding_details | 큰 본문의 참조·크기·형식·해시·보존 정보; 목록 쿼리에서 제외 |
| collection_runs | 실행 ID·상태·설정 revision·시작/종료·성공/오류 건수·바이트·마지막 저장 checkpoint·전체 범위 완료 여부 |
| asset_managers | 원천 필드 기반 담당자와 수동 override 목록·적용 상태; 수동 지정 우선, 미설정 시 원천 기본값; Admin 역할과 별개 |
| assignments | 내부 finding 참조와 플랫폼 담당자 정보; 원천 owner와 별개 |
| audit_logs | 업무 변경 주체·대상·시각·변경 내용; 비밀정보 제외 |
| users / auth_sessions | 계정관리를 활성화한 경우의 모델 후보; 별도 명세에서 확정 |
| asset_relations / 모듈별 레코드 관계 | 가공 결과의 관계와 담당 자산 연결에 필요한 기본 모델; 시각적 관계 그래프는 후속 기능 |

assets·findings·collection_runs는 최초 수집→저장→조회 검증부터 사용한다. 담당자·감사는 해당 업무 단계에서, 사용자·세션은 선택 인증 단계에서 추가한다. 기존 저장 정보를 지우고 재삽입하는 방식으로 재수집하지 않는다. 같은 CVE라는 이유만으로 서로 다른 대상·패키지의 취약점을 합치지 않는다. 수집처 간 동일성 판단은 별도 규칙이며, 초기에는 출처를 보존한다.

### 수집 실행과 저장

1. 시작 시 전체 실행·일일 스케줄·수동 CLI·자산별 요청으로 승인된 설정 revision과 Connection을 읽고 실행 기록을 만든다.
2. connector가 원천을 페이지·스트림으로 읽는다. 원천이 지원하면 안정적인 cursor/keyset 또는 변경 시각과 ID를 사용한다.
3. 플러그인의 mapping/가공 코드가 선언한 레코드·관계로 변환하고, 플랫폼이 타입·필수 값·고유 키·크기·자산 연결을 공통 검증한다.
4. 제한된 묶음으로 upsert하고 저장 완료와 checkpoint 확정을 동일 트랜잭션 등 일관된 방법으로 처리한다. 격리한 레코드의 오류·재처리 근거도 checkpoint 진행 전에 영속 기록한다.
5. 레코드별 미저장 오류를 포함해 최종 결과와 오류·부분 완료 여부를 기록한다. 재실행은 저장된 checkpoint와 안정적인 키를 사용한다.

수동 실행은 최초 단계에서 CLI 프로세스로 제공하며 웹 조회 요청 안에서 전체 수집을 실행하지 않는다. 이후 실행 API·큐·워커를 붙일 때도 같은 수집 코어를 사용한다. 수집 요청 접수는 저장 완료를 의미하지 않는다.

매일 22:00 실행은 원천의 변경분 지원 여부와 관계없이 전체 범위를 수집한다. 증분 갱신은 Phase 2의 별도 실행 방식이며 일일 전체 동기화를 자동 대체하지 않는다. 전체 순회는 제한된 묶음으로 처리하고 비용을 측정한다. checkpoint가 만료되면 재수집 범위와 중복 방지 정책을 적용하며 완료를 가장하지 않는다. 같은 수집 범위의 실행은 겹치지 않게 하거나 이전 실행이 최신 데이터를 덮지 않도록 순서를 보장한다.

### 원천에서 사라진 자산의 보관·복원

- 플러그인·Connection을 제거하거나 비활성화해 수집하지 않은 경우에는 원천 부재로 판단하지 않고 기존 자산 상태를 유지한다.
- 자산은 별도 DB로 옮기거나 자동 삭제하지 않고 같은 DB에서 활성·보관 상태로 관리한다. 기본 활성 목록과 보관 목록을 구분하고 동일한 조회 권한을 적용한다.
- 전체 범위 수집이 정상 완료된 것으로 검증된 경우에만 이번 수집에서 확인되지 않은 자산을 보관 상태로 전환하고 ‘원천에서 확인되지 않음’으로 표시한다. 판정은 해당 수집처·데이터 종류 범위에 한정한다.
- 수집 실패·부분 성공·페이지 누락·잘못된 레코드가 있으면 그 범위의 부재 판정을 하지 않고 기존 자산·담당자·상태를 유지한다. HTTP 성공이나 빈 응답만으로 전체 범위 완료를 판단하지 않는다. 종료 조건·응답 구조·원천이 제공하는 전체 건수 등을 검증하며 빈 결과의 정상 완료 판단 기준은 수집처 계약으로 정의한다.
- 보관 시 내부 ID·유일키·수동 담당자·관계·이력과 마지막 관측·보관 시각을 유지한다. 보관은 취약점 해결이나 데이터 삭제를 의미하지 않는다.
- 같은 플러그인·데이터 종류·수집처 범위의 같은 유일키로 다시 나타나면 기존 레코드를 활성 상태로 복원하고 원천 필드를 갱신한다. 수동 담당자와 이력은 보존한다. 자산별 수집도 해당 자산의 재등장은 반영할 수 있지만 다른 자산의 부재는 판정하지 않는다.

### 자산 수동 삭제

Security·Audit·Admin은 원천에서 제거된 것으로 확인된 보관 자산을 수동 삭제할 수 있다. 원천에 존재하는 자산과 활성 자산은 삭제할 수 없다. Employee에게는 삭제를 허용하지 않는다. 계정관리 비활성화 시에는 전체 접근 정책에 따라 삭제 기능을 제공하되 원천 존재 여부 조건은 동일하게 적용한다. 원천 시스템의 데이터는 삭제하지 않는다.

삭제 시 서버는 권한과 자산 상태를 검사하고 원천에 해당 자산이 없는지 다시 확인한다. 원천에 존재하면 삭제를 거부하며, 조회 실패·부분 응답·원천 연결 또는 플러그인 비활성화 등으로 확인할 수 없을 때도 삭제를 진행하지 않는다. 단건 조회 미지원 원천의 확인 방법은 수집 계약에서 정하며 단순한 API 오류나 빈 응답을 부재 증거로 사용하지 않는다. 동기화와 삭제가 같은 자산에서 충돌하지 않도록 처리한다.

삭제는 플랫폼에서 복구할 수 없는 영구 삭제로 처리한다. 삭제 주체·시각·대상과 원천 부재 확인 근거는 자산과 별개의 감사 기록으로 보존하며 자산 삭제에 연쇄 삭제되지 않게 한다. 실행 전 화면에서 대상과 영구 삭제 여부를 확인할 수 있게 한다. 영구 삭제한 자산과 그 수동 담당자 지정은 복원하지 않는다. 이후 같은 유일키가 원천에서 다시 수집되면 새 내부 ID의 자산으로 등록하고 원천 담당자 매핑을 적용한다. 보존한 삭제 감사 기록은 과거 삭제 사실을 확인하기 위한 것이며 복원 데이터로 사용하지 않는다. 공유 관계·본문 등 관련 데이터의 정리 경계는 구현 전에 확정한다. 자동 보관·복원과 사용자 영구 삭제는 별도 동작으로 구분한다.

### 일일 전체 동기화

- MVP는 매일 밤 10시(22:00)에 등록·활성화된 모든 수집 대상의 전체 동기화를 시작한다. 시간대는 우선 `Asia/Seoul`로 가정하며 배포 설정으로 명시한다. 다른 시간대 사용 여부는 운영 요구에 따라 확정한다.
- 전체 동기화는 각 대상의 전체 범위를 읽어 필수 가공·검증·upsert하는 의미다. 원본 응답 전체 복제나 플랫폼 DB 삭제 후 재삽입을 뜻하지 않는다. 자산 관리자와 취약점 담당자 등 수동 업무 데이터는 보존한다.
- 수동 실행과 스케줄 실행은 동일 수집 코어를 사용한다. 중복 기동·이전 실행 지연 시 동일 대상이 겹치지 않도록 하고, 일부 수집처 실패가 다른 수집처의 실행을 막지 않도록 한다.
- 실행 예정 시각·시간대·시작/종료·전체/부분 성공·실패·마지막 성공을 기록한다. 22:00은 시작 시각이며 완료 시각 보장이 아니다.
- 22:00 전체 동기화가 실패하거나 부분 실패하면 실행 결과를 저장하고 역할·담당 자산·계정관리 활성화 여부와 관계없이 모든 사용자에게 화면 맨 위 공통 알림을 표시한다. 공통 알림은 실패 시각과 실패·부분 실패 여부를 알린다. 자산별 상세 정보와 실행 결과는 기존 조회 권한을 적용해 제공한다. 초기 요구는 인앱 실패 알림이며 자동 재시도·이메일·메신저 발송을 필수로 추가하지 않는다.
- 실패·부분 실패 알림은 해당 대상·범위의 다음 동기화가 정상 완료되면 자동 해제한다. 다른 수집처의 성공이나 전체 범위 중 일부 자산의 성공만으로 미해결 실패 알림을 해제하지 않는다. 여러 대상이 실패했다면 미해결 대상이 남아 있는 동안 공통 알림을 유지한다. 알림 해제 후에도 실패 시각·대상·원인·실행 결과는 이력으로 보존한다. 이력 보존 기간은 운영 정책에서 정한다.
- 전체 동기화 중이거나 실패해도 기존 저장 데이터의 목록·상세 조회를 유지한다. 실패한 항목의 마지막 저장 결과와 수동 담당자 지정값은 보존한다.
- 최초 설치와 재시작을 포함해 플랫폼을 시작할 때마다 등록·활성화된 모든 수집 대상을 전체 동기화한다. 실행 중에는 매일 22:00에도 전체 동기화한다. 시작 시 누락 일정 여부로 실행을 제한하지 않으며 누락 일정을 별도로 반복 보충하지 않는다. 대상이 없으면 수집하지 않는다.
- 시작 시 전체 동기화 중에도 기존 데이터 조회를 유지하고 최초 수집 전에는 미수집·수집 중 상태를 표시한다. 실패 기록은 보존하며 모든 사용자 대상 알림 정책을 적용한다.
- 시작 실행과 정규 실행이 겹치거나 여러 인스턴스가 동시에 시작돼도 같은 범위의 작업이 중복 실행되지 않도록 실행권을 관리한다. 중단 당시 작업은 미완료 상태로 식별하고 이전 실행이 새 결과를 덮지 않도록 한다. 구체적 실행 복구·checkpoint 처리는 명세에서 정한다.
- 알림 이력 보존 기간, 실행 중단 복구·중복 방지의 구체적 방식과 스케줄러 구현은 후속 명세에서 확정한다. Redis·별도 worker는 이 일일 실행 요구의 필수 구현 방식으로 고정하지 않는다.

### 자산별 수동 동기화

각 자산에 동기화 버튼을 제공한다. 사용자가 실행하면 서버가 권한과 대상 범위를 확인하고 해당 자산의 수집·가공·검증·갱신 작업을 시작한다. 요청 접수와 작업 완료를 구분하고 진행 중·성공·실패 상태를 표시한다. 웹 요청에서 장시간 수집을 완료할 때까지 기다리게 하지 않는다.

자산별 실행과 일일 전체 실행은 같은 코어와 수동 담당자 보존 규칙을 사용하고 동일 자산의 중복 실행·오래된 결과 덮어쓰기를 막는다. 원천이 단건 조회를 지원하지 않으면 connector가 필요한 범위를 읽어 해당 자산을 선택하는 방식을 명세화하고, 단건 실행에서 다른 자산의 부재·삭제를 판정하지 않는다. Security·Audit·Admin은 버튼과 실행 API를 사용할 수 있으며 Employee는 조회 전용으로 동기화 실행을 허용하지 않는다.

### 조회 API와 화면

조회 API는 플랫폼 DB의 저장된 자산·취약점만 읽는다. 목록은 인덱스와 안정적인 정렬·페이지 처리를 적용해 요약 필드만 반환한다. 상세·큰 본문·다운로드는 별도 요청으로 제공하며 응답 크기를 제한한다. 원천 Connection으로 우회 조회하거나 원천 장애 때문에 화면 조회를 실패시키지 않는다.

수집 전에는 ‘아직 수집되지 않음’, 성공했으나 결과가 없으면 ‘결과 없음’, 실패·부분 완료 시에는 해당 상태와 마지막 저장 시각을 표시한다. 묶음 단위 저장 완료 데이터는 조회할 수 있지만 실행 중·부분 갱신임을 명시한다. 동기화 중 기존 조회를 유지한다는 요구는 조회 가능성의 보장이다. 성공한 묶음부터 갱신하므로 이전 값과 새 값이 함께 보일 수 있고 실패 시 이미 저장한 묶음을 되돌리지 않는다. 기본 계약은 전체 실행의 원자적 화면 교체를 보장하지 않는다. 전체 스냅샷 전환이 필요하면 별도 요구로 설계한다.

목록은 불투명 cursor 기반의 다음 묶음 이동과 묶음당 20·50·100·200건 선택을 필수 제공한다. 기본값은 20건이다. 사용자가 20·50·100·200건 중 선택한 값은 목록 설정에 저장하고 다음 방문 시 복원한다. 초기 조회는 `lastSeenAt DESC, id ASC`의 안정적인 고정 정렬과 keyset pagination을 사용하고, 응답은 `nextCursor`와 `hasNextPage`를 제공한다. 정확한 전체 결과 건수와 임의 페이지 번호 이동은 기본 계약에 포함하지 않는다. 후속 필터링·검색·오름차순/내림차순 정렬은 묶음 분할 전에 서버에서 권한이 허용된 전체 결과에 적용하며 동일 정렬 값에는 고유 ID를 마지막 정렬 기준으로 추가한다. 조회 범위·검색·필터·정렬 또는 묶음 크기가 달라지면 기존 cursor를 폐기하고 첫 묶음부터 조회하며, API는 다른 조건에 귀속된 cursor와 허용되지 않은 묶음 크기를 거부한다.

검색창 하나에서 플러그인이 검색 가능으로 지정한 여러 필드를 함께 검색한다. 검색어가 지정된 필드 중 하나라도 포함되면 일치하는 것으로 처리한다(필드 간 OR). 별도 필터는 검색 결과에 함께 적용한다(검색과 필터 간 AND). 현재 묶음이 아니라 조회 권한이 있는 전체 데이터에서 검색·필터를 적용한 뒤 정렬·cursor 묶음 분할을 수행한다.

필드별 필터는 플러그인이 종류와 필요한 옵션을 명시한다. 예를 들어 위험도는 multiSelect와 선택값 목록, 발견일은 dateRange를 정의하고 플랫폼이 해당 필터 UI와 서버 조회 조건을 제공한다. 필터 정의가 없는 필드는 필터 UI에 표시하지 않는다. 플랫폼이 데이터 타입만으로 필터 종류를 임의 결정하지 않으며 선언된 필터·옵션과 데이터 타입의 호환성을 검증한다. 지원 필터 종류와 연산자의 정확한 계약은 후속 명세에서 확정한다.

메뉴는 플러그인에서 이름·아이콘·그룹·표시 순서와 화면 경로를 지정한다. 플랫폼은 등록된 정의에 따라 메뉴를 생성하고 그룹별로 지정 순서를 적용한다. 아이콘 식별자·경로·설정 형식을 검증하며 메뉴 숨김 여부와 별개로 서버에서 조회 권한을 검사한다. 그룹 자체의 순서와 같은 순서값 처리 등 세부 규칙은 후속 명세에서 정한다.

상세 화면은 플러그인에서 섹션 제목·순서와 각 섹션에 표시할 필드·순서를 정의한다. 기본 상세 화면은 선언 순서대로 섹션과 필드를 표시하며 객체·배열도 공통 필드 표시 규칙을 사용한다. 예를 들어 기본 정보·담당자 정보·추가 정보로 구성할 수 있다. 플랫폼은 필드 참조를 검증하고 서버의 조회 권한을 적용한다. 정확한 JSON 키는 후속 명세에서 확정한다.

정렬 가능한 필드는 플러그인이 명시한다. 사용자는 해당 컬럼 제목을 눌러 오름차순·내림차순을 선택하고 현재 방향을 확인할 수 있다. 정렬 불가 필드에는 정렬 동작을 제공하지 않으며 서버도 미허용 필드의 정렬 요청을 거부한다. 선택한 정렬은 목록 설정 저장 정책에 따라 복원한다.

검색·정렬·필터는 허용된 필드와 타입으로 제한하고 인덱스는 실제 쿼리·양쪽 DB 성능 검증에 근거한다. 집계와 추가 수집처 통합 검색은 저장 구조 위에서 후속 기능으로 구현한다.

### 플러그인 변경과 데이터 호환성 — MVP 최소 정책

플러그인 수정·재배포를 지원하기 위해 표시 변경과 데이터 변경을 구분한다. 배포 전 기존 저장 모델과의 호환성을 검증하고, 자동으로 안전하게 적용할 수 없는 변경은 명시적인 migration 또는 재가공 계획 없이 적용하지 않는다.

| 변경 | MVP 처리 기준 |
|---|---|
| 표시명·컬럼 순서·메뉴 변경 | 저장 데이터를 재가공하지 않고 적용; 개인 설정의 유효 필드 참조를 검증 |
| 선택 필드 추가 | 기존 레코드의 값 없음 처리를 정의하고 다음 수집 시 채움 |
| 필수 필드 추가·타입 변경 | 기존 데이터 검증·재가공 또는 migration을 선행; 미지원 변경은 배포 검증에서 차단 |
| 필드 삭제 | 목록·상세·검색·개인 설정 참조를 정리; 배포만으로 기존 저장 값을 파괴적으로 삭제하지 않음 |
| 유일키·출처 범위 변경 | 새 레코드 대량 생성과 담당자 연결 유실을 막기 위해 자동 적용 금지; 내부 ID·관계·수동 담당자를 보존하는 이관 계획 필요 |

플러그인·스키마·가공 코드 revision을 실행 기록과 연결한다. 재가공에 원본이 필요하지만 보관하지 않았다면 원천 재수집 가능 여부를 검증한다. 원천에 다시 접근할 수 없는 경우 변경을 완료한 것으로 취급하지 않는다.

코드·설정 롤백과 DB 복구를 구분한다. 이전 코드가 현재 저장 스키마를 읽을 수 있는지 배포 전에 확인하고, 데이터 변경이 있었다면 검증된 역이관 또는 백업 복구 절차를 사용한다. Git revision만 되돌려 데이터까지 복구된다고 가정하지 않는다. 범용 migration 생성기·재가공 UI는 Phase 2에서 확장하되 최소 호환성 검사와 차단은 MVP에 포함한다.

### 대용량 본문과 데이터 보관

필요한 필드만 정규화하고 전체 원본을 무조건 복제하지 않는다. 건수와 바이트·동시성을 함께 제한하며 한 건이 한도를 넘을 때의 오류·격리 또는 스트리밍을 명시한다. 큰 본문을 API 응답 전체나 JSON attributes에 무제한 적재하지 않는다.

본문을 별도 저장소에 둘 경우 완료된 본문만 DB에서 참조하고, 실패 후 남은 파일의 정리·재실행·무결성 검증을 설계한다. 본문·원본·수집 이력의 보존 기간과 용량 한도를 구분하고, 담당자·감사 정보가 원본 보관 만료로 삭제되지 않게 한다. 저장소 부족 시 실패 상태를 남기고 성공 checkpoint를 앞당기지 않는다.

### 자산 관리자와 취약점 담당자 지정

자산 조회 담당자의 기본값은 플러그인에서 지정한 데이터 필드의 사람이다. 플러그인 작성자가 가공 결과의 담당자 필드와 계정의 어떤 속성을 비교할지 설정한다. 이메일·사번 등 특정 식별 방식을 플랫폼에서 고정하지 않으며 복잡한 원천 값은 가공 코드로 변환할 수 있다. 플랫폼은 설정에 따라 계정을 연결하고, 값이 없거나 일치하는 계정이 없거나 여러 계정이 일치하면 미지정으로 처리하고 매핑 상태를 표시한다. 모호한 값을 임의로 한 사람에게 연결하지 않는다.

수동 지정값의 기본은 미설정이다. 별도로 한 명 이상 지정하면 그 목록이 원천 담당자를 대체하여 Employee의 유효 조회 담당자가 된다. 원천 담당자와 수동 담당자를 자동 합집합으로 처리하지 않는다. 원천 담당자 값과 수동 지정 목록·적용 상태를 별도로 저장하고, 전체·자산별 재수집은 원천 값만 갱신하며 수동 지정값을 보존한다. 조회 API는 유효 담당자를 기준으로 즉시 접근 범위를 계산한다.

자산 상세 등에서 복수 담당자 지정·변경과 원천 기본값으로 복귀하는 동작을 제공한다. 수동 담당자를 모두 해제하면 수동 지정 상태를 해제하고 원천 데이터의 담당자로 복귀한다. 원천 담당자가 없거나 계정 매핑에 실패하면 미지정으로 표시한다. 화면에는 전체 해제 시 원천 담당자로 복귀함을 안내한다. 중복 지정을 막고 내부 자산 ID와 사용자 식별자, 변경 주체·시각을 기록한다. 이 지정은 플랫폼 전체 Admin 역할이나 데이터 수정 권한을 부여하지 않는다.

담당자 지정·변경과 동기화 실행은 Security·Audit·Admin에 허용한다. 계정관리 활성화·비활성화 상태의 관리자 선택·표현 방식은 상세 설계한다. 유효 담당자가 없는 자산은 Employee에게 자동 공개하지 않는다. 계정관리 비활성화 상태는 담당자 제한을 적용하지 않는다.

외부 owner·CODEOWNERS와 플랫폼 담당자를 분리한다. assignments는 안정적인 내부 취약점 ID에 연결하고 수집 과정에서 덮어쓰지 않는다. 원천 ID가 바뀌는 경우의 동일성 기준은 조사 후 명세화한다. 조치 상태는 검증된 외부 의미를 매핑하고 알 수 없는 값은 임의로 해결 처리하지 않는다.

계정관리 비활성화 상태의 담당자 표현·감사 주체는 업무 구현 전에 정한다. Git 설정 관리와 화면에서의 담당자 변경은 구분한다.

### 선택적 LDAP 연동의 로그인·사용자 관리

계정관리 활성화 시 LDAP·Active Directory 인증만 지원한다. 플랫폼에 저장하는 사용자 참조·역할·세션은 연동 인증을 위한 정보이며 자체 로그인 계정을 의미하지 않는다. 향후 자체 계정 인증도 같은 사용자·세션·권한 계약을 구현하게 하고 LDAP 사용자와 새 인증 제공자의 동일성·연결 규칙은 도입 시 명세화한다. 아래 로그인·세션 흐름은 상세 설계 후보이며 그룹-역할 매핑과 함께 구현 전에 확정한다. 여러 서비스에 한 번에 로그인시키는 SSO, OIDC, SAML 기능은 범위에 넣지 않는다.

사용자가 이 서비스의 로그인 화면에 계정과 비밀번호를 입력하면 API가 LDAP에서 사용자와 그룹을 확인하고, 성공 시 이 서비스 전용 세션을 만든다. 비밀번호는 LDAP 검증에만 사용하며 서비스 운영 DB, 로그, 브라우저 저장소에 보관하지 않는다.

인증 정보로는 LDAP의 안정적인 사용자 식별자, 표시명, 활성 상태, 마지막 로그인, 세션 hash, 감사 기록을 둔다. 담당자 지정은 별도 업무 데이터로 저장한다. LDAP 그룹과 서비스 역할의 매핑은 Git의 LDAP 정책 파일로 관리하고, LDAP 디렉터리 전체를 복제하지 않는다.

LDAP 연결은 LDAPS 또는 StartTLS를 필수로 하고, 서비스 bind 계정의 비밀번호는 외부 secret store에서만 읽는다. 사용자 검색 filter는 이스케이프하며, 로그인 rate limit과 실패 감사 로그를 적용한다.

## 8. 개발·설치·배포

- Node.js·pnpm 로컬 개발과 Docker 개발을 제공하고 웹 HMR·서버 watch를 지원한다.
- API·웹의 Dockerfile과 배포 이미지를 제공하며 기본 설치는 Compose, Kubernetes는 후속 Helm 선택 경로로 둔다.
- 공식 플랫폼 이미지는 정확한 릴리스 태그 또는 digest로 고정한다. 외부 서버 플러그인·등록 목록·Connection은 이미지에 복사하지 않고 Compose에서 운영자 관리 디렉터리를 읽기 전용 볼륨으로 주입한다.
- 등록된 운영 DB 어댑터 중 하나를 선택하고 운영 DB와 원천 fixture의 계정·데이터·영속 저장소를 분리한다. 수동 담당자·감사·설정과 큰 본문의 복구 일관성을 검증한다.
- 운영자는 플랫폼 이미지와 플러그인·등록 목록·Connection·권한 정책 revision의 조합을 배포 전에 검증하고 독립적으로 고정·롤백한다. 비밀정보는 Git·이미지·브라우저에 포함하지 않는다.
- 외부 자격증명 없는 mock 샘플로 설치·수집·화면 확인이 가능해야 한다. 계정관리 비활성화 상태에는 LDAP 서버가 필요하지 않다.
- 지원 OS·CPU·DB 버전, 이미지 배포·백업·복구 절차는 실제 검증 결과와 함께 실행 가이드에 기록한다. 구체적 Compose·환경변수·명령 예시는 이 플랜에서 중복 관리하지 않는다.

## 9. 사용자·운영자 도구

플러그인 예제와 계약 검증 도구를 제공한다. 검증은 manifest·source·필드·코드 참조·유일키·메뉴 경로·버전 호환성을 검사하고 배포 전에 오류를 표시한다. 샘플 수집·가공·화면을 확인하는 개발 경로를 제공한다.

운영 화면은 마지막 동기화·실행 상태·오류·설정 revision을 보여주고 자산별 동기화 버튼과 상단 실패 알림을 제공한다. Connection·플러그인 구조 변경은 Git 파일과 재배포로 관리한다.

## 11. 공개 배포 준비

설치·플러그인 작성·데이터 규약·Connection·DB adapter·인증·복구 문서와 기여·보안 신고·버전 호환성 정책을 제공한다. 라이선스·공개 이미지 경로·지원 환경은 릴리스 전에 확정한다. 문서 본문은 한국어, 코드·설정 식별자는 영어를 사용한다.

한 번에 한 기능만 구현하고 검증을 마친 뒤 다음 기능으로 넘어간다. 각 Phase는 여러 작은 작업을 묶은 목표이며 단일 구현 작업이 아니다.

### 0.1.0 기술 프리뷰 범위

0.1.0은 첫 정식 릴리스인 1.0.0의 완료를 의미하지 않는다. Registry에 접근할 수 없는 폐쇄망 단일 서버에서 현재 핵심 흐름을 평가하고 초기 도입 가능성을 확인하기 위한 기술 프리뷰다. 지원 환경, 출시 절차와 차단 게이트는 `docs/development-workflow.md`를 따른다.

0.1.0은 다음 범위를 하나의 사용자 여정으로 검증한 뒤 공개한다.

- 오프라인 번들 checksum 검증과 이미지 load, 버전 고정 Compose를 이용한 최초 설치
- PostgreSQL 17.6 또는 MySQL 8.4.6의 명시적 migration과 영속 데이터 보존
- 운영자가 별도로 관리하는 플러그인·Connection 설정의 읽기 전용 주입과 기동 전 검증
- 지원 원천의 수집·가공·저장과 플랫폼 DB만 사용하는 메뉴·목록·상세 조회
- 이전 테스트 버전에서의 업데이트와 migration 전 롤백 또는 migration 이후 DB 백업 복원
- Ubuntu 24.04 `linux/amd64`의 Docker Compose 환경에서 health·ready와 대표 핵심 기능 확인

LDAP·Active Directory 인증, 역할 권한, 담당자·감사, 보관·삭제, 매일 22시 자동 수집, 자산별 동기화, 검색·필터·정렬, 사용자별 목록 설정과 운영 상태 화면은 Phase 1 및 후속 작업으로 유지하며 0.1.0 지원 범위에서 제외한다. 이 기능을 구현한 것으로 간주하거나 0.1.0 공개를 이유로 기존 Phase 완료 기준을 변경하지 않는다. 공개 릴리스에는 현재 구현과 계획을 구분한 알려진 제한 사항을 포함한다.

### Phase 0: 샘플 수집부터 저장·조회까지

현재 상태: **진행 중**. 수집부터 저장·조회까지의 기반은 위 표와 같이 완료되었으나, 다음 작업과 최종 통합 검증이 남아 있다.

남은 작업:

1. 첫 실제 수집처의 비밀정보를 제거한 샘플을 확보하고 식별자·상태·데이터 규모·호출 규칙을 확인한다. 추가 수집 방식은 실제 요구에 따라 별도 change로 정의한다.
2. 개인별 표시 컬럼·순서·너비 등 목록 설정을 브라우저에 저장·복원한다.
3. 기존 수집 상태 조회 API를 사용해 마지막 수집 상태·시각을 화면에 표시한다.
4. 큰 본문의 분리 저장·참조와 건수·바이트·메모리·응답 기준을 구체화한다.
5. 위 기능을 연결한 뒤 기존 수집·가공·저장·조회 계약을 포함해 아래 완료 기준을 통합 검증한다. 실제 수집처의 원천 변경·중단·재개·규모 제약도 확인한다.

완료 기준(기존 구현의 회귀 검증 포함):

- 계정관리를 비활성화하고 Redis·주기 worker 없이 원천 mock API → 플러그인 가공 → 공통 검증·DB 저장 → 메뉴·목록·상세가 동작한다.
- API와 데이터 구조가 다른 플러그인도 파일 추가·등록·빌드·배포만으로 동작한다. 본체 diff 없이 저장·조회·메뉴·화면이 확장되는지 확인한다.
- 중첩 배열의 레코드·관계 변환과 잘못된 가공 결과의 적재 차단을 검증한다.
- 계정관리 비활성화 상태에서 사용자 컬럼 선택·순서·너비 등 목록 설정이 현재 브라우저에 저장·복원되고 플러그인 기본 정의를 변경하지 않는다.
- 같은 샘플을 다시 수집해도 동일 항목이 중복되지 않고 변경 값이 갱신된다.
- 원천을 중단해도 저장된 목록·상세를 조회하며 마지막 수집 상태·시각을 확인할 수 있다.
- 저장 완료 전 checkpoint가 앞서가지 않고 재개 결과에 누락이 없다.
- 목록과 큰 본문이 분리되고 사전에 정한 건수·바이트·메모리·응답 기준을 검증한다.
- 플랫폼 DB와 원천 fixture는 설정·계정·영속 저장소가 분리된다.
- PostgreSQL·MySQL의 기본 저장·조회·재수집 계약 테스트를 통과한다.

이 단계에는 LDAP 로그인, 차트, 자동 수집 큐, Helm과 운영 규모 성능 보장을 포함하지 않는다. 대용량 검증은 작은 기능 경로에서 재현 가능한 fixture로 수행한다.

### Phase 1: 기본 업무와 설치 가능한 MVP

확정된 역할 권한을 바탕으로 사용자 식별·자산 연결과 동기화 실행 계약을 정한 뒤 화면·인증·스케줄을 연결한다. 필드·키 변경의 호환성 검사와 미지원 변경 차단은 이 단계에 포함한다.

- 계정관리는 기본 비활성화로 제공한다. 설정으로 활성화한 LDAP·AD 인증과 로그인 없는 기본 실행을 각각 검증한다.
- 구현된 [기동·재시작 전체 수집](../../openspec/specs/startup-full-collection/spec.md)과 [대상별 실행 조정](../../openspec/specs/collection-run-coordination/spec.md)을 기반으로 매일 22:00 전체 동기화를 추가한다. 우선 Asia/Seoul을 사용하며 정기 실행과 기존 실행 간 충돌·부분 실패·수동 업무 데이터 보존을 검증한다.
- 원천 필드 기본 담당자와 수동 복수 지정 우선 규칙, 원천 기본값 복귀·감사·접근 범위 변경을 구현한다.
- 권한에 따른 자산 수동 삭제와 감사 기록을 구현한다. 확정된 영구 삭제·동일 키 재수집 시 신규 등록 정책을 적용한다.
- 같은 DB에서 활성·보관 목록을 제공하고 검증된 전체 수집의 미확인 자산 보관과 동일 키 재등장 시 복원을 구현한다.
- 자산별 동기화 버튼·실행 상태와 전체 동기화 실패 시 상단 알림을 제공하고 동기화 중 기존 데이터 조회를 검증한다.
- Employee 조회 전용·담당 자산 제한과 Security·Audit·Admin 전체 권한을 적용하고 사용자 식별·담당 자산 연결에 대한 공통 서버 권한 검사를 구현한다. Employee의 타인 자산 접근은 목록·상세·검색·집계·다운로드 및 직접 API 호출에서 차단한다.
- 기존 기본 목록·상세에 서버 권한 경계를 연결하고 화면 교체 시에도 같은 조회·권한 계약을 유지하도록 설계·검증한다. 사용자 정의 화면 파일의 등록·빌드·배포 지원은 Phase 2로 미룬다.
- 기존 최상위 object·array의 재귀 JSON 표시를 바탕으로 업무용 중첩 필드 경로·요소 타입 검증과 표시 규칙을 확장한다.
- 첫 실제 수집처를 연결하고 식별·상태 변환·중복·갱신·부분 실패 정책을 검증한다.
- fixture·JSON-file·REST·PostgreSQL connector를 한 개씩 확장한다. 기존 조회 화면·API에 수집처별 원천 코드를 추가하지 않는다.
- 플랫폼 DB의 검색·정렬·필터를 구현하고 기존 cursor 묶음 이동에 결합한다. 자산·취약점 상세에 업무 데이터와 권한을 연결한다.
- 담당자 지정 API·화면·감사와 재수집 시 보존을 검증한다. 계정관리 비활성화 상태의 담당자 표현·감사 주체를 먼저 설계한다.
- 기존 상태 조회 API를 사용하는 수집 결과·오류·설정 revision의 읽기 전용 운영 화면을 제공하고 변경된 운영 절차를 수동 CLI 가이드에 반영한다.
- 기존 JSON 구조·참조 검증에 신규 계약을 반영하고 개발 전용 설정 hot reload와 화면 상태 복원을 구성한다.
- 큰 본문 저장·참조·다운로드·보존·실패 정리를 구현하고 원본 전체 저장 여부는 필요에 따라 선택한다.
- 기존 양쪽 DB migration·계약 테스트와 릴리스 이미지·Compose를 기반으로 최종 오프라인 번들 및 설치·업데이트·복구 절차를 완성하고 같은 배포물로 검증한다.

완료 기준(기존 구현의 회귀 검증 포함):

- 사용자가 계정관리를 비활성화하고 샘플로 설치하고 실제 수집처 설정으로 전환할 수 있다.
- 수집 후 조회 API는 플랫폼 DB만 사용하며 UI 조회가 원천 읽기를 유발하지 않는다.
- 담당자 변경이 재수집으로 덮어써지지 않고 누락·실패를 해결로 오판하지 않는다.
- 실패·부분 성공은 자산 보관을 유발하지 않는다. 검증된 전체 수집 후 미확인 자산을 보관하고 동일 키 재등장 시 내부 ID·수동 담당자·이력을 유지해 복원한다.
- 공식 예제와 양쪽 DB 테스트가 CI를 통과한다.
- 역할·대상 접근 검증이 플러그인별 예외 없이 동작하고, 계정관리 비활성화와 활성화의 경계가 문서화된다.
- 이미지로 설치한 환경에서도 수동 수집을 실행할 수 있다. 수동 수집은 자동 수집 큐에 의존하지 않는다.
- 큰 데이터의 제한·보존 정책과 검증한 규모가 문서화되어 있다.
- LDAP 로그인·그룹 역할 매핑과 계정관리 비활성화 상태를 각각 실행 검증하고 LDAP 실패가 모드 전환을 일으키지 않는다.
- 원천 담당자 기본값·수동 복수 지정에 의한 대체·기본값 복귀와 Employee 조회 범위를 검증한다.
- 최초 실행의 등록 대상 전체 동기화·재시작 중복 방지·실패 기록과 인증 제공자 교체 시 공통 권한 경계를 검증한다.
- 지정 시간대 매일 22:00 전체 범위 실행, 재시작 전체 동기화·동시 실행 중복 방지, 실패·부분 실패 상단 알림, 동기화 중 기존 조회와 수동 지정 보존을 검증한다.
- 자산별 버튼·비동기 실행 상태·권한 검사·전체 실행과의 충돌 방지·다른 자산 보존을 검증한다.
- 실패 대상·범위의 다음 정상 동기화 후 알림이 해제되고 실패 이력은 남는다. 다른 대상·부분 범위의 성공으로 미해결 알림이 해제되지 않는다.
- cursor 기반 20·50·100·200건 묶음 이동과 검색·필터·정렬, 권한을 적용한 `hasNextPage`가 실제 DB에서 동작한다. 목록 설정은 계정관리 활성화 시 계정별 DB에, 비활성화 시 브라우저에 저장·복원하며 다른 계정의 설정이 섞이지 않는다.
- 기본 목록·상세가 공통 조회·필드 계약과 서버 권한 검사를 사용하며 추후 화면 교체가 저장·조회·권한 코드 변경을 요구하지 않는 구조인지 검증한다.
- 객체 배열의 login 태그와 중첩 날짜 표시가 필수 가공·검증·저장을 거쳐 기본 화면에서 동작한다.
- 필드·유일키 변경의 호환성 검사, 미지원 변경 차단과 코드/DB 롤백 절차를 검증한다.

### Phase 2: 운영 편의와 선택 연동

- MVP에서 설계한 화면 교체 계약에 따라 List.tsx·Detail.tsx 등 사용자 정의 화면의 등록·플랫폼 빌드·배포와 공통 권한 적용을 구현한다. 외부 프론트엔드 번들 로딩은 별도 계약으로 다시 설계한다.

핵심 수집·저장·조회가 검증된 후 필요에 따라 각 작업을 독립적으로 착수한다.

- 자동 수집 고도화: MVP의 일일·자산별 동기화 API 위에 일괄 실행 API, Redis + BullMQ, worker, 취소·모니터링을 필요에 따라 추가
- 증분 수집 최적화: 원천이 지원하는 변경분·삭제 이벤트 활용; 미지원 원천의 전체 비교 비용 검증
- 저장 데이터의 숫자 카드·막대·파이 차트와 집계 최적화
- LDAP 운영 고도화: MVP의 선택 인증·역할 매핑을 바탕으로 실제 운영 요구를 개선; 계정관리 비활성화 경로 유지
- MVP의 공개 SDK·예제를 바탕으로 생성 도구와 외부 패키지 배포·로딩 고도화
- MVP의 변경 호환성 정책을 바탕으로 범용 migration·재가공 도구와 운영 UI 고도화
- PR preview·문서 사이트 및 Helm 선택 배포 검증

Redis·worker는 큐 기반 자동 수집을 선택한 환경의 실행 의존성이며 데이터 저장 자체의 선택 여부를 결정하지 않는다. LDAP·Helm은 일반 사용자의 설치 선행 조건이 아니다.

### Phase 3: 수요가 확인된 확장

- 기존 기본 관계 모델을 활용한 관계 그래프·분석 고도화
- webhook·GraphQL·S3 및 추가 원천 DB connector
- 여러 수집처의 의미가 검증된 통합 검색·중복 연계와 dashboard composition
- 정책·알림·추가 스캐너 결과 연동 plugin

AI·IAM·규제 대응·분산 처리 및 자동 확장은 실제 필요성과 성능 측정에 근거해 별도 계획으로 검토한다.

## 13. MVP에서 제외할 기능

다음 기능은 초기 개발 범위에서 제외한다.

- AI 분석
- 외부 IAM 권한 부여 및 회수 (플랫폼 내부 Employee·Security·Audit·Admin 접근 제어는 포함)
- 플랫폼 자체 계정 생성·비밀번호 로그인 구현 (인증 제공자 확장 경계는 MVP에서 설계)
- SSO, OIDC, SAML 로그인 연동
- DevSecOps 스캐너 직접 실행
- JSON·웹 입력 문자열을 실행하는 자유 형식 JavaScript transform (빌드에 포함하는 플러그인 가공 코드는 지원 범위)
- 운영 시점 TypeScript transpile, 플러그인별 임의 의존성 설치, 원격 코드 다운로드와 웹 UI 플러그인 설치·수정
- 외부 사용자 정의 React 화면 번들 로딩
- 원본 DB에 대한 자유 형식 SQL 전달
- 실시간 이벤트 처리 플랫폼 (대용량을 나눠 읽는 수집 스트리밍은 기본 처리에 포함)
- 복잡한 관계 그래프
- 완전한 대시보드 편집기
- 모든 데이터베이스와 클라우드 SDK 내장
- 원천 직접 조회 화면, 고급 큐·워커, 차트·Helm의 완성 (후속 단계에서 진행; 일일 전체 동기화와 선택 LDAP 지원은 MVP에 포함)

## 14. 공통 운영 원칙

- JSON·웹 입력을 코드로 실행하지 않는다. 배포에 포함한 가공·custom 수집 코드의 의존성·버전과 실행 제한을 관리한다.
- 원천 연결의 읽기 권한·timeout·크기 제한을 적용하고 비밀정보는 응답·로그에 출력하지 않는다.
- LDAP는 LDAPS 또는 StartTLS와 인증서 검증을 사용한다. 역할 매핑 실패는 접근 거부로 처리하고 계정관리를 자동 비활성화하지 않는다. 비밀번호를 저장·기록하지 않는다.
- 플랫폼 이미지와 외부 플러그인·설정·정책 revision의 조합을 고정하고 DB 호환성을 확인한다. 데이터 변경의 복구는 이미지나 Git revision 롤백과 별도 절차로 다룬다.

## 15. 다음 작업

현재 활성 OpenSpec change는 없다. 완료된 기반은 12절에 모아 두고, 다음 작업은 아래 공개 준비와 기능 확장 후보에서 구체화한다.

0.1.0 공개 준비는 [기술 프리뷰의 출시 차단 게이트](../../openspec/specs/technical-preview-release/spec.md)를 기준으로 추적한다. [Release 자산 자동화](../../openspec/specs/github-release-artifacts/spec.md)는 API·웹 내부 산출물로 기본 번들과 PostgreSQL 포함 번들을 만들고, GitHub Release에는 두 번들과 외부 `SHA256SUMS`만 게시한다. 공개 전 최종 번들 검증과 태그 후보 CI 등 각 게이트의 증거를 확인한다.

기능 확장 후보는 서버 검색·필터·정렬과 개인별 목록 설정, 기존 상태 조회 API를 사용하는 운영 화면, 매일 22시 정기 수집 및 Phase 0의 나머지 완료 기준이다. 각 후보는 기존 계약을 기반으로 별도 change에서 구체화하며 후보 간 착수 순서는 아직 확정하지 않았다.

- **수동 삭제**: 원천 부재 확인 방법, 영구 삭제 시 공유 관계·본문 등 관련 데이터 정리 경계

- **플러그인 확장**: 기존 [선언·source 계약](../../openspec/specs/plugin-source-contract/spec.md), [가공 실행](../../openspec/specs/plugin-transform-runtime/spec.md), [묶음·checkpoint·오류 처리](../../openspec/specs/common-collection-runner/spec.md), [서버 배포 계약](../../openspec/specs/server-plugin-deployment/spec.md)은 확정되어 있다. 남은 결정은 page·custom 등 추가 수집 방식, 필드·키 변경의 호환성 정책과 Phase 2의 외부 UI 빌드·SDK·번들 계약이다.
- **DB 확장**: 기존 [공통 저장 모델·관계·유일키 범위](../../openspec/specs/platform-record-storage/spec.md)와 [PostgreSQL](../../openspec/specs/postgresql-platform-db/spec.md)·[MySQL](../../openspec/specs/mysql-platform-db/spec.md) 연결·migration 계약은 확정되어 있다. 남은 결정은 업무 관계·검색 인덱스 확장, 필드·유일키 변경 시 데이터 이관과 릴리스별 DB 지원·호환성 정책이다.
- **인증·권한**: LDAP 사용자 매핑·세션, 복수 역할·복수 자산 규칙과 권한 변경 시 반영 방식
- **담당자**: 플러그인별 담당자 필드↔계정 속성 매핑 설정 형식과 미일치·다중 일치 상태 표시, 계정관리 비활성화 상태 표현·감사 주체
- **동기화·알림**: 기동 수집과 [대상별 실행 충돌 조정](../../openspec/specs/collection-run-coordination/spec.md)은 확정되어 있다. 남은 결정은 Asia/Seoul 기준 매일 22시 스케줄러, 정기 실행과 기존 실행의 결합, 운영 화면·알림 및 실패 이력 보존 기간이다.
- **목록**: 플러그인 지정 필터의 지원 종류·연산자·옵션 공급 방식, 다중 정렬, 검색의 대소문자·여러 단어·배열/비문자 타입 처리, 필드 변경·계정관리 설정 전환 시 목록 설정 처리
- **운영 규모**: 첫 실제 수집처와 대표 샘플, 건수·바이트·응답 한도, 큰 본문 저장 위치와 원본·이력 보존 기간
- **릴리스**: [0.1.0 기술 프리뷰](../../openspec/specs/technical-preview-release/spec.md)의 Ubuntu 24.04 linux/amd64·Docker Compose·PostgreSQL 17.6/MySQL 8.4.6 검증 대상과 [태그·번들 자산 게시 규칙](../../openspec/specs/github-release-artifacts/spec.md)은 확정되어 있다. GitHub Release는 기본 번들, PostgreSQL 포함 번들과 외부 `SHA256SUMS`만 공개한다. 남은 항목은 라이선스와 후속 지원 환경 확대다.

Node.js 24 LTS·pnpm·React/Vite·NestJS와 PostgreSQL/MySQL 지원은 유지한다. Redis/BullMQ는 후속 큐 기반 고도화에 사용하며 일일 동기화의 필수 설치 조건으로 고정하지 않는다.
