# 브랜치 및 릴리스 전략

이 문서는 oss-scp의 소스 개발, PR 병합, 출시 후보 검증과 제품 릴리스 기준을 정의한다. 첫 정식 릴리스는 `1.0.0`을 목표로 하며 클라이언트와 서버를 하나의 제품 버전으로 함께 릴리스한다.

## 기본 브랜치 흐름

GitHub Flow를 기본으로 사용한다. 작업 브랜치에서 개발하고 PR로 `main`에 통합한다. `main`은 빌드와 적용 가능한 테스트를 통과한 상태로 유지한다. 병합할 때마다 정식 버전을 출시할 필요는 없다.

| 브랜치 | 시작 지점 | 역할과 종료 시점 |
| --- | --- | --- |
| `main` | 저장소 기본 브랜치 | 검증된 변경을 통합하며 계속 유지 |
| `feature/<name>` | `main` | 기능 개발 후 PR 병합 시 삭제 |
| `fix/<name>` | `main` | 일반 버그 수정 후 PR 병합 시 삭제 |
| `release/<version>` | 출시 대상 main 커밋 | 별도 QA가 필요할 때 생성하고 출시 및 수정 반영 확인 후 삭제 |
| `hotfix/<name>` | 수정할 출시 버전 태그 | 기존 출시 버전의 긴급 수정과 패치 릴리스 후 삭제 |

Codex의 작업 브랜치는 `codex/<작업명>` 형식을 사용할 수 있으며 동일한 PR·검증 기준을 적용한다.

작업 브랜치는 하나의 목적을 담은 작은 PR로 짧게 유지한다. 설정된 필수 CI와 리뷰를 통과한 뒤 병합한다. 애플리케이션·CI가 없는 초기 단계에는 변경 문서와 링크를 검토하고, 이후 구현된 검사 항목을 적용한다.

클라이언트와 서버가 함께 바뀌어야 동작하는 변경은 가능한 한 하나의 PR에 담는다. 여러 PR로 나누면 각 병합 시점에도 빌드와 기존 기능이 유지되도록 순서를 정하고 관련 이슈와 의존 관계를 명시한다.

## 버전 정책

제품 버전은 `MAJOR.MINOR.PATCH` 형식으로 관리하고 Git 태그에 `v`를 붙인다.

- `0.x.y`: 정식 출시 전 중간 결과를 공유하고 검증하는 개발 릴리스이며 GitHub에서는 prerelease로 표시한다.
- `1.0.0-rc.1`, `1.0.0-rc.2`: 기능 범위를 완료한 뒤 검증하는 출시 후보 버전이다.
- `1.0.0`: 합의한 기능 범위와 검증 기준을 충족한 첫 정식 릴리스다.
- 이후 호환 가능한 버그 수정은 `1.0.1`, 호환 가능한 기능 추가는 `1.1.0`, 공개 계약을 깨는 변경은 `2.0.0`처럼 올린다.

클라이언트와 서버는 동일한 제품 버전을 사용하고 각 이미지 digest는 별도로 기록한다. 제품 버전과 API·설정 schema 버전은 별도로 관리한다. 개발 릴리스에서도 계약 변경은 릴리스 노트에 기록한다.

릴리스 자동화는 `v<MAJOR>.<MINOR>.<PATCH>`와 `v<MAJOR>.<MINOR>.<PATCH>-rc.<NUMBER>` 태그만 허용한다. 태그 commit에서 전체 CI를 다시 통과한 뒤 개별 Docker image archive, 버전 고정 Compose, 환경변수 예시와 checksum을 만든다. 이어서 이 자산을 재검증해 기본 폐쇄망 번들과 PostgreSQL 포함 번들을 생성·검증하고 같은 draft에 업로드한 후 공개한다. 동일 태그의 GitHub Release가 이미 있으면 기존 본문이나 자산을 덮어쓰지 않고 실패한다. 사용 절차는 [폐쇄망 번들 가이드](offline-bundle.md)를 따른다.

## 0.1.0 기술 프리뷰

0.1.0은 외부 Registry에 접근할 수 없는 폐쇄망 단일 서버에서 oss-scp의 핵심 흐름을 평가하고 초기 도입 가능성을 확인하기 위한 개발 릴리스다. 운영 안정판이나 장기 지원 버전이 아니며, 아래에 명시하지 않은 환경과 기능의 호환성을 보장하지 않는다. 첫 정식 릴리스 목표와 완료 기준은 기존 1.0.0 범위를 유지한다.

검증 대상 배포 환경은 Ubuntu 24.04 `linux/amd64`와 Docker Compose다. 운영 DB는 PostgreSQL 17.6과 MySQL 8.4.6 조합을 검증한다. macOS를 포함한 로컬 개발 환경과 그 밖의 OS·CPU 아키텍처·컨테이너 런타임·DB 버전은 동작할 수 있어도 0.1.0 지원 조합으로 표시하지 않는다.

0.1.0은 다음 사용자 여정을 지원 범위로 둔다.

1. 오프라인 번들의 checksum과 대상 버전을 확인하고 이미지를 load한다.
2. 버전이 고정된 Compose와 별도 운영자 플러그인·Connection 설정을 사용한다. 외부 설정은 읽기 전용으로 주입하고 기동 전에 검증한다.
3. 지원 DB에 명시적으로 migration을 적용한 뒤 API와 웹을 기동하고 health·ready를 확인한다.
4. 지원 원천을 수집·가공해 플랫폼 DB에 저장하고 원천을 다시 읽지 않는 목록·상세 화면에서 결과를 조회한다.
5. 이전 테스트 버전에서 0.1.0으로 업데이트해 데이터와 외부 설정 보존을 확인하고, 의도한 실패 단계에 맞춰 이전 이미지로 롤백하거나 DB 백업을 복원한다.

다음 기능은 0.1.0 지원 범위에 포함하지 않고 릴리스 노트의 알려진 제한 사항에 기록한다.

- LDAP·Active Directory 인증과 역할 기반 접근 제어
- 담당자 지정·감사, 보관·복원과 수동 삭제
- 매일 22시 자동 수집과 자산별 동기화
- 검색·필터·정렬과 사용자별 목록 설정
- 수집 상태·오류·설정 revision 운영 화면
- 0.1.0 이후 버전과의 장기 호환성·유지보수 보장

0.1.0 공개 전에는 다음 게이트를 모두 통과해야 한다.

- 외부 설정 주입 #70, 릴리스 자동화 #71, 오프라인 번들 #88, 공개 OSS 정책·문서 #89 완료
- 공개할 태그 commit에서 PostgreSQL·MySQL·로컬 빌드·Docker·브라우저를 포함한 전체 CI 성공
- 공개할 산출물과 동일한 번들로 깨끗한 폐쇄망 환경의 최초 설치·업데이트·실패 복구 검증
- 제품 버전, Git revision, 이미지 digest, checksum, 검증 환경과 알려진 제한 사항을 포함한 릴리스 노트 검토

하나라도 충족하지 않으면 `v0.1.0` 태그와 공개 릴리스를 만들지 않는다. 성공한 최종 commit에 이동하지 않는 태그를 한 번 생성하고, GitHub에서는 기술 프리뷰임을 알 수 있도록 prerelease로 표시한다.

## 1.0.0 개발과 출시

1.0.0의 기능 범위와 완료 기준은 개발 플랜에서 정하고 구현 작업은 OpenSpec change와 관련 이슈로 추적한다. 기능 개발은 작업 브랜치에서 main으로 계속 통합한다.

1. 1.0.0 범위를 완료하면 `main`에서 출시 대상 커밋을 정한다.
2. 후속 개발과 QA를 병행해야 한다면 해당 커밋에서 `release/1.0.0`을 만든다. 분리가 필요하지 않으면 main의 출시 대상 커밋에서 검증한다.
3. 후보 커밋에 `v1.0.0-rc.1` 태그를 붙이고 클라이언트·서버를 함께 빌드해 검사한다.
4. 수정이 필요하면 새 커밋과 `v1.0.0-rc.2` 등 새 후보 태그로 다시 검증한다. 공개한 태그를 다른 커밋으로 옮기지 않는다.
5. 최종 검증된 커밋에 `v1.0.0` 태그를 붙이고 소스와 클라이언트·서버 이미지 조합을 릴리스한다. 공개하는 최종 아티팩트도 검증 대상과 일치하는지 확인한다.

release 브랜치에는 출시를 위한 버그 수정만 반영하며 새 기능은 main에서 개발한다. QA 수정은 원칙적으로 main에 PR로 병합한 뒤 release 브랜치에 필요한 커밋을 반영한다. 코드 차이로 release에서 먼저 수정해야 한다면 main에도 대응 PR을 만들어 누락되지 않게 한다. 각각 반영한 브랜치에서 다시 검증한다.

릴리스 노트에는 변경 사항, 호환성을 깨는 변경, 소스 태그와 이미지 digest를 기록한다. 출시가 끝나고 필요한 수정이 main에 반영되면 release 브랜치를 삭제한다. 출시 소스는 태그로 보존한다.

## 출시 버그 수정과 다음 버전 개발

v1.0.0 출시 후 main에서 1.1.0 기능을 개발하는 중에 1.0.1 수정이 필요하면 다음 흐름을 따른다.

1. `v1.0.0` 태그에서 `hotfix/<name>`을 만든다.
2. 필요한 버그 수정만 반영하고 클라이언트·서버 조합을 검증한다.
3. 패치 커밋에 `v1.0.1` 태그를 붙여 패치 릴리스를 제공한다.
4. 동일한 수정 또는 현재 코드에 맞춘 대응 수정을 PR로 main에도 반영한다. 진행 중인 release 브랜치도 영향을 받으면 반영하고 검증한다.
5. 릴리스와 후속 반영을 확인한 뒤 hotfix 브랜치를 삭제한다.

이 방식으로 다음 버전의 미출시 기능을 패치 릴리스에 포함하지 않는다. 여러 과거 버전을 장기간 유지보수해야 하면 지원 범위와 유지보수 브랜치 규칙을 별도로 정한다.

## PR과 릴리스 검증 기준

PR에는 변경 목적, 영향받는 클라이언트·서버·공통 패키지, 관련 이슈, 실행한 검증을 적는다. API나 schema를 바꾸면 호환성 영향과 함께 반영해야 하는 변경을 명시한다.

- 코드 변경: 영향받는 패키지의 빌드·타입 검사와 필요한 테스트
- API·schema 변경: 관련 계약 검증
- 클라이언트·서버 연계 변경: 함께 동작하는지 통합 검증
- 릴리스: 태그 커밋과 제공할 클라이언트·서버 아티팩트 조합 확인
- 문서 변경: 내용과 링크 확인

구체적인 실행 명령은 애플리케이션과 CI 구성 시 추가한다. 아직 없는 검사나 실행하지 않은 검사를 통과했다고 기록하지 않는다.
