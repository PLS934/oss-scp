# 개발 및 배포 워크플로

이 문서는 클라이언트와 서버를 함께 개발하고 배포할 때 지켜야 할 저장소·릴리스 운영 규칙을 정의한다. 제품의 기술 방향과 범위는 통합 개발 플랜에서 관리하고, 이 문서는 변경을 실제로 통합하고 배포하는 방법을 다룬다.

## 기본 원칙

- `main`은 언제든 배포할 수 있는 상태를 유지한다.
- 작업 브랜치는 짧게 유지하고, 하나의 목적을 담은 작은 PR로 `main`에 병합한다.
- 클라이언트와 서버의 배포 파일은 릴리스 시점에 하나의 버전 조합으로 고정한다.
- 배포 순서를 맞추기보다 이전 클라이언트와 새 서버가 잠시 함께 동작하도록 API를 설계한다.
- 호환성 검증과 통합 테스트가 끝난 뒤 기능 플래그를 켠다.

## 브랜치 전략

GitHub Flow를 기본으로 사용한다. 정기 출시를 위한 장기 `develop` 브랜치나 상시 `release` 브랜치는 만들지 않는다.

```text
main ──●────●────●────────●────●────  (항상 배포 가능)
        \  feature/*  /    \ fix/* /
         └──── PR ────┘      └─ PR ┘
                              │
                        release tag
```

브랜치 이름은 목적이 드러나도록 다음처럼 작성한다.

| 브랜치 | 용도 | 수명 |
| --- | --- | --- |
| `main` | 검증을 통과한 통합 코드와 운영 배포 기준 | 영구 |
| `feature/<name>` | 기능 개발 | 짧게, PR 병합 후 삭제 |
| `fix/<name>` | 일반 버그 수정 | 짧게, PR 병합 후 삭제 |
| `hotfix/<name>` | 운영 장애나 긴급 보안 수정 | 짧게, `main`에 우선 병합 |
| `release/<version>` | 출시 조합을 고정해 통합 QA가 필요할 때만 사용 | QA 기간 동안만 |

`release/*`는 개발을 분리하기 위한 상시 브랜치가 아니다. 여러 변경을 한 번에 검증하거나 배포 승인 대기 중 `main`의 후속 개발을 계속해야 할 때만 `main`에서 만든다. QA 중 발견한 수정은 먼저 `main`에 반영한 뒤 release 브랜치에도 반영해 두 경로가 어긋나지 않게 한다.

모든 PR은 CI를 통과하고 리뷰 승인을 받은 뒤 병합한다. 클라이언트와 서버의 변경이 함께 있어야 동작하는 경우에는 하나의 PR로 묶거나, 두 PR에 같은 릴리스 이슈와 호환성 설명을 연결한다.

## 버전 정책과 1.0.0 개발 목표

첫 정식 릴리스는 `1.0.0`을 목표로 한다. 제품 버전은 `MAJOR.MINOR.PATCH` 형식을 사용하고, Git 태그에는 `v`를 붙인다. 예를 들어 제품 버전 `1.0.0`의 태그는 `v1.0.0`이다. 날짜 기반 버전은 사용하지 않는다.

- `0.x.y`: 정식 출시 전 개발·검증용 릴리스. 필요한 중간 결과를 배포할 때 사용하며, 계약이 바뀔 수 있음을 릴리스 노트에 명시한다.
- `1.0.0-rc.1`, `1.0.0-rc.2`: 1.0.0의 기능 범위를 완료한 뒤 통합 QA에 사용하는 출시 후보 버전이다.
- `1.0.0`: 합의한 출시 범위와 검증 기준을 충족한 첫 정식 릴리스다.
- 정식 출시 이후에는 호환 가능한 버그 수정은 `1.0.1`, 호환 가능한 기능 추가는 `1.1.0`, 공개 계약을 깨는 변경은 `2.0.0`처럼 올린다.

클라이언트와 서버는 하나의 제품 릴리스 버전을 공유한다. 각 이미지 digest는 별도로 기록한다. 제품 버전과 API·설정 schema 버전은 별도로 관리하며, 제품 릴리스마다 API 버전을 바꾸지는 않는다.

`1.0.0`은 개발 목표이며 개발 기간 내내 유지할 브랜치 이름이 아니다. 기능 개발은 작업 브랜치에서 `main`으로 통합하고, 출시 후보를 고정할 시점에 필요하면 `release/1.0.0`을 만든다. 기능 범위와 완료 기준은 통합 개발 플랜에서 정의하고, 구현 변경은 OpenSpec change로 나누어 추적한다. 버전 번호만으로 1.0.0의 기능 범위가 확정되지는 않는다.

## 릴리스와 배포

릴리스는 **검증한 클라이언트·서버 아티팩트의 조합**으로 정의한다. 예를 들어 `v1.0.0`은 다음을 함께 가리킨다.

```text
v1.0.0
├── client: web 이미지 또는 빌드 artifact sha256:...
└── server: api 이미지 sha256:...
```

권장 흐름은 다음과 같다.

1. `main`에서 출시 대상 커밋을 정한다. 별도 QA 기간이 필요하면 이 시점에 `release/1.0.0`을 만든다.
2. 선택한 커밋을 기준으로 클라이언트와 서버를 각각 빌드한다.
3. 단위 테스트, 계약 테스트, 통합 테스트, 배포 이미지 검사를 실행한다.
4. `v1.0.0-rc.1` 같은 후보 태그에 커밋을 고정하고, 이미지 digest와 설정 버전을 기록해 스테이징에서 통합 QA를 진행한다. 수정이 생기면 새 후보 버전으로 다시 빌드하고 검증한다.
5. 승인된 커밋에 `v1.0.0` 태그를 붙이고 릴리스 노트에 클라이언트·서버 digest를 함께 기록한다.
6. 검증한 아티팩트를 재빌드하지 않고 동일한 digest 조합으로 운영에 배포한다.

운영 장애가 발생하면 마지막으로 검증된 릴리스의 클라이언트·서버 조합으로 함께 되돌린다. 데이터베이스 migration은 되돌릴 수 없을 수 있으므로, 배포 전에 하위 호환 migration인지와 롤백 절차를 별도로 확인한다.

## 클라이언트·서버 호환 규칙

모바일 앱이나 이미 열린 웹 탭은 즉시 업데이트되지 않을 수 있으므로, 동시 배포를 전제로 API를 깨뜨리지 않는다.

새 API나 필드는 다음 순서로 변경한다.

1. 서버에 새 필드·엔드포인트를 추가하고 기존 요청·응답을 계속 지원한다.
2. 서버의 호환성 테스트를 통과시킨다.
3. 클라이언트가 새 계약을 사용하도록 배포한다.
4. 모니터링으로 구버전 클라이언트 사용이 충분히 줄었는지 확인한다.
5. 제거가 필요한 경우 별도 변경으로 공지하고, 유예 기간 뒤에 이전 계약을 제거한다.

응답 필드를 삭제하거나 타입을 바꾸는 변경, 필수 요청 필드를 즉시 추가하는 변경은 breaking change로 취급한다. 이런 변경은 버전을 올리고, 구버전 클라이언트를 지원하는 기간과 제거 일정을 릴리스 노트에 명시한다.

## 기능 플래그

클라이언트와 서버에 걸쳐 동시에 활성화해야 하는 기능은 기능 플래그 뒤에 둔다. 배포는 코드를 포함하는 단계이고, 플래그 활성화는 검증이 끝난 뒤 기능을 공개하는 단계다.

- 기본값은 안전한 이전 동작으로 둔다.
- 스테이징에서 클라이언트·서버 플래그를 함께 켜고 통합 검증한다.
- 운영에서는 제한된 사용자나 내부 환경부터 단계적으로 켠다.
- 플래그 제거 시점과 담당자를 이슈에 기록한다. 영구 플래그를 만들지 않는다.

## PR과 검증 기준

PR 본문에는 변경 목적, 영향을 받는 앱(`web`, `api`, `worker` 등), API 호환성 여부, 기능 플래그 여부, 실행한 검증을 적는다. 클라이언트와 서버가 함께 바뀌면 배포 순서와 구버전 호환 기간도 적는다.

최소 검증 기준은 다음과 같다.

- 변경된 패키지의 단위 테스트와 타입 검사
- API 계약 또는 schema 변경 시 계약 테스트
- 클라이언트·서버가 함께 바뀐 경우 Docker 기반 통합 테스트
- 릴리스 후보의 이미지 digest와 설정 버전 기록

이 규칙은 애플리케이션과 CI가 추가된 뒤 실제 명령으로 구체화한다. 명령이 아직 없는 단계에서는 문서에 존재하지 않는 스크립트를 성공 기준으로 간주하지 않는다.
